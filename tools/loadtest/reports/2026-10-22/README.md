## 一、一句话结论

**单机 2 核 1.6G、workers=1：服务端单请求 27ms（本机回环、2 并发），吞吐天花板 ~75 QPS，
拐点在 20 并发；40 并发时 CPU 86% 占满——瓶颈是 CPU，不是线程池。全程 34,997 请求 0 失败。**

### 服务器本机轮（第三轮，`srv.html`，压 127.0.0.1:8000，不含 nginx 与网络）

| 并发 | QPS | 中位 | P95 | P99 |
|---|---|---|---|---|
| 2 | 75.8 | **27ms** | 39ms | 56ms |
| 10 | 71.5 | 32ms | 180ms | 220ms |
| 20 | 68.0 | 84ms | 340ms | 430ms |
| 40 | 67.8 | 150ms | 615ms | 810ms |

压测中抓的服务器快照（40 并发档）：`%Cpu 68.2 us + 18.2 sy = 86.4%`，load average **4.95**（2 核），
locust 进程自身占 23.6%。**吞吐天花板 ~75 QPS 在两侧测量一致**（远程压 75.2–76.2，本机压 67.8–75.8），
天花板是 CPU，不是 anyio 线程池的 40——40 并发时线程根本没排队，是核不够了。

## 二、这份记录能证明什么、不能证明什么

能证明：

- 压测是真实跑的：原始 CSV（逐秒采样）+ locust HTML 报告都在本目录，命令可复现
- 0.00% 失败率：8,832 + 13,345 = 22,177 个请求，无一失败、无 5xx、无超时
- 饱和点与延迟增长曲线（P95 与并发近似线性，符合 Little's law 的定性预期）
- 端到端可复现：脚本在 `tools/loadtest/`，任何人 clone 下来十几分钟可以重跑

不能证明（面试里主动交代，别等被问）：

1. **远程轮的延迟含网络 RTT**（~85ms，health 基线）。服务器本机轮没有这层，
   但压测发生器和服务抢同一个 CPU，高并发档的延迟被抬高——两组数字各有偏差，
   结论只取两侧一致的：**天花板 ~75 QPS、瓶颈是 CPU**。
2. **detail 压的是空会话**（5 条消息都没有），比真实会话轻，是乐观下限。
3. **20 并发以下的远程 QPS 受客户端节奏影响**；服务器本机轮 2 并发就到 75.8 QPS，
   说明 27ms 的单请求耗时才是服务端真实水平。
4. 服务器本机轮**不含 nginx**（直压 127.0.0.1:8000），nginx/TLS 那层没测。
5. GIL / MySQL / 序列化哪个吃掉更多 CPU，没拆——只能说"CPU 是瓶颈"，
   再往下是 profile 的活。

## 五、LLM 轮（qwen3.8-flash，发布 6409702 后跑的）

探路 3 次全过（无兜底、无降级，中位 1.88s），随后 `1:190,2:90,4:60,8:60` 阶梯：

| 指标 | 值 |
|---|---|
| chat 请求 / 失败 | 404 / **0**（含 `E_FALLBACK`、`E_DEGRADED` 计数，均为 0） |
| 中位 / 均值 | 2.1s / 2.37s |
| P95 / P99 / 最大 | 4.0s / 4.7s / 5.35s |
| 吞吐 | 1 并发 0.8 QPS → 8 并发 6.0 QPS，**近线性，8 并发未饱和** |

结论：LLM 链路在 8 并发内延迟平稳（模型单请求 ~2s 是主导项），吞吐随并发线性涨，
失败为零——**没有静默兜底混进成功样本**（这正是 `E_FALLBACK` 判定要防的）。

token 消耗：404 × ≈186 ≈ **7.5 万 tokens**（qwen3.8-flash 剩余额度的约 9%）。
`llm.html` 是本轮报告；注意这轮数字含"等待模型"的时间，**不能当服务端能力报**。
