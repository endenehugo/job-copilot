# 2026-10-26 压测现状总结（供决策）

## 一句话

memory 模式已经优化到头（P95 7656 → 4328ms，慢请求消失），**剩下的 99% 是等模型返回**；
但 RAG（8.4s）和 Agent（22.6s）这两个更重的场景**从来没有被拆开看过**，容量也从来没测过。

## 二、这批数字里哪些可信，哪些不可信

必须说清楚，否则会被误导：

**可信（结构性变化）**

- `compress` 占比 37% → 8% → 0%，`answer` 62% → 91% → 99%。这是拆出来的，不是估的。
- 第 8 次请求 4.5s → 1.8s。同一位置、同一触发条件，三轮都复现。
- 后台压缩实耗 927/835ms（线上 `COMPRESS` 日志），比同步的 4475ms 快 5 倍。

**不可信（轮间不可直接比）**

- **P95 的轮间差异有相当部分是上游模型漂移，不是改动效果。** `answer` 的 P95 在三轮里
  2929 → 3550 → 4217ms 一路走高，`max` 从 3717 → 5200ms，而主模型三轮都是同一个
  `qwen3.8-flash`、配置也没动。
- 也就是说 p3 的 P95 4328 里，`answer` 贡献了 4217。如果 p3 还带着同步压缩，P95 会更差，
  但**不能把 7656 → 4328 的降幅全部记在优化头上**。
- 单轮只有 20 个样本，分位数随时会被一两个抖动带偏。

## 四、没测过的部分（决定下一步的关键）

| 盲区 | 现状 | 影响 |
|---|---|---|
| **RAG 场景** | 只有端到端 6.7-9.3s（5 轮，无 trace） | 不知道检索、重排、校验各占多少，优化无从下手 |
| **Agent 场景** | 只有端到端 21.9-23.0s（3 轮，无 trace） | 不知道工具轮与模型轮的比例，这是最慢的场景 |
| **容量上限** | 完全未知 | 只知道"30 RPS 封顶下 20/30/40 用户无差异"，测的是脚本限速不是服务器 |
| **流式 TTFT** | 从未采集 | 真实用户走 `/chat/stream`，压测全是非流式；数据与用户体验有系统性偏差 |
| **回答质量** | 未评估 | 压缩策略（更早压、清单式摘要）改了三轮，没做过人工抽查 |

## 五、下一步的四个选项

### A. 拆 RAG / Agent（推荐先做）

- 做法：`run_ai_stage.ps1 -Stage 3 -Mode rag|agent -Trace`，工具链现成，两轮约 10 分钟。
- 收益：RAG 的 8.4s 和 Agent 的 22.6s 立刻能拆到 retrieve / rerank / answer / verify /
  tool / agent.round。这两个是产品主场景，比 memory 重要。
- 成本：几轮模型调用 + 一次采样，风险极低。
- 预期能回答：RAG 是不是重排慢？Agent 的 20 秒里有几轮是工具调用？校验占多少？

### B. 测容量

- 做法：放开 `--max-rps`、加并发用户，压到 CPU/内存出现拐点。
- 收益：唯一能回答"能扛多少人"的方式。
- 成本/风险：会真的把机器压满，演示站可能卡；必须挑低峰时段并盯着，且需要人工中止条件。
- 建议：等 A 做完、知道瓶颈在哪之后再压，否则只知道"扛不住"不知道"为什么扛不住"。

### C. 采流式 TTFT

- 做法：压测脚本支持 SSE，解析首字节/首 delta 的时间。
- 收益：唯一能反映真实用户体验的数字。现在所有数据都是非流式，用户看到的却是打字机效果。
- 成本：要改 `ai_common.py` 的请求与解析，工作量中等。

### D. 换主模型

- 做法：`qwen3.8-flash` 换成更快的档，或对简单问题走小模型。
- 收益：`answer` 占 99%，这是唯一还能大幅动延迟的地方。
- 成本/风险：回答质量是产品核心，必须做质量评估，不是纯技术决定。而且现在模型抖动本身
  就有 1.3-5.2s 的跨度，换模型的收益可能被抖动吃掉。

## 六、我的建议

**先 A，再 C，B 放最后，D 要单独评估。**

理由：A 几乎零成本且信息量最大；C 补的是"数据与真实体验脱节"这个系统性偏差；
B 会影响线上演示站，应该在知道瓶颈之后再压，否则压完也只有"扛不住"三个字；
D 是产品决策，不该由压测数据单方面驱动。
