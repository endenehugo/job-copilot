# 2026-10-26 分段计时与服务器资源：memory 阶段慢在哪

## 目的

之前 13 轮压测只能看到端到端延迟，无法回答两件事：

1. memory 阶段慢请求固定出现在"每个用户第 7~10 次请求"，怀疑与历史压缩（`_MAX_HISTORY_MESSAGES=12` 触发的额外小模型调用）有关，但没有证据；
2. RAG 8.4s / Agent 22.6s 分不清检索、重排、模型、工具、校验各占多少。

## 结论

**慢的全部是历史压缩，不是回答变慢，也不是服务器。**

- 第 1-7 次：`compress=0`，每次 1 次模型调用，端到端 2.0-3.0s。
- 第 8-10 次：`compress` 2.6-6.5s，每次 2 次模型调用（多出来的那次全在 `compress` 里），端到端 4.6-8.4s。
- **answer 阶段没有变慢**。前 7 次的 answer 在 2147-2658ms，第 8 次 2565ms（持平），第 9、10 次降到 2109/1493ms——历史被压成摘要后，回答的输入上下文变短了。

触发点在第 8 次而不是第 7 次：第 7 次请求前累计 12 条消息，`len(history) <= 12` 不压缩；第 8 次前 14 条，开始压。

| | 压缩调用 | 回答调用（对照） |
|---|---|---|
| 次数 | 6 | 20 |
| 耗时均值 | **4475 ms** | 2243 ms |
| 输入 token | 144-305 | 110-623 |
| 输出 token | **142-383** | 56-162 |

**压缩比回答慢一倍，输出长 2-4 倍**，而且用的是同一个模型——配置里的 `llm_small_model` 也是 `qwen3.8-flash`，这个"小模型"档位在选 flash 时不起作用。

## 优化建议（按风险从低到高）

> 1、2 已在同日实施并复测，见文末「优化实施与复测」；3、4 未做。

1. **压缩一次压到更低水位**（12 → 6~8 条）。现在每轮都刚好压 2 条，下一轮又来 2 条，于是第 8 次之后每次都触发。改低水位能让触发频率降到每 3~4 轮一次。代价：更早丢失原始细节，只剩摘要。
2. **限制压缩输出长度**（`max_tokens` 400 → 150 左右）并明确"只保留事实清单，不要行文"。实测输出 142-383 token，对 12 条消息的摘要明显超长，而这部分完全在关键路径上。代价：摘要密度下降，可能漏掉细节。
3. **压缩换更小的模型**。前提是先让 `llm_small_model` 真的比主模型便宜/快；现在两者相同，改了等于没改。
4. **压缩异步化**（先返回回答、后台压缩）。收益最大，但要在同一会话上并发写摘要与水位，需要加锁并处理"压缩完成前的新消息"，风险最高，不建议先动。

建议先做 1+2：都不改交互时序，改动小，且数据直接支持。

## 限制

- **这轮不回答"最多能扛多少"**。1 RPS / 2 用户、CPU 3%，压力远未到服务器极限；要测容量得放开 `max-rps` 并加大并发。
- 样本 20 次、单轮，分位数参考价值有限，结论主要建立在"第 1-7 vs 第 8-10 的对照组"上，这一对比足够强（compress 从 0 跳到 2.6-6.5s，answer 不变）。
- `Server-Timing` 只做在非流式 `/conversation/chat`；流式请求的分段只进 PERF 日志（`ttft_ms` / `done_ms`），本轮未采。
- 观测本身不是零开销：每请求一行 JSON 日志进 journal。从与历史轮次的 P50/P95 对比看影响在噪声内，但没有做严格的 A/B。

## 顺带修掉的问题

上线后第一次请求就暴露：**一次模型调用被记成两次**（两条 `llm.call`，token 数一模一样，`n=2`、`llm 合计 6726ms` 超过 `total 4338ms`）。

原因是 `streaming=True` 的客户端在 `invoke()` 时，`ChatOpenAI._generate` 内部会走 `self._stream`，两层各记一条。已用 ContextVar 标记"正在 `_generate` 计时范围内"修掉（`b69984b`），直接 `stream()` 调用仍记一条，并加了两个回归用例。

## 优化实施与复测

### 改动（`f35804a`）

1. **触发阈值与目标水位分开**：`_MAX_HISTORY_MESSAGES=12`（触发）/ `_COMPRESS_TARGET_MESSAGES=8`（保留）。旧逻辑只有一个阈值兼作目标，每次只压掉溢出的 2 条，下一轮又溢出，于是第 8 次之后每轮都触发。两个值都进 settings。
2. **摘要收紧**：prompt 从"300 字以内的行文"改成"最多 5 条、每条 30 字的事实清单"，加 `max_tokens=240` 兜底与 320 字截断，并**关掉思考**（`enable_thinking=False`）。

另外修了一个上下文错位隐患：压缩条数向下取偶。消息是成对的 user/assistant，压奇数条会让水位停在 user 上，下一轮 recent 从 assistant 开始。

### 复测（同参数，`config_id=daef876c6e51`）

| 指标 | 优化前（`7615ef420f1e`） | 优化后（`daef876c6e51`） | 变化 |
|---|---|---|---|
| P50 | 2655 ms | **2134 ms** | −20% |
| P95 | 7656 ms | **4523 ms** | **−41%** |
| max | 8411 ms | **4887 ms** | −42% |
| compress 阶段 share | 37% | **8%** | −29pp |
| 压缩触发次数（20 次请求） | 6 次（第 8/9/10 次 × 2 用户） | **2 次**（只有第 8 次） | −67% |
| 压缩调用均值 | 4475 ms | **1940 ms** | −57% |

逐请求：第 8 次仍会压（这是累积到阈值必然要付的一次），但第 9、10 次已经回到 `compress=0`、1 次模型调用、1.3-3.6s。

服务器侧无变化：CPU 均值 3.6%（前 3.0%）、load1 0.17、可用内存 530MB、swap 0，无预警——优化没把开销挪到机器上。

### 诚实的归因

- **P95 降 41% 主要来自触发频率**（6 次 → 2 次），不是压缩本身变快。20 次请求里只有 2 次慢，P95 就落不到那两次上。
- 压缩调用从 4475ms 降到 1940ms，其中相当一部分是**关掉思考**的功劳：本地单独测 prompt 改动，3 轮对照输出 113 vs 133 字、耗时 2810 vs 3044ms，都在噪声内。所以"收紧 prompt"这一项本身收益有限，别按"压缩快一倍"理解。
- 关思考不是可选项：开着思考时思考 token 也计入 `max_tokens`，第一次实测 240 的额度被吃满、**正文返回空串**。

### 现在的瓶颈

`answer` 占 91%（均值 2308ms），基本就是一次模型调用的时间，`db` 只有 1%。要继续降只能动模型档位、缩短输入或流式返回首字，压缩这条路已经到头了。

### 剩余风险

- 压缩更早发生（第 8 次压到 8 条，原来第 8 次只压到 12 条）意味着更早依赖摘要、原始对话保留更少。本轮没做回答质量评估——摘要清单的信息量比原来的行文摘要更依赖模型是否选对了要点，这需要人工抽查几轮真实对话。
- 复测仍是单轮 20 样本、1 RPS，只证明"慢请求消失了"，不证明容量上限。

## 第二轮优化：后台压缩 + 小模型换档

### 3 的选型：先做基准，再决定改不改

原建议写的是"换更小的模型"，但查下来 `llm_small_model` 本来就是 `qwen3.8-flash`（清单里最便宜的一档）——
压缩慢不是因为没选小模型，而是压测时 `-Model qwen3.8-flash` 让主模型和压缩模型撞在一起了。
所以这一项改成"实测有没有更快的档"，同一段 14 条历史 × 3 轮：

| 模型 | P50 | 相对基线 | 输出字数 | 条目 | 空输出 | 结论 |
|---|---|---|---|---|---|---|
| qwen3.8-flash（原基线） | 2248 ms | 1.00x | 99 | 4.3 | 0 | |
| **qwen3.7-flash** | **1028 ms** | **0.46x** | 127 | 5 | 0 | **选用** |
| qwen3.8-omni-flash | 1455 ms | 0.65x | 99 | 4 | 0 | |
| deepseek-v4.1-flash | 4984 ms | 2.22x | 0 | 0 | **3/3** | **淘汰：`enable_thinking=False` 下正文恒为空** |
| qwen-plus | 1962 ms | 0.87x | 118 | 4.3 | 0 | |

交替跑 8 轮复核：qwen3.8-flash P50 1589ms vs qwen3.7-flash 1075ms，**1.48x**。

价格按阿里云百炼官方价目（≤32K 档，元/百万 token）：qwen3.7-flash 输入 0.2 / 输出 0.8，
qwen3.8-flash 0.8 / 2.7——**快 1.5 倍还便宜 3~4 倍，是纯优化，不是拿钱换时间**。

结构化输出冒烟（各 5 轮）：重排 JSON 5/5 可解析、P50 982→495ms；校验判断 5/5。

`llm_small_model` 默认值改为 `qwen3.7-flash`，影响压缩、事实校验、检索重排三处。

### 4 的实现：压缩转后台队列

压缩只服务**下一轮**，本轮的 prompt 在它之后才组装。所以等待没有任何当下收益：

- 新增 `context_compression_scheduler`：单线程执行器 + `pending` 去重，任务内部**重新读**摘要与历史再压。
- 写库复用 `update_context_summary` 已有的乐观锁（`until_id` 不前进就跳过），所以多 worker 部署失去内存去重也不会写坏水位，最坏重跑一次。
- `_prepare_chat` 在阈值（12）与硬上限（40）之间只排队，本轮直接用全量历史回答；超过 40 条说明用户连发、后台追不上，退回同步压缩。
- 后台任务跑在独立线程、请求 trace 可能已经结束，改打一行 `COMPRESS {json}` 到 `app.perf`。

### 结论：压缩这条路走完了

- **第 8 次请求从 4.5s 降到 1.8s（−60%）**，这是这一项的直接收益。
- 但整体 P95 只从 4523 降到 4328，因为 P95 的构成变了：p3 的最慢请求是 5291ms，其中 `answer` 占 5200ms——**纯模型抖动**，与本轮改动无关。
- `compress` 占比 0%、`answer` 占 99%。代价是每轮多带几条历史（answer 均值 2308 → 2395ms，+87ms），净收益仍是正的。
- 服务器侧 CPU 3.6%、swap 0、无预警，后台线程没有增加机器压力。

要继续压延迟，只能动模型档位、缩短输入或改流式首字——**观测手段已经把能拆的都拆干净了**。

### 新引入的风险

- 后台压缩失败只记 warning，用户无感：摘要会停在上一次，历史继续变长，直到 40 条硬上限退回同步。查 `journalctl -u job-copilot | grep COMPRESS` 里的 `error` 字段。
- `written:false` 说明水位没前进（乐观锁拒绝了），正常但值得留意频次。
- 单线程执行器意味着压缩是全局串行的：并发会话多时后排会等。20 用户以内的量级没问题，量级大了要改成多 worker + 去重。
