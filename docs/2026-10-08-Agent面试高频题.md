## 零、先给面试官的 30 秒概览

**Agent 组装链路**（`app/services/conversation_chat_service.py:68-154`）：

```
请求 → 模式归一(agent/rag/memory) → 历史取出 → 历史压缩 → 混合检索取上下文
     → 组装 Prompt(system + history + context + query) → LLM
     → [命中工具] 工具轮迭代(≤3) → 最终回答
     → 幻觉验证 + 引用标注 → 持久化 user/assistant 消息对 → 返回
```

**关键设计**：自实现 ReAct 式工具循环（不是 LangGraph 那套 AgentExecutor）、三种上下文模式、三级检索降级、工具错误以字符串回灌模型、SSE 流式 + 后置校验。

## 一、上下文治理（Context Governance）

### Q1：你的 Agent 每轮塞进 Prompt 的上下文由哪几部分组成？分别怎么控量？

**出处**：`conversation_chat_service.py:291-295`、`_prepare_chat:68-100`

**答案要点**：

四段式拼装，通过 `ChatPromptTemplate.from_messages` 组织：

| 段 | 来源 | 控量手段 |
|---|---|---|
| System | `build_agent_system_prompt()` + 动态技能清单 | 技能清单只放"名称+一句话"，几十 token |
| History | MySQL 全量消息 → 压缩 | 阈值 20 条，超出部分摘要化 |
| Context | 混合检索 Top-4 + 内置知识库 Top-2 | `limit=4`、验证时截 3000 字符 |
| Query | 用户输入 + 图片 markdown | 无 |

控量的三板斧：**条数截断（历史）、TopK（检索）、摘要化（压缩）**。

**追问**：为什么 System 提示里的动态内容要 `.replace("{", "{{")`？
> 因为返回值会被当作 `ChatPromptTemplate` 的模板字符串，技能描述里出现单个花括号会被当成模板变量，`invoke` 时抛 KeyNotFound，**导致所有请求全挂**。这类"一处出错全局瘫痪"的动态拼接必须转义。`conversation_chat_service.py:32`

### Q2：历史压缩的策略是什么？为什么按"条数"而不是按 token 触发？

**出处**：`context_compression_service.py:23-51`、`conversation_chat_service.py:57`

**答案要点**：

```python
_MAX_HISTORY_MESSAGES = 20        # 20 条 ≈ 10 个来回
if len(history) <= max_messages:  # 未超限，原样返回
    return history
# 超限：最早 (len-20) 条 → LLM 摘要（200 字内）→ 作为一条消息放回队首
return [summary_msg] + recent_messages
```

- **保留最近、压缩最远**：符合"近因性"，用户刚说的内容权重最高。
- **为什么按条数**：实现简单、可预测、零依赖（不需要 tiktoken/分词器），对中小预估 Token 足够。

**加分反思（一定要说）**：按条数是**工程妥协**，真实风险是——用户上传一份 2000 字 JD 后再聊几轮，20 条就可能撑爆上下文窗口。更稳妥的做法是：**按累计 token 触发，且保留最近 N token**。中文场景可以用 `字符数 ≈ token 数 × 1.5` 粗估，或者按 `qwen` 的 tokenizer 精确算。

**追问**：摘要生成本身要调一次 LLM，失败怎么办？延迟怎么算？
> **降级路径**（`_summarize_messages:123-142`）：LLM 摘要成功 → 作为一条 `[上下文摘要]` 消息放回队首；失败 → `text[:300] + "……"`（暴力截断原文兜底，**宁可丢一部分上下文，也不能让整个请求失败**），并把摘要长度硬截断到 500 字符以内防止摘要超长。
>
> **延迟**：摘要调用是**串行挡在主链路上的**，会实打实加在首字延迟（TTFF）里。生产优化方向：异步后台预压缩 / 把摘要持久化到 DB，避免每轮从零重算。

### Q3：你说有三种模式（agent / rag / memory），它们到底差在哪？为什么这么切？

**出处**：`conversation_chat_service.py:70`、`81-89`、`117-127`

| 模式 | 是否检索文档 | 是否绑工具 | 典型场景 |
|---|---|---|---|
| `agent` | ✅ | ✅ `bind_tools` | 默认，要干活："帮我优化这段项目描述" |
| `rag` | ✅ | ❌ | 纯文档问答，不许乱调工具 |
| `memory` | ❌ 上下文置空 | ❌ | 纯多轮闲聊/追问，靠模型自身能力 |

**为什么要做成可切换**：成本和可控性。
- 每次请求都 `bind_tools` 会让 prompt 里多出全部工具的 schema，**非工具场景是白白浪费 token 且诱导模型误调**；
- `memory` 模式直接跳过 FAISS 检索，省掉 embedding + 检索层的几十到几百毫秒。
- 归一逻辑是**白名单而非黑名单**：`mode if mode in {...} else "agent"`，非法输入静默降级而不是报错。

**追问**：非法 mode 为什么不报错返回 400？
> 这是"**输入容错 vs 契约严格**"的取舍。用户侧参数是软约束，静默降级保证可用性；但涉及安全/数据完整性的输入（如图片文件名）就必须硬校验、直接报错——见 Q27。

### Q4：检索上下文的三级降级是怎么设计的？为什么不让"没命中"直接返回空？

**出处**：`document_index_service.py:109-137`

```
会话私有索引（混合检索）  →  公共全局索引（相似度阈值 0.4）  →  内置知识库 Top-2（常驻）
     一级                        二级                          三级
```

- 一级没结果才走二级，用 `if not docs` 逐级触发。
- 三级（内置知识库）是**无条件追加**，无论前面有没有命中。理由是产品诉求：这是个求职助手，用户问"Flask 请求生命周期"这类问题时，即使没上传文档，也希望能答出来（`docstring: 92-94`）。

**设计点**：把"降级"做成**责任链**，每级只关心自己有没有产出，上层不感知具体实现。

**追问**：内置知识库无条件追加会不会污染上下文、反而诱导幻觉？
> 会。所以这里必须配**后置校验**（见 Q8）：`add_citations` 会给这些片段标来源 `[1] [2]`，并且 `verification` 会把"无支撑断言"标出来。上下文注入和幻觉治理必须成对设计——**只加不管等于放大幻觉**。

### Q5：混合检索（向量 + BM25）具体怎么做？为什么要混合？合并后怎么排序？

**出处**：`document_index_service.py:168-246`

```python
vector_docs = 向量检索(limit*2)   # 语义相似
bm25_docs   = BM25 检索(limit*2)  # 关键词匹配
merged      = 去重(page_content)  # 保留首次出现顺序
ranked      = Rerank(query, merged, top_k=limit)
```

**为什么混合**：
- **向量检索**吃语义，但对**精确关键词**（函数名、报错码、专有名词）不敏感；
- **BM25** 吃精确词频，但对**同义改写**（"怎么优化简历" vs "简历怎么写更好"）无力；
- 两者互补，这是 RAG 的经典共识。

**三个实现细节（说得出细节才像做过）**：
1. `k` 取 `limit*2` 先扩召回再精排，避免召回面太窄。
2. BM25 的 `score == 0` 直接丢弃（`bm25_retrieve:235`）——得分为 0 说明 query 分词和文集**一个词都没撞上**，这种结果只有噪声。
3. BM25 索引用 `pickle` 反序列化 FAISS 的 `index.pkl` 构建，并**缓存在实例字典**里；且兼容了三种序列化形态（`_extract_store_documents:296-310`）——因为 langchain 版本升级改过 `(docstore, index_to_docstore_id)` 元组结构。

### Q6：向量检索为什么要有"阈值 + 兜底"两级？直接用 similarity 不行吗？

**出处**：`document_index_service.py:191-206`

```python
# 一级：阈值检索 score_threshold=0.35
docs = threshold_retriever.get_relevant_documents(query)
if docs: return docs
# 二级：不带阈值的相似度兜底
return fallback_retriever.get_relevant_documents(query)
```

**为什么**：纯向量余弦相似度对**短 query / 概述性问题**（"这个文件讲了什么"）天然偏低，卡阈值会全部落空 → 用户体验是"上传了文档却说不知道"。所以 **阈值用于保证质量，兜底用于保证可用**。

**这个设计的哲学**：凡是"硬门槛"，都必须配一条"不让它彻底失败"的出路。这条原则贯穿整个项目（后面工具调用、检索、rerank 全是同一个思路）。

### Q7：Rerank 两层降级（BGE → LLM），为什么这么排？

**出处**：`document_index_service.py:324-407`

```python
if len(docs) <= top_k: return docs        # 结果不够，无需排序
try:  reranked = _rerank_with_bge(...)    # 一级：专用交叉编码器
except: pass
return _rerank_with_llm(...)              # 二级：LLM 打分 0-10
```

- **BGE Reranker 优先**：交叉编码器（cross-encoder）准确率高于向量召回，且本地推理成本低、无网络抖动。
- **LLM 兜底**：`FlagEmbedding` 是可选依赖，生产环境（README 提到"生产依赖已最小化，无 torch/OpenMP 冲突"）很可能没装 → `ImportError` 直接跳过。
- **LLM 打分也有自己的兜底**：解析失败/越界 → 默认 **5.0 分**（中立值），既不置顶也不沉底（`_score_batch_with_llm:404-406`）。
- 还有一个容易忽略的**性能优化**：`_bge_reranker` 懒加载后**缓存在实例上**（`docstring:344-346`）——旧版每检索一次重装一遍数百 MB 的模型，是当时延迟的主要浪费点。**这是很适合拿来当"性能优化故事"的素材。**

**追问**：LLM 逐篇打 0-10 分有什么问题？
> 虽然函数名叫 batch，`_score_batch_with_llm` 里实际是 **for 循环逐个 invoke**，串行调用 N 次 LLM，延迟随候选数线性增长。优化：改成一次 prompt 输出全部分数，或换 pointwise 排序模型。

### Q8：怎么治理幻觉？你们的验证是前置还是后置？

**出处**：`context_verification_service.py:25-57`、`154-166`、`conversation_chat_service.py:131-143`

**答案**：**后置验证（Post-hoc Attribution）**——回答生成完，再单独用一次 LLM 判定每条断言是否有上下文支撑。

产出结构：
```python
{"supported_claims": [...], "unsupported_claims": [...],
 "verification_detail": "...", "hallucination_risk": "low|medium|high"}
```

**为什么后置而不是前置**：流式回答必须边生成边发token，无法先验证再发；而且"先生成后校验"能同时产出引用标注。

**风险分级规则（这段代码很有讲点，`_assess_risk:59-87`）**：

```python
ratio = 无支撑断言 / 总断言
ratio >= 50%  → high
ratio >= 25%  → medium
否则          → low

# 升级规则：无支撑断言里含"具体量化数据"（百分比/小数/倍数/两位以上数字）
if 含量化数据:
    low → medium
    量化断言 >= 2 条 或 ratio >= 10% → high
```

**为什么还要额外设计这条升级规则？** ——这是最出彩的地方：
> "编造一个模糊的说法"和"编造 `简历匹配度 87%` 这种具体数字"危害完全不同。**用户天然更相信带数字的回答**，所以含具体量化数据的无支撑断言，单位权重必须更高。

整个模块还做了**静默容错**：验证服务挂了不影响主链路，`except Exception` → 打 warning 跳过（`conversation_chat_service.py:141-143`）。**校验是增强不是必须**。

### Q9：引用标注 `[1][2]` 是怎么加的？有什么隐患？

**出处**：`context_verification_service.py:102-152`、`224-246`

流程：
1. 从每个 source doc 抽关键短语（≥8 字符的句子/子句，去重，按长度倒排，最多 50 条）；
2. 用 **`phrase in answer` 子串匹配**判断这条片段是否被回答引用；
3. 命中则在**断言文本尾部**插入 `[n]`；
4. 逆序插入（`insertions.sort(reverse=True)`）避免前面插入后位置偏移。

**面试官一定会追问的隐患（主动说出来）**：
- **子串匹配极脆弱**：模型复述时改几个字就匹配不上 → 漏标；长短语顺序里有短的重复片段 → 误标。正解是 Embedding 相似度匹配或让模型自己在生成时吐 `[1]` 标记。
- **插入位置粗暴**：只是追加在片段尾部，可能出现 `[1][1]` 重复。
- 但工程上它有一个巨大优点：**零额外 LLM 成本、纯本地字符串操作、不会失败**。这是典型的"用 60 分方案换 0 成本和 100% 可用性"。

### Q10：上下文 Chunk Size 怎么定？chunk 700 / overlap 120 的依据？

**出处**：`core/config.py:53-54`、`document_index_service.py:426-436`

```python
conversation_index_chunk_size: int = 700
conversation_index_chunk_overlap: int = 120
separators = ["\n\n", "\n", "。", "；", "，", " "]  # RecursiveCharacterTextSplitter
```

**答案**：
- **为什么按中文场景调**：英语常见 500/1000，中文同等语义的字符数更少，700 字符约等于 400~500 token，适合 `text-embedding-v3` 的输入窗口且不容易超出最佳语义粒度。
- **为什么 separators 按"\n\n → 句号 → 分号 → 逗号"降序**：`RecursiveCharacterTextSplitter` 是**递归**的——先用大分隔符切，切不动才用更小的，最大程度保留段落/句子的自然边界。**保持语义完整是分块的第一原则**。
- **overlap 120 ≈ 17%**：跨块边缘的信息不至于丢失。代价是索引体积和召回冗余。
- 参数**外置到 config**（pydantic-settings）而不是硬编码 → 可以不动代码按文档的语料特征调。

**追问**：重叠会导致同一段话被召回两次吗？
> 会。所以 `_hybrid_retrieve` 里按 `page_content` 做了**去重**（`seen_contents`）。设计上前后呼应。

### Q11：索引重建为什么要用 tmp 目录 + rename，而不是直接删旧建新？

**出处**：`document_index_service.py:34-83`（注释本身就把原因写出来了）

```python
# 先把新索引写到临时目录，构建成功后再替换旧目录。
# 旧版先删后建：embedding API 一失败旧索引就没了，会话检索瘫痪到重新上传。
tmp_dir = index_dir + ".tmp"
shutil.rmtree(tmp_dir)
FAISS.from_texts(...).save_local(tmp_dir)
shutil.rmtree(index_dir)
os.rename(tmp_dir, index_dir)      # 原子替换
```

**面试官想听到的词**：**原子替换 / 破坏性操作延后**。
- 关键不在于 `rename` 本身是否原子（同一分区下 `os.rename` 确实是原子操作），而在于**把唯一的破坏性操作（删旧索引）推迟到新索引 100% 构建成功之后**。
- 失败路径也清理了临时目录（`except: rmtree(tmp_dir); raise`），不留垃圾。
- 这是从线上排障得来的经验：embedding API 抖动时，先删后建会让用户文档"全没了"。**非常适合作为简历上的一个"我踩过的坑 + 我怎么修"的故事点。**

## 二、历史对话管理

### Q12：多轮历史存放在哪？为什么这么存？

**出处**：`conversation_store_service.py:101-142`

**MySQL `conversation_message` 表**，每条消息一行（`role` / `content` / `created_at`），会话维度用 `conversation_id` 关联。

写入是**单事务原子写两条**：

```python
with session.begin():
    conversation = get(...)              # 不存在 → raise ValueError
    create(role="user", ...)
    create(role="assistant", ...)
    update_summary(title=..., message_count=+2, last_message_preview=..., updated_at=...)
```

**为什么 user/assistant 成对写入**：一次问答要么都存在要么都不存在。写一半的话，下一轮回放历史会出现"只有问没有答"，模型会以为上条回答丢失而重复回答。

**追问**：`message_count` 为什么 +2 而不是 COUNT(*)？
> 冗余字段，为了让会话列表页不必 JOIN 消息表做聚合。`last_message_preview` 同理（截断 500 字符）。这是典型的**读多写少场景下的反规范化**。

---

### Q13：为什么存进历史的是"原始回答"，返回给前端的是"带引用的回答"？

**出处**：`conversation_chat_service.py:145-152`、`230-243`

```python
append_message_pair(conversation_id, user_content, answer, mode)   # 存 answer
return {"answer": cited_answer, "original_answer": answer, ...}    # 返回 cited_answer
```

**答案**：**引用标记是渲染层的装饰，不是事实内容。**

如果 `[1][2]` 和"📖 参考来源"留在历史里：
1. 下一轮回放时，模型会把角标当成**自己的发言风格**，开始凭空编造 `[3][4]`；
2. 这些 markdown 噪音会污染历史摘要，也会干扰 `add_citations` 的关键短语子串匹配（它靠 `phrase in answer` 匹配，满屏 `[1]` 会显著降低精度）；
3. 多轮之后回答里会重复叠加 `--` 分隔线和来源列表，**历史越长越臃肿**，token 成本被装饰性内容吃掉。

**原则**：**持久化的必须是干净的语义内容，装饰性信息只在出口层渲染。** 同理适用于 UI 上的高亮、按钮、流式状态。

### Q14：历史是怎么回放成 LangChain 消息的？多模态历史和文本历史有什么不一样？

**出处**：`_build_history:428-438`、`_build_multimodal_history:398-426`

**文本路径**（`agent` / `rag` / `memory`）：
```python
content = _strip_image_markdown(item["content"])    # 先剥掉图片 markdown
role == "user"      → HumanMessage(content)
role == "assistant" → AIMessage(content)
```

**多模态路径**：要把历史里 `![image](/conversation/image/...)` 还原成真实的图片入参：
```python
image_urls = _extract_image_urls(content)
parts = [{"image": 本地路径} for url in image_urls]   # 解析失败 → continue 跳过
if clean_text: parts.append({"type": "text", "text": clean_text})
messages.append(HumanMessage(content=parts))
```

**这个设计的巧妙点**：**图片以 markdown 占位符存库，回放时再还原成文件**。数据库不存二进制、也不需要单独的"附件表"，存的是**可解析的语义标记**。

**代价 / 坑**：
- 图片文件被删了怎么办？→ `try/except: continue` **静默跳过**（`413-414`），历史里那条消息变成纯文本。**容错优先：一张图丢了不该让整个多轮问答崩掉。**
- 接口文档里明确写了（一个重要约束）：`docstring:5-7` —— **图片 URL 格式 `/conversation/image/<cid>/<filename>` 已经被硬校验且写进历史消息的 markdown 占位符里，不能改格式、不能加 `/api/v1` 前缀**，否则所有历史消息里的图片全部失效。**这是"契约固化在持久化数据里"的典型教训，很适合当设计评审的案例。**

### Q15：历史里的 system 消息会怎样？（送分陷阱题）

**出处**：`_build_history:428-438` vs `context_compression_service.py:46-49`

**这是本项目里最值得拿来讲的一道题。**

```python
# compress_history 产出：
summary_msg = {"role": "system", "content": "[上下文摘要] 以下是较早对话的摘要：\n..."}
return [summary_msg] + recent_messages

# _build_history 处理：
role = item.get("role")
if role == "user":      → HumanMessage
elif role == "assistant": → AIMessage
# system 分支：不存在 → 被静默丢弃
```

**结论**：压缩出来的摘要，**花了 LLM 调用的钱生成，却从来没有进入过模型的上下文**。`role == "system"` 这条分支没有人处理，摘要直接被 `continue`-like 丢弃了。

**面试时怎么答（非常重要，这是区分度最高的题）**：
> "这是我们代码里一个真实的缺陷，我已经定位到 `\`_build_history\`` 只映射了 user/assistant 两个角色。修复有两个层次：
> 1. **短期**：在 `_build_history` 里补 `role == "system" → SystemMessage` 分支；
> 2. **更合理**：不要把摘要塞进 MessagesPlaceholder('history')。System 消息在 API 语义里应该放在序列开头（或作为 human 消息的一部分注入），混在多轮中间会破坏大部分模型的 turn-taking 假设（很多模型要求 system 只能一条且在最前）。所以正确做法是把摘要**拼进 context 段**，而不是伪装成一条历史消息。"

**还能接着追问**：那就算修好了，还有什么问题？
> 摘要**从未被持久化**。每轮的 `get_conversation_messages` 都是从 MySQL 拉全量原始消息，超过 20 条就**重新摘要一次** → 每次白白多一次 LLM 调用，且摘要质量随对话增长越来越不稳定。正确做法是**增量摘要**：把旧的摘要 key->value 存库（或 Redis），下次只把"新超出部分 + 旧摘要"合并成新摘要。

### Q16：会话删除怎么保证数据不残留？

**出处**：`conversation_store_service.py:240-278`、`api/conversations.py:123-143`

**两段式清理**：
1. **DB 层**：单事务级联删除 6 张表的关联数据（面试科目标 `InterviewMessage` → `InterviewSession` → `JobAnalysis` / `ResumeVersion` / `ConversationMessage` / `ConversationDocument` → `Conversation`）。注意删 InterviewMessage 前**先查出 session_id 列表**，用 `in_()` 批量删。
2. **文件/索引层**：事务**提交成功后**，才 `shutil.rmtree` 四个目录（`uploads`、`parsed_docs`、`faiss_index_uploads`、`uploads/images`）+ 清 BM25 缓存。

**为什么分开**：文件操作**不参与数据库事务**（没法 rollback）。顺序必须是**先 DB 后文件**——反过来会导致"文件删了但 DB 还有记录"，产生永久悬空引用。反过来,即使文件清理失败，DB 记录消失后也只是"垃圾文件"，不会崩溃。**这是典型的最终一致性取舍。**

### Q17：history 的长度、内容与 token 成本怎么权衡？（开放 + 落地）

| 层次 | 手段 | 代价 |

| 回放层 | 剥离图片 markdown；图片失效跳过 | 少量信息损失 |

## 三、工具调用与兜底机制

> 本项目的 Agent 工具循环是**手写 ReAct**，不是 LangChain AgentExecutor。面试官如果问"为什么不用 LangGraph/AgentExecutor"，答：垂直场景工具只有 8 个、循环逻辑简单、手写可以完全掌控消息序列和流式行为，也更省依赖。

### Q18：工具循环的主循环长什么样？最多几轮？

**出处**：`_invoke_agent:302-324`、`_run_tool_rounds:245-265`

```python
for _ in range(3):                       # ← 硬上限 3 轮
    response = agent_llm.invoke(messages)
    messages.append(response)
    tool_calls = response.tool_calls or []
    if not tool_calls:
        return response.content          # 模型不再要工具 → 出结果
    for tool_call in tool_calls:

```

**消息序列**（符合 OpenAI/DashScope tool-calling 协议）：
```
SystemMessage → [History...] → HumanMessage(含 context+query)
  → AIMessage(tool_calls=[...])
  → ToolMessage(id=xxx, content=...)     # 每个 tool_call 都必须有对应回执
  → AIMessage(最终答案)
```

### Q19（核心题）：工具调用失败时，你们怎么处理？为什么是"字符串回灌"而不是抛异常？

**出处**：`_invoke_agent:312-323`

```python
tool = self.tool_dic.get(tool_call.get("name"))
if tool is None:
    content = f"工具不存在：{tool_call.get('name')}"
else:
    try:
        content = tool.invoke(tool_call.get("args"))
    except Exception as exc:
        logger.warning("工具 %s 执行异常: %s", name, exc)
        content = f"工具执行失败：{exc}"
messages.append(ToolMessage(tool_call_id=tool_call.get("id"), content=content))
```

**这是本项目工具兜底的核心设计，必须讲透。**

**为什么绝对不能把异常抛出去**：
1. **协议完整性**：模型发起了 N 个 `tool_call`，就必须回 N 条 `ToolMessage`。少一条（或 tool_call_id 不匹配），DashScope / OpenAI 会直接返回 **400 Invalid parameter**，整轮请求失败。
2. **给了模型"自我修复"的机会**：错误文本本身是信息。模型看到"工具执行失败：缺少参数 b"，下一轮可能就会重试并补齐参数。**把错误变成对话的一部分，而不是终止符。**
3. **兜底文案要结构化**：`"工具不存在：xxx"`、`"工具执行失败：{exc}"` —— 让模型能识别这是错误类型，而不是把异常栈当成了答案内容。

**三层兜底，任何一层失败都不能让外层崩**：
- 工具名查不到 → 字符串
- 工具抛异常 → 字符串
- 外层还有 `answer = answer or "抱歉，我暂时无法生成回答。"`（`:129`、`:216`）保证永远不会返回空。

**可以补充的工程点**：
- `_run_tool_rounds` 里 `except Exception` 后 `continue`，**不会因为一个工具挂了影响同批其他工具**。
- 但是：工具调用是**串行执行**的，没有并发；也没有重试/退避。这两个是明确的演进点。

### Q20：工具内部自身有哪些兜底？（拿 web_search 举例）

**出处**：`tools/web_search.py:20-80`

这段代码是"工具内部防御"的标准范例，逐层列出：

| 层 | 校验 | 返回 |
|---|---|---|
| 参数层 | `query` 缺失/空白 | `"错误：缺少搜索关键词 query。"` |
| 配置层 | `METASO_API_KEY` 未配 | `"错误：未配置 METASO_API_KEY，无法执行网页搜索。"` |
| 网络层 | `requests.RequestException` | `"搜索时发生网络错误: {exc}"` |
| 解析层 | `ValueError`（JSON 解析失败） | `"搜索结果解析失败: {exc}"` |
| 业务层 | HTTP `raise_for_status` | 走网络层分支 |
| 业务层 | `errCode not in (None,0,"0")` | `"搜索接口返回错误: errCode=..., errMsg=..."` |
| 空结果 | `records` 为空 | `"未检索到相关网页结果。"` |
| 字段层 | title/snippet/url/date | 每个字段都有默认值兜底 |

另外两个工程细节：
- `timeout=30`：**必须设**，否则一个挂死的请求能把整个 Agent 拖住。
- `records[:5]`：搜索本身请求了 `size=10`，**只取前 5 条**塞回上下文——控制工具返回的 token 量。

**统一约定**：所有工具都遵守 **"错误以字符串返回，不抛异常"**（`tools/skill.py:4` 的 docstring 明写）。这个约定非常重要——**它把错误处理从 Agent 循环下沉到了工具实现**，循环层只需要统一 try/except。

### Q21：模型的 tool_call 参数如果不符合 schema 怎么办？

**出处**：`tools/mutipy.py`、`tools/job_tools.py`

两层防护：
1. **Pydantic `args_schema`**：`Field(description=...)` 的描述会作为 JSON Schema 发给模型，让模型知道该传什么。**description 是给模型看的最重要的提示词，不是注释。**
2. **工具内部运行时校验**：`MultiplyTool` 里显式排除了布尔——
```python
if isinstance(a, bool) or isinstance(b, bool) or not isinstance(a, (int,float)) ...:
    return f"错误：参数 a 和 b 必须是数字，收到 a={a!r}, b={b!r}。"
```
> **面试点**：`bool` 是 `int` 的子类，`isinstance(True, int) == True`。如果不显式排除，`multiply(True, 3)` 会返回 `3` 而不是报错。这种类型系统的坑在真实项目里很常见。
> 注意 `!r` 的用法：把收到的**实际值**回传给模型，模型才能知道错在哪 —— **错误信息必须带上下文**。

**为什么不让框架来校验**：LangChain 的 schema 校验失败会抛 `ToolException`。我们选择在 `_run` 里做软校验并返回字符串，是因为它更符合本项目"**永不中断主链路**"的整体契约（见 Q19）。

### Q22：`load_skill` 这个工具是怎么设计的？为什么叫"渐进式加载"？

**出处**：`tools/skill.py`、`utils/skill_loader.py:76-82`、`conversation_chat_service.py:30-32`

**这是本项目最有讲头的 Agent 设计之一，一定要主动讲。**

问题背景：内置 9 个求职技能（job-match / make-resume / interview / project-guide ……），每个技能的完整指南（SKILL.md）动辄几千 token。**如果全部常驻 System 提示，每次对话都要付 9 份指南的钱，还会互相干扰模型的注意力。**

解决思路：**把"工具清单"和"工具说明书"分开。**

```
System 提示里只放：              实际要用时：
  - job-match：岗位匹配分析    →    load_skill("job-match")  →  拿到完整 SOP
  - interview：模拟面试深挖         （一次性进 ToolMessage）
  ...9 条，每条几十 token           （只有命中的那一份进上下文）
```

模型通过 tool description 判断"这个任务需要哪份指南"，再按需调用 `load_skill` 加载。**这就是 Anthropic Agent Skills / Claude Code 的 progressive disclosure 模式。**

两个设计细节：
- `skill_name='list'` 是**逃生舱**：模型不确定有哪些技能时可以先列目录（大模型常会猜错名字，必须有恢复路径）。
- 技能不存在时返回 `"错误：技能 X 不存在。可用技能：a、b、c"`（`:42-44`）——**把可用项回传让模型自我纠正**，跟 Q21 的 `!r` 是同一个套路。

### Q23：工具循环达到轮次上限会怎样？这个上限合理吗？

**出处**：`_invoke_agent:302-324`、`_run_tool_rounds:245-265`

```python
for _ in range(3): ...
return ""      # 3 轮后模型还在要工具 → 返回空串
```

外层：`answer = answer or "抱歉，我暂时无法生成回答。"`

**评价（要两面说）**：
- ✅ **必须有上限**：防止模型陷入工具循环无限烧钱（"死循环 Agent"是生产事故常见原因）。
- ⚠️ **超限就返回空串、让用户只看到一句兜底文案，其实是"力气用错了方向"**：更好的做法是**在最后一轮给模型一个明确指令**（如"已达工具调用上限，请基于已有信息直接作答"），让它输出一个降级答案，而不是空手而归。这叫 **forced answer / graceful degradation**。
- ⚠️ 3 轮是拍脑袋定的，应该按业务复杂度分层配置。

**顺带可以提的另一个缺陷**：每轮是 `agent_llm.invoke(messages)`，**整个 messages 列表每轮都全量重发**（ToolMessage 会不断累加），3 轮下来 token 消耗是累加的。这在工具返回很大（比如 web_search 返回 5 条网页摘要）时会明显膨胀。优化方向：对过长的 ToolMessage 做截断/摘要。

### Q24：流式模式下工具调用怎么适配？和裸管道有什么差异？

**出处**：`conversation_chat_service.py:190-210`

```python
for chunk in agent_llm.stream(prompt_messages):   # 第一轮 token 级流式
    merged = chunk if merged is None else merged + chunk
    if chunk.content: yield delta
if merged.tool_calls:                             # 中途发现命中工具
    messages.append(AIMessage(content=merged.content or "", tool_calls=...))
    final_answer = _run_tool_rounds(messages)     # 工具轮：非流式
    answer = final_answer or streamed_text
    if final_answer: yield delta(final_answer)    # 整段补发
```

**核心思路**：**"先看吐不吐 tools，再决定怎么发"**。用 `merged + chunk`（LangChain 的消息加法）累积出完整的 AIMessage，检查它的 `tool_calls`。

**为什么工具轮要放弃流式**：工具轮中间的消息是一次性产出的，没法流式；而且工具调用本来就有明显等待了，用户此刻关注的是"正在查资料"的状态，而不是打字机。

**两个必须提的坑**（很加分）：
1. **流式中途异常**：`except Exception: logger.warning(...)` 后**继续往下走**，用已累积的 `streamed_text` 兜底（`:199-200`）——**宁可给用户半截答案，也不要让 SSE 连接挂了前端干等。**
2. **重复文本风险**：如果模型**既吐了正文又开始调工具**（例如边解释边调用），`streamed_text` 已经发给了前端，随后 `final_answer` 又整段补发一次 → 前端出现重复内容。修法：命中工具时给前端发一个 `reset/truncate` 事件，或者前端识别到工具阶段后丢弃已渲染的正文。**这是真实存在的边界情况，能说出来说明真的调过。**

### Q25：bind_tools 之后怎么保证工具不会越权执行？

**出处**：`conversation_chat_service.py:281-283`、`_invoke_agent:313`

```python
tools = [MultiplyTool(), WebSearchTool(), ... SkillTool()]
self.tool_dic = {tool.name: tool for tool in tools}
self.agent_llm = self.qa_llm.bind_tools(tools)
```

执行时：**只从 `tool_dic` 里按名字查**。所以：
- 模型只能调用 bind 过的工具 —— **白名单执行，模型给出的工具名不构成任何权限**；
- 即使模型幻觉出一个 `"exec_shell"` 这样的工具名，`tool_dic.get()` 返回 `None` → 走 `工具不存在` 分支。

**原则**：**永远不要 `getattr`/`eval` 模型给的名字**，只能做白名单字典查找。

**另外一点值得主动提**：`MultiplyTool` 这种演示用工具在生产 Agent 里应该删掉。残留的 demo 工具会**分散模型的工具选择注意力**（工具越多越容易选错），而且 8 个工具已经接近 qwen-plus 稳定调度的上限附近了。

## 四、流式输出与 SSE

### Q26：SSE 事件序列怎么设计的？为什么引用来源和校验结果放最后？

**出处**：`conversation_chat_service.py:156-243`、`api/conversations.py:85-120`

```
meta → delta* → sources → verification → done
```

**为什么 sources / verification 必须在 delta 之后**：
- **它们依赖完整回答**。幻觉校验和引用标注都是"事后归因"，需要看到完整的答案文本才能做（对比 Q9 的子串匹配）。
- 所以前端是"先看到字在打字，最后一刻补上引用角标和来源面板"。

**done 事件携带完整数据**（`answer` 带引用 / `original_answer` / `conversation`），前端拿它做最终态对齐。

**传输层两个要点**：
```python
media_type="text/event-stream",
headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"}
```
- `X-Accel-Buffering: no`：**告诉 Nginx 禁用对这次响应的缓冲**。否则 Nginx 会攒够缓冲区才下发，打字机效果变成"卡 3 秒然后全文蹦出来"。README 里也写了 Nginx 侧必须 `proxy_buffering off`。
- 这本身就是一道题：*"你们流式上线后前端说没效果，怎么排查？"* → 答案就是**代理层缓冲**，从里到外一层一层查：应用层是否真的逐 chunk yield → uvicorn → Nginx → 浏览器的 EventSource。

**异常处理**：generator 里 `except ValueError → error 事件`，`except Exception → 500 + error 事件`（`api/conversations.py:106-110`）。**SSE 一旦 started 就无法改 HTTP 状态码**，只能靠自定义事件把错误推给前端。

## 五、Agent 安全与稳定性

### Q27：模型/用户给的路径参数怎么防止目录穿越？

**出处**：`conversation_chat_service.py:351-361`、`utils/skill_loader.py:60-72`、`api/conversations.py:183-197`

三个位置用了三种手段，**能说出"针对不同威胁级别选不同手段"才是懂行**：

| 位置 | 手段 | 理由 |
|---|---|---|
| 图片 URL 解析 | **白名单正则** `^[A-Za-z0-9_.-]+$` + 段数硬校验（必须 4 段） | 模型/历史里可能注入 `../`，从源头禁止任何分隔符 |
| 技能名加载 | **白名单正则** `^[a-z0-9][a-z0-9-]*$` | 模型给的参数，**绝对禁止出现 `..` 和 `/`** |
| 静态文件服务 | `os.path.realpath` + `startswith(image_dir + os.sep)` | 这一层拿的是外部 URL 路径，用**规范化后的前缀约束**做最后一道防线 |

**为什么第一和第二用正则而不是 realpath**：因为它们是**拼接前的输入校验**，从源头拒绝非法字符；而 `realpath + startswith` 用于事后兜底。两者结合是纵深防御。

**顺带**：API 层还对图片做了 **扩展名白名单 + content-type 校验 + 大小限制（20MB）**（`api/conversations.py:157-163`）。

### Q28：工具的错误信息会不会把 API Key 泄漏进上下文？

**出处**：`tools/web_search.py`、`utils/api_key_checker.py:223-231`

- `WebSearchTool` 自身不会打印 key，但它的异常文本 `exc` 会进 ToolMessage → 进 messages。**这是一个真实风险**：`requests` 的异常有时会带上完整 URL（含 query 参数）。
- 好在项目对密钥做了**脱敏工具**：`_mask_key` 只回显前 4 位和总长度，**不回显尾部**。
  ```python
  # 旧实现 key[:4] + "****" + key[-4:]，尾部 4 位可被拿来验证离线爆破的猜测 → 已废弃
  return f"{key[:4]}****（共 {len(key)} 位）"
  ```
  **面试点非常漂亮**：为什么尾部也不能回显？因为**拿到脱敏串的人可以用它校验自己猜的 Key 是否正确**（离线爆破的验证码）。安全评审里这类"信息泄漏只要一点点就够"的细节最能体现深度。

**一句话原则**：**工具的错误文案必须脱敏后才回灌给模型**，因为 ToolMessage 会被持久化/进日志/可能被前端展示。

### Q29：进程内有状态的缓存会不会影响水平扩展？

**出处**：`core/deps.py:38-59`、`document_index_service.py:23`、`README.md:56`

项目里有三类**进程内缓存**：
- `_bm25_indexes` dict（BM25 索引）
- `public_db`（公共 FAISS 实例）
- `lru_cache` 的服务单例 + `_bge_reranker` / `_compressor_llm` / `_verifier_llm` 等类级缓存

README 里明确写了：**"后端保持 `workers=1`（进程内缓存语义）"**。

**面试官会问**：这样不是不能横向扩展了吗？
> 诚实回答：是的，**目前这是一个已知的技术债**。多 worker 会导致每个进程各持一份 BM25 索引缓存，文档更新后不同请求命中不同进程、结果不一致；也让内存占用翻倍。
> 演进方案（三层，任选一层先做）：
> 1. 把 BM25 索引和 FAISS 实例挪到独立的**检索服务**，HTTP/gRPC 调用；
> 2. 缓存挪到 Redis，**用版本号 key 做失效**；
> 3. 退一步：至少把 BM25 索引**持久化到磁盘**（现在是每次重启重建），并加一个 `updated_at` 版本号校验。
>
> **加分**：能主动指出 `__init__` 里 `_compressor_llm = None` 是**类属性**（没写类型注解，所以不是 dataclass 字段），意味着它被**所有实例共享**——这算巧合性的单例，但也说明依赖要在 DI 层管理，不该散落在类里。

## 六、代码里真实存在的坑（高分题）

> 这一节是"面试官追问还能挖出什么"的答案，也是简历上"重构与优化"故事线的素材。**主动指出自己项目的不足，比只会背优点有说服力得多。**

### Q30：同一个功能两份实现，你怎么处理？（重复代码治理）

**出处**：`_invoke_agent:302-324` vs `_run_tool_rounds:245-265`

两段代码逻辑几乎一样，只有三处差别：
| | `_invoke_agent` | `_run_tool_rounds` |
|---|---|---|
| 无工具时 | `break` 并返回 `response.content` | `return response.content` |
| 超限返回 | 已有内容 / `""` | `""` |
| 注释 | 详细 | 简略 |

**重构方案**：抽成 `_execute_tool_loop(messages) -> tuple[str, AIMessage]`，两个入口分别适配返回值即可；顺带把硬编码的 `3` 提成配置项（`max_tool_rounds`）。

**为什么要强调这个**：写出这段代码的人都觉得"就几行，复制一下快"，结果后面两边改的不一致（比如给一边加了重试没给另一边加），这才是真正的维护成本。

### Q31：项目里有没有"写了但没人调用"的代码？

**出处**：`context_compression_service.py:53-119`

**有**：`build_compressed_context()` 和 `extract_key_information()` 从未被生产代码引用过（只在压缩服务内部自调用）。

`extract_key_information` 的设计本身不错——把历史压成五类结构化卡片：
```
【涉及文档】/【关键事实】/【用户需求目标】/【已确认信息】/【待确认待补充】
```
这其实比单纯的一句摘要更适合做长期记忆（结构化、可增量更新、可单独检索）。

**面试怎么答**：要么接上去做成一个 `memory` 卡片（每 N 轮刷新一次并持久化），要么删掉。**死代码的危害是它会给人"这个功能已经有了"的错觉。**

### Q32：多模态历史的 content 结构不一致，会有什么后果？

**出处**：`conversation_chat_service.py:409-416`

```python
{"image": 本地路径}                      # 图片 part
{"type": "text", "text": clean_text}     # 有图的那条历史的文本 part
{"text": self.multimodal_system_prompt}  # SystemMessage / 当前轮的用户 part
```

同一个 List 里混用了**带 `type` 和 不带 `type`** 两种 dict 结构。DashScope 的多模态接口对不同形态的兼容行为不一致，在某些版本上会报 content 格式错误。

**答法**：统一成 `{"type": "text"/"image", "text"/"image": ...}` 的显式形态；并在构造多模态消息时抽一个工厂函数而不是到处手写 dict。**异构外部 API 的参数构造必须收敛到一处，否则版本一升级全线报错。**

### Q33：如果 ToolMessage 的 content 不是字符串会怎样？

**出处**：`tools/mutipy.py:28`

`MultiplyTool._run` 返回的是 `a * b`（**int / float**），而其他工具都返回字符串。LangChain 的 `tool.invoke` 原样返回 → `ToolMessage(content=42)`。

后果取决于 ChatTongyi 的序列化实现，轻则被 `str()` 兜住，重则报 content 类型非法。

**答法**：统一约定 **工具返回值必须是 `str`**，可以在基类或 Agent 循环里加一层 `content = str(content)` 的规范化（和"错误返回字符串"同属一类契约）。

### Q34：校验服务的 JSON 解析为什么写了 5 级降级？（顺带体现"和 LLM 打交道的经验"）

**出处**：`core/json_utils.py:65-103`

```python
1. json.loads(原文)
2. markdown 代码块提取 → loads → repair_json 后再 loads
3. 括号计数（带字符串/转义状态机）提取最外层对象 → loads → repair 后 loads
4. 原文 repair_json 后再 loads
5. 正则兜底提取最外层非嵌套对象
全部失败 → raise ValueError(error_message)
```

**必答的两个点**：
- **`repair_json` 修的是什么**：LLM 生成 JSON 数组时常见的毛病——**用 `}` 去闭合 `[`**（`"} → ]"`）。这是一条从实际日志里总结出来的错误模式，**能说出具体错误形态才是真踩过坑**。
- **`extract_json_by_braces` 为什么手写转义状态机**：因为直接按 `{`/`}` 计数会把 `"a\": {"` 这类字符串里的括号误判成嵌套层级。这个 `escape / in_string` 的状态机是必需的正确性保证。
- **组织方式**：这段原来是四处重复实现，收拢成公共模块后策略顺序保持不变 —— **重构的第一原则是保行为不变**。

## 七、开放设计题

### Q35：如果要给这个 Agent 加长期记忆，你会怎么做？

**分层作答**：

| 层 | 内容 | 载体 | 触发 |
|---|---|---|---|
| L0 短期（一轮内） | 工具轮消息 | 内存 messages | — |
| L1 会话历史 | 全量 user/assistant | MySQL | 每轮 |
| L2 会话摘要 | 压缩后的对话摘要 | MySQL / Redis（当前未持久化） | 超 20 条时**增量**更新 |
| L3 事实卡片 | 关键实体/已确认/待补充 | JSON 字段 + 向量索引（项目里已有 `extract_key_information` 的雏形） | 每 N 轮或事件触发 |
| L4 用户画像 | 跨会话的目标岗位、技能栈 | 独立表 + Embedding 检索 | 会话结束时异步写 |

**落地要点**：写入要**异步/后置**（不挡主链路），读取要**按需注入**（不是全塞），并且**每一层都要有 TTL 或淘汰策略**。最后补一句：本项目目前只做到了 L1，L2 存在缺陷（Q15），L3 有代码未接线（Q31）。

### Q36：如果工具调用要用异步/并行，现在这套要改什么？

1. **工具本身改 async**：现在 `_run` 里是同步 `requests.post` / 同步 DashScope SDK，在 FastAPI 的线程池里跑。改 `httpx.AsyncClient` + `asyncio.gather`。
2. **同一轮的多个 tool_call 并行**：现在 `for tool_call in tool_calls` 串行。改成 `await asyncio.gather(*[_ainvoke(tc) for tc in tool_calls])`。
3. **保序**：并行产出后要**按原始 `tool_call` 顺序**构造 ToolMessage 列表 —— 部分 Chat API 对 ToolMessage 顺序敏感。
4. **超时与熔断**：给每个工具单独 timeout，全局加并发上限；失败仍走"字符串回灌"。
5. **幂等**：写类工具（如 `word_document_tool`）并行重试会产生重复文件，需要幂等键。

### Q37：如果让你评估这套 Agent 的成本和延迟，你会看哪些指标？

| 维度 | 指标 | 本项目现状（可优化点） |
|---|---|---|
| 延迟 | TTFF、总时长 | 历史摘要 + 混合检索 + Rerank + 后置校验，**串行 4 次额外 LLM/模型调用** |
| Token | 每轮 prompt/completion | 工具轮全量重发 messages；历史摘要每轮从零重算（未持久化）；技能清单每次启动扫盘 |

| 质量 | 幻觉风险等级分布、工具命中率、工具失败率 | 已有 `verification`，但**没有埋点/可观测** |
| 稳定 | 工具异常类型分布、超时率 | 只有 `logger.warning`，**没有 metrics** |

**一针见血的结论**：**现在最大的问题是"不可观测"**——所有兜底都只打日志。生产 Agent 至少要补齐：trace_id 贯穿（LLM 调用/工具/检索各 span）、工具失败率看板、幻觉风险分布。

> 顺带可提：`list_skills()` 每次 `build_agent_system_prompt()` 都重新扫描磁盘、读取 9 个 SKILL.md 的 frontmatter（`conversation_chat_service.py:32`）。好在系统提示走的是 `_ensure_initialized` 的幂等懒加载（`:267-268`），**只在首次请求时扫一次盘**，之后一直复用；副作用是技能文件**热更新必须重启进程** —— 这是"进程内缓存 + workers=1"的又一个连带成本。

## 八、速查表：一句话知识点

> 面试前的最后一遍过码，每个都能在 15 秒内展开。

**上下文治理**
1. 阈值压缩 20 条（≈10 轮），超出部分 LLM 摘要，保留最近 N 条完整。
2. 摘要失败 → 原文截断 300 字符（`+ "……"`）。
3. 检索三级降级：会话私有索引 → 公共索引 → 内置知识库 Top-2（常驻）。
4. 混合检索 = FAISS 向量 + BM25 关键词，按 `page_content` 去重合并。
5. 向量检索两级：阈值 0.35 → 纯相似度兜底（短 query 向量分天然偏低）。
6. Rerank 两级：BGE 交叉编码器（懒加载缓存）→ LLM 0-10 打分（失败默认 5.0）。
7. BM25 `score == 0` 直接丢弃；索引从 FAISS 的 `index.pkl` 反序列化构建并缓存。
8. 幻觉治理：后置 LLM 归因 + 子串匹配引用 + 三级风险分（**含量化数字要升级**）。
9. chunk 700/overlap 120，递归分隔符（保语义边界），参数外置到 config。
10. 索引重建：tmp 目录构建成功后 `os.rename` 原子替换（防止 API 抖动毁掉旧索引）。

**历史对话**
11. MySQL 成对写入（单事务），冗余 `message_count(+2)` 与 `last_message_preview(500)` 避免 JOIN 聚合。
12. **存原始回答，返回带引用回答** —— 引用角标是渲染层装饰，不能污染历史。
13. 图片以 markdown 占位符存库，回放时还原成本地文件；文件失效则跳过该图（`try/except: continue`）。
14. **图片 URL 格式已固化在历史数据里，不可变更**（契约硬编码的经典教训）。
15. **已知缺陷**：摘要用 `role="system"` 产出，但 `_build_history` 只映射 user/assistant → 摘要被静默丢弃；且摘要从不持久化，每轮重复生成。
16. 删除会话：DB 单事务级联 6 张表 → 事务提交成功后才清文件与向量索引（文件操作无法回滚，故顺序不可逆）。

**工具调用兜底**
17. 手写 ReAct，工具轮硬上限 **3 轮**，超限返回空串 → 外层兜底文案。
18. **错误以字符串回灌模型**（`工具不存在：` / `工具执行失败：{exc}`），保证每个 `tool_call` 都有对应 `ToolMessage`，否则 DashScope 直接 400。
19. 工具名走 `tool_dic` 白名单查找，**永不 eval/getattr 模型给的名字**。
20. 工具内的多层防御：参数 → 配置 → 网络 → 解析 → 业务错误码 → 空结果 → 字段默认值。
21. `requests` 必设 `timeout=30`；搜索请求 10 条只回灌 5 条（控 token）。
22. `bool` 是 `int` 子类，`isinstance(True, int)` 为真 → 数值工具必须显式排除 bool。
23. 错误信息要带收到的实际值（`!r`），让模型能自我纠正。
24. `load_skill` 渐进式加载：System 只放技能清单，命中才加载完整 SOP；`skill_name='list'` 是猜错名字时的逃生舱。
25. 工具轮 `messages` 全量重发，token 随轮数累加。

**流式与 SSE**
26. 事件序列 `meta → delta* → sources → verification → done`；sources/verification 后置是因为它们依赖完整回答。
27. `X-Accel-Buffering: no` + Nginx `proxy_buffering off`（打字机效果的头号杀手是代理层缓冲）。
28. 命中工具时工具轮非流式，最终答案整段补发 —— **若模型既吐正文又调工具，会出现重复文本**。
29. SSE 一旦开始无法改 HTTP 状态码，错误只能走自定义 `error` 事件。

**安全与工程**
30. 路径防御三手段：白名单正则（URL 4 段硬校验 / 技能名 `^[a-z0-9-]+$`）+ `realpath + startswith`（静态文件兜底）+ 上传三件套（扩展名 / content-type / 20MB）。
31. 密钥脱敏只回显前 4 位 + 总长度，**不回显尾部**（尾部可被用作离线爆破的验证位）。
32. 有状态进程内缓存（BM25 / FAISS / lru_cache 单例）→ 必须 `workers=1`，是**已知横向扩展债务**。
33. JSON 解析五级降级管道（由业务服务里四处重复实现收拢而来）；`repair_json` 修的是 **"用 `}` 闭合 `[`"** 这一具体 LLM 毛病。
34. 工具类缓存写成类属性（无类型注解）→ 实际被所有实例共享，依赖管理应收敛到 DI 层。
