## 怎么读这张表

- **TTFT ≠ 总耗时**：对话的"开始有字"和"回答完"是两件事，用户等的是前者。
- **agent 与 rag 是两条链路**：agent 先做工具决策（可能连续调用多轮工具），rag 直接检索后作答。
  agent 一旦工具轮次跑满却没有产出最终回答，就会退化成兜底文案（表里标"降级"），这时耗时虽长但没有结果。
- **面试是链式的**：一轮作答里包含评价生成 + 下一题生成两次模型调用，所以单轮比一次问答慢；
  整场面试的总时长约等于「开始 + 轮数 × 单轮」，这个数值直接决定用户会不会中途放弃。
- **纯检索/导出都在亚秒级**：说明慢的部分全在模型调用，不在数据库或文件 IO。

## 分阶段：对话的时间都花在哪

把 SSE 事件按到达时间打点（curl 逐行打时间戳，rag 模式，带一份简历文档）：

| 事件 | 到达时间 | 含义 |
| --- | --- | --- |
| `meta` | 2.1s | 历史压缩 + 上下文检索完成 |
| `delta`（整段答案） | 3.0s | 答案已生成，用户开始读到 |
| `sources` | 4.2s | 检索来源下发 |
| `done` | 4.7s | 回答落库、会话详情组装完成 |
| `verification` | **50.0s** | 断言校验（另一次小模型调用） |

也就是说：**用户 3 秒就看到答案，连接却挂了 50 秒**。多跑几轮，`verification` 在 22s～99s 之间波动，
它是整轮耗时里最大、最不稳定的一块。

无文档的对照会话同样跑了校验（34.8s），说明 `context` 不只来自会话文档，知识库检索也参与，
所以"没有简历就不会校验"这个假设不成立。

单独调用校验用的模型（`_llm_verify`，qwen3.8-flash）两次：**18.3s / 29.8s**；
响应元信息里 `reasoning_tokens` 为 36～53，说明它是思考型模型，即使只要求输出一个 JSON 也会先想很久。

## 本次测试发现的问题

### 1. 流式对话必崩：ContextVar 跨 context 复位（已修）

- 症状：每个流式回答在 `done` 之后抛 `ValueError: Token was created in a different Context`，
  前端把它拼到回答末尾；`verification` 事件永远收不到（引用标注、风险徽章全部失效）。
- 根因：starlette 的 `iterate_in_threadpool` 是**每次 `__next__` 一个新 context 拷贝**，
  第一次迭代里 `set()` 的 token 到后续迭代 `reset()` 必然报错。
- 修法：`app/api/conversations.py` 改成 async 生成器，用 `contextvars.copy_context()` +
  `run_in_threadpool(ctx.run, ...)` 把整条流固定在同一个 context 里驱动。
- 验证：修复前 `meta/delta/tool_status/done` 缺 `verification`，且末尾带 error；
  修复后五类事件齐全、无 error。

### 2. agent 模式会「跑满工具轮次却不回答」（已修）

同一个问题（"用三句话说明这个项目最难的技术点"）实测触发了：

```
load_skill → jd_parser_tool → project_rewrite_tool → resume_score_tool
→ html_document_tool → html_document_tool   （6 轮用尽）
```

结果 `degraded: true`，`warnings: ["工具调用已达轮次上限，未能生成最终回答"]`，
用户最终只看到"抱歉，我暂时无法生成回答。"，白等 33～45 秒。

修法（`conversation_chat_service.py`）：轮次用尽后再发一次**不带工具**的收尾调用
（`_finalize_without_tools`），把已执行工具的结果（每条截断到 1200 字）连同用户问题一起交给模型作答。
流式与非流式两条路径共用；收尾调用本身失败时退回原来的降级行为。

实测（同一个会耗尽轮次的问题）：
- 修复前：`done.answer` = "抱歉，我暂时无法生成回答。"
- 修复后：244 字的实质回答，`warnings` 变为「工具调用已达轮次上限，回答由已执行工具的结果汇总生成」，
  仍然保留降级标记（这是汇总答案，不是模型本来的最终回答）。
- 代价：多一次模型调用。整轮 66.8s 里包含 6 轮工具 + 收尾 + 校验，收尾本身约 5～8s。

风险：收尾答案基于工具结果，仍可能出现过度推断（实测有一次写出了简历里没有的
"消息队列或 Redis 缓存"），所以降级标记不能去掉——校验阶段的风险等级也照常生效。

### 3. 校验阶段吃掉 80% 的尾部时间（未修，待定方案）

单次校验 18～99s，且它在 `done` 之后才跑：用户不等待，但 SSE 连接一直挂着，
非流式端点则直接把这个时间算进响应（本次 112.4s，其中 100s 是校验）。

缩小方向的优先级：① 校验改用非思考模式；② 上下文从 3000 字降下来；③ 改成按需触发（点"查看来源"时才校验）。

## 一个环境层面的偶发故障

测试中出现过一次 `POST /document/upload` 500：

```
PermissionError: [WinError 5] 拒绝访问 ... faiss_index_uploads\conv_xxx.tmp -> faiss_index_uploads\conv_xxx
```

即 `document_index_service.py:61` 的 `os.rename` 在 Windows 上偶发失败（文件被占用），重试一次即成功。
生产在 Linux 容器里不会遇到，但本机演示时可能踩到，可加重试兜底。
