## 一、成果总览：修复前 vs 修复后

| 指标 | 修复前 | 修复后 |
|---|---|---|
| LLM 最坏等待 | **50 分钟**（ChatTongyi 无超时 + 默认重试 10 次） | **2 分钟**（统一 `request_timeout` + `max_retries=2`） |
| 流式首字节（TTFF） | 15~30s（历史摘要串行挡路） | **3.7s**（摘要从关键路径移除） |
| 验证结果到达 | done 之后还要再等 ~15s | 验证异步补发，done 提前 ~15s |
| Rerank 延迟 | 逐篇打分，随候选数线性增长 | **listwise 单次调用，提速 5.8×** |
| Agent 工具链进度 | 气泡静默干等几十秒 | `tool_status` 事件实时显示当前工具 |
| 工具链异常结束 | 返回空串/静默失败 | 降级答案 + `warnings` 信封可见 |
| LLM 缺字段 | 伪造 0 分落库、空评价 | 置 None + 明确「未评分」+ 告警 |
| 面试空题场景 | 前端白题卡死、状态卡在"进行中" | 自动转 summary 正常收尾 |
| 导出功能 | 后端 3 接口完整但**零入口** | 三个面板均有导出按钮 |
| 请求可取消 | ❌ | 前端「停止生成」（AbortController） |
| 会话快速切换 | 高亮与内容可能错位 | select 请求序号保护，过期响应丢弃 |
| 索引上传耗时 | 每次全量重 embedding | **增量追加**（按 document_id 去重，失败自动退回全量） |
| Key 无效 | 完全无感，聊天报错才知情 | 启动检测 + `/health` 附 `keys_ok` |
| 前端全局异常 | 静默消失 | errorHandler + unhandledrejection 兜底（10s 去重） |

**测试**：45 项 → **143 项**（新增 SSE 事件序、降级信封、面试规范化、索引增量等专项）。

## 三、诚实记录：实测否决项

优化不是加功能，**实测数据否决了两个原计划方案**：

1. **RRF 融合（原 T1 方案）→ 否决**。基准测试显示 BM25 分词按字切分污染严重，RRF 与 LLM 逐篇打分的排序重合率仅 **0.14~0.33**，不可用。改为 listwise（单次调用、重合率可用、5.8× 提速），per_doc 保留为降级路径，RRF 仅作最后兜底。
2. **A13/A14（数据库查询优化 / service 全量异步化）→ 否决**：A13 相关表仅 5 行数据，收益不成立；A14 实测同步 service 改 async 反而卡死事件循环，维持现状并在文档标注。
