# 自动简历生成模块（调用 make-resume skill）方案

- 日期：2026-10-18
- 目标：在 job-copilot 里增加"一键生成可编辑简历 HTML"的产品化模块，执行时自动使用内置 `make-resume` skill
- 状态：方案待拍板，未动代码

---

## 0. 先纠正三个前提

### 0.1 "自动调用 skill"已经存在，且是当前最差的那条路

对话链路里已经能跑：模型调 `load_skill("make-resume")` → 拿 SKILL.md → 自己分块写 HTML → 调 `html_document_tool` 落盘（`app/services/conversation_chat_service.py` 第 25/37 行就是这套引导，`app/tools/html_document.py` 负责分块写入与下载链接）。

所以本需求真正缺的不是"能不能调 skill"，而是**把一个自由发挥的对话过程变成确定、可复现、可二次编辑的模块**。如果新模块只是把 `load_skill` 再走一遍让模型写 HTML，等于给现有能力套个壳，不解决任何问题——版式每次不一样、A4 分页靠运气、改一个错别字要重新生成 20k token。

### 0.2 make-resume 的可执行部分是空的，别按它的流程实现

SKILL.md 要求：读 `assets/asu-resume/template.html`、用 `scripts/build-asu-resume.mjs` 内联 CSS/JS、调 `scripts/export-resume-pdf.mjs` 导 PDF、对照 18 套模板壳、跑 Playwright print QA。

事实上：

| SKILL.md 引用 | 本地 `backend/resources/skills/make-resume/` | GitHub `Hisn00w/ASu-skills` |
| --- | --- | --- |
| `assets/asu-resume/` | 不存在 | 是单文件 `assets/asu-resume-template.html`，没有目录 |
| `assets/templates-html/`（18 套） | 不存在 | README 提"18 个模板"，但仓库无此目录 |
| `assets/latex-resume/` | 不存在 | 未确认 |
| `scripts/build-asu-resume.mjs` | 不存在 | 不存在（`scripts/` 只有 sync/bridge 两个 mjs） |
| `scripts/export-resume-pdf.mjs` | 不存在 | 不存在（PDF 靠浏览器打印） |

还有一处自相矛盾：`references/default-resume-template.md` 第 3 行写"完整可复制的 HTML 骨架写在 SKILL.md 末尾"，而 SKILL.md 里并没有这段骨架，也没有它引用的"交付前 QA 自查清单"。

结论：**skill 的文档版本（v2）比仓库资产（v1）新**。照 SKILL.md 实现会一路撞墙，所以下面不实现它的流程，只取它的**规范文本**（输入清单、内容规则、视觉参数、`.pending` 占位约定），模板自己固化一份。

### 0.3 输入源和交付格式你还没定义

这三点直接决定表结构和接口，必须拍板（见第 6 节）。下面的方案按推荐默认值写：**输入 = 会话内已解析的简历 + 已有 JD 分析/项目改写结果；交付 = 可编辑 HTML + 浏览器打印 PDF，不做 docx 一键导出。**

## 1. 三条路对比

| | A. 模板渲染流水线（推荐） | B. 模型直出 HTML（现状做法产品化） | C. 服务端真跑 skill 脚本 |
| --- | --- | --- | --- |
| 实现量 | 1 模板 + 1 service + 1 API + 1 Vue 组件 | 几乎零（加个按钮） | 装 node 资产 + Playwright + 沙箱 |
| 版式稳定性 | 固定，A4 分页一次调好 | 每次不同，溢出/断页靠运气 | 取决于模板资产 |
| 输出 token | ~1.5k（结构化 JSON） | 15–25k（整份 HTML），截断风险实存 | — |
| 二次编辑 | 改 JSON 重渲染，不花钱 | 只能重新生成整份 | 同 B |
| 回归测试 | 同 JSON → 同 HTML，可快照 | 不可测 | 不可测 |
| 现在能不能做 | 能 | 能 | **不能**，资产与脚本都不存在 |

选 A。B 的灵活性只有"支持任意版式"时才值钱，本项目只需要一套默认模板，用不上。

## 2. 推荐方案 A：三段式流水线

```
会话上下文                        skill 规范                     产出
─────────────────────────       ─────────────────           ──────────────────
parsed_resume.txt   ┐            SKILL.md 白名单小节  ┐
job_analysis(27)    ├─ 抽取 ──►  references 内容规则  ├─► ResumeData(JSON)
project_rewrite(6)  ┘  LLM       视觉参数/占位约定   ┘        │
user 补填字段        (thinking=off)                              │
                                                               ▼
                                              Jinja2 渲染 asu_resume.html.j2
                                                               │
                                                               ▼
                                     事实一致性审计（LLM）→ warnings / pending 标记
                                                               │
                                                               ▼
                                     generated_docs/resume_<id>.html + 落库
```

### 2.1 阶段一：skill 规范注入（真调用，但不是整篇塞）

新增 `backend/app/services/resume_generation_service.py`，取规范用现有 `skill_loader`：

```python
guide = skill_loader.load_skill("make-resume")                       # SKILL.md 原文
ref   = skill_loader.load_reference("make-resume",
                                    "references/default-resume-template.md")
spec  = extract_sections(guide, ["输入清单", "缺失字段补问规则", "默认排版"])
spec += extract_sections(ref,   ["视觉参数", "内容规则", "页面结构"])
```

**关键判断：不能把 SKILL.md 全文塞进 prompt。** 它 3000+ 字里有大半在讲 `node scripts/...`、18 套模板矩阵、LaTeX 导言区，对服务端流水线是纯噪音，还会诱导模型输出"我将执行构建脚本"或反过来要用户提供 assets。按二级标题切片、只取白名单小节，既保住了"skill 一升级 prompt 自动跟着变"，又把噪音挡在外面。

白名单外的小节（模板与资源、工作流程、PDF 导出验收、LaTeX 输出）明确不用，理由写进代码注释，避免后人又整篇塞回去。

### 2.2 阶段二：结构化抽取

一次 LLM 调用，`build_chat_llm(enable_thinking=False)`（记忆里 2026-10-18 的结论：结构化判断关思考，15.8–19.7s → 3.67s）。输出固定 schema：

```json
{
  "profile":   {"name","phone","email","city","target_role","links":[]},
  "education": [{"school","degree","major","start","end","gpa","awards":[]}],
  "works":     [{"company","team","role","start","end","bullets":[{"text","basis","source_span"}]}],
  "projects":  [{"name","role","start","end","stack":[],"bullets":[{"text","basis","source_span"}]}],
  "skills":    {"language":[],"framework":[],"db":[],"tools":[],"cert":[]},
  "missing":   ["姓名","毕业时间"]
}
```

硬约束（写进 prompt，从 skill 的"缺失字段补问规则"改写）：

1. 公司、学校、职位、起止时间**只能来自素材原文**，取不到填 `null` 并进 `missing`，不许编。
2. 每个 bullet 必须给 `basis`（`resume` / `rewrite` / `user`）与 `source_span`（原文片段）。
3. 原文没有的数字、技术栈、职级**不得新增**。确需量化而无数据时，输出 `【待补：指标】` 文本。
4. 这条是对 2026-10-18 测试里两个 P0 的直接对症：`project_rewrite_service` 的"尽可能加入量化指标"把 90% 编成"78%→92%"、凭空加 Docling，是同一类失败模式。

### 2.3 阶段三：模板渲染 + 审计

- 模板：`backend/resources/resume_templates/asu_resume.html.j2`（单文件，含内联 CSS 与 `@page { size: A4; margin: 12mm }`）。视觉参数直接抄 `references/default-resume-template.md` 的"视觉参数"节：分区标题 `#2458B8` 13pt、公司条 `#F3F4F6` 圆角 6px、正文 9.5–10.5pt、`.item { page-break-inside: avoid }`、占位符 `<span class="pending">`。
- Jinja2 已随 FastAPI 环境可用（实测 3.1.6），但 **`requirements.txt` 里没有显式声明**，部署镜像可能缺——必须补一行 `jinja2==3.1.6`。
- 审计：第二次 LLM 调用（也可与抽取合并成一次，省 3s），逐条比对 `source_span` 是否真在原文里出现；不通过的打 `warnings`，HTML 对应文本包 `.pending`。

### 2.4 为什么模板化能顺带解决"可编辑"

用户改一个词不需要重新生成：`POST /resume/regenerate` 收改过的 `data_json`，纯渲染，0 次 LLM 调用，200ms 内返回。这是 A 相对 B 最实际的收益，也是"可编辑简历"这条产品主张的落地方式（skill 的原意是让人在 HTML 里改，但那样改完的结构回不到系统里，版本就断了）。

## 3. 接口与存储

新增 `backend/app/api/resume_generation.py`（挂 `/api/v1`）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/resume/generate/stream` | SSE，阶段事件 `skill@` → `extract@` → `render@` → `audit@` → `save@` → `done@`，对齐 `/job/analyze/stream` 现有风格 |
| POST | `/resume/regenerate` | 传 `generation_id` + 改后的 `data_json`，只渲染不调 LLM |
| GET | `/resume/generations` | 会话下生成历史（会话树子节点用） |
| GET | `/resume/generation/detail` | 取 `data_json` + `warnings` + `html_url` |

HTML 交付复用现成的 `/api/v1/conversation/file/<name>`（`app/api/conversations.py:223`），落盘到 `generated_docs/`，不新增静态目录、不加鉴权旁路。

新表（不复用 `resume_versions`，那张表是"上传简历打分"的版本线，字段对不上）：

```sql
resume_generations(
  id, generation_id VARCHAR(64) UNIQUE, conversation_id, document_id,
  data_json TEXT, warnings_json TEXT, missing_json TEXT,
  html_path VARCHAR(500), template VARCHAR(64), model VARCHAR(64),
  created_at, updated_at
)
```

放在 `app/repositories/resume_generation_repository.py`，与现有 repository 同构（`mapped_column` + 静态方法）。

## 4. 入口：两条路，一个 service

用户要的"自动调用"有两个入口，都必须落到同一个 service，否则两套逻辑迟早分叉：

1. **确定性入口**：前端点"生成简历" → `POST /resume/generate/stream` → service 内部直接 `skill_loader.load_skill`。这条路径不需要模型决定"要不要用 skill"，是真正的自动。
2. **对话入口**：用户在聊天里说"帮我生成简历" → 新增 agent 工具 `generate_resume`（照 `app/tools/job_tools.py` 写一个 BaseTool），它内部调同一 service 并返回 `artifact` 链接。同时把 `conversation_chat_service` 现有引导改一句：**需要交付简历文件时优先调 `generate_resume`，不要用 `html_document_tool` 手写整份 HTML**。

  现在的引导（第 37 行）恰恰是"必须按指南先把模板骨架写全再分块写入"，也就是把 B 方案写死在系统提示里了。不改这句，新模块上线后对话路径仍然走老路。

前端（4 个文件）：

- `store/resumeGen.js`：`generate / regenerate / load / detail`
- `components/resume/ResumeGenerateView.vue`：左 iframe 预览（`src` 直指 file 下载路由）+ 右栏"缺失字段 / 风险项"清单 + 操作（重新生成、改字段、打印为 PDF）
- `conversation.js` 的 `activeType` 增加 `'resume'`；`Workspace.vue` 加一个 `v-else-if` 分支（第 140–142 行同款）
- 打印走 `iframe.contentWindow.print()`，零依赖；PDF 由浏览器"另存为 PDF"生成，纸张吃模板的 `@page`

## 5. 失败与降级

| 情况 | 处理 |
| --- | --- |
| 会话里没有简历文档 | 返回 `needs_input` + `missing` 字段清单，前端弹最多 3 个必填项（对齐 skill 的"最多补问 3 个"） |
| 抽取 JSON 解析失败 | 修复式重试 1 次（带错误信息回灌），仍失败返回明确错误，**不返回半成品 HTML** |
| 审计发现无来源数字 | 不阻断生成，标 `.pending` + `warnings`，前端顶部黄条"有 N 处需人工核对" |
| 渲染异常 | 记日志返回 500 文案，不把 Jinja 栈信息给前端 |
| 模型额度耗尽 | 走 `llm_factory` 现有降级链，`warnings` 里写明实际使用的模型 |

### 9.3 实测暴露并已修的问题

1. **文档状态过滤写错**：只认 `parsed`，而上传成功后的真实状态是 `indexed` → 「当前会话还没有解析成功的简历」。已改为 `parsed` / `indexed` 都收。
2. **Jinja 渲染期字段污染 data**：`name_html` / `html_text` 被写回返回给前端的 `data`。已改为全量重建对象，并加单测。
3. **`group.items` 撞 Jinja 的 `dict.items`**：技能组整段渲染失败。镜像字段改名 `tags`，注释写明原因。
4. **教育条 `degree` 丢失**：条件写成 `if edu.major`。已修，并补 `period()` 宏处理缺 start/end 时的孤立破折号。
5. **头部信息重复**："现居深圳 · 深圳"。已加包含去重。
6. **技能区标签被裁切**：flex + 固定宽度下长分类名溢出，已改 grid。
7. **缺失项被 JD 缺口污染**：模型把"是否掌握 C++""是否具备 Linux 后台经验"塞进 `missing`。prompt 加硬约束 + `_JD_NOISE_PATTERN` 兜底过滤。
8. **学校名填成身份行**：模型把"本科 · 2022 年 6 月毕业"填进 `school`。加 `_DEGREE_WORD_PATTERN` 兜底。
9. **首屏密度不足**：初版只填 72% 版面，调字号/行距/间距后约 85%。

### 9.4 已知偏差（未修，P2 处理）

1. **项目技术栈仍会轻度补全**：prompt 第 5 条要求"只收该项目原文提到的技术"，但仍出现过把工作经历里的 Go/FastAPI 塞进项目 stack。审计只能在"整份简历都找不到"时报警，抓不到这种跨段落搬运。彻底解法是抽取时按项目段落做归属，或对 stack 做逐项回查（会带来较多误报，需先定阈值）。
2. **姓名是推断值**：素材里只有 `zhangsan@example.com`，没有"张三"，模型从邮箱推断后填进 `name`，同时把"姓名"列进 `missing`。行为上是自洽的（既给值又提示核对），但不符合"不得推测"的严格口径。是否改成强制占位待定。
3. **无 PDF 一键下载**：按拍板走浏览器打印，`iframe.contentWindow.print()` 已验证可用。
4. **不落库**：刷新即丢，P2 才接 `resume_generations` 表与 `/resume/regenerate`。
