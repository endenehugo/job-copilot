# 面试故事：四个排障复盘的完整讲法

> 配套《2026-10-07-项目变更总结.md》第七节。每个故事按统一框架组织：
> **钩子（一句话）→ 30 秒版 → 完整版（现象/排查/根因/修复/验证）→ 高频追问应答 → 复盘**。
> 所有数字与证据均来自 job-copilot 仓库的真实提交与冒烟记录，可现场打开代码佐证。

## 故事一：SQLAlchemy 2.0 自动事务，让上传接口悄悄 500 了三年

**钩子**：重构上传接口时，双端口冒烟发现旧应用的 `/document/upload` 一直在返回 500——但文档其实已经成功入库建索引了，这个问题被掩盖了整整三个版本。

### 30 秒版

把 Flask 原型迁到 FastAPI 时做双端口对照冒烟，发现旧应用上传接口返回 `code: 500, "A transaction is already begun on this Session"`，而新应用同请求返回成功。排查发现根因在创建简历版本记录的函数：先用 `session.execute()` 查最大版本号——SQLAlchemy 2.0 里这会**自动开启事务**（autobegin）——接着又显式调 `session.begin()`，2.0 直接抛 InvalidRequestError。我用一个 30 秒的 SQLite 内存库最小实验复现了这不是环境问题而是确定行为，然后把"读版本号 + 写记录"合并进同一个事务。这个 bug 的隐蔽之处在于：上传的主流程（保存、解析、建索引）在崩溃前已经逐个提交，文档看起来一切正常，只有接口响应是 500、简历版本表永远是空的。

### 完整版

**现象**。双端口冒烟（旧 Flask 跑 5000、新 FastAPI 跑 8018，同一请求对照）发现旧应用上传接口返回 HTTP 200 但信封 `code: 500`，message 是 SQLAlchemy 的 `InvalidRequestError`。更微妙的是：删除接口、详情接口都显示文档 `indexed`、字数正常——**功能看起来是好的，只有响应是错的**。

**排查**。后端日志堆栈指向 `_create_resume_version`。读代码：

```python
session = db_manager.get_session()
max_ver = ResumeVersionRepository.get_max_version_number(session, conversation_id)  # ← SELECT
with session.begin():                                                               # ← 二次 begin
    ResumeVersionRepository.create(session, ...)
```

`get_max_version_number` 内部是 `session.execute(select(...))`。SQLAlchemy 2.0 的 Session 是 autobegin 语义：第一次执行 SQL 就隐式开启事务；此时再调 `session.begin()` 就抛 "A transaction is already begun on this Session"。为了排除"环境/版本巧合"，我写了个 30 秒的最小实验：SQLite 内存库 + 一个 SELECT + 一个 `begin()`，稳定复现同样的 `InvalidRequestError`——证明这是 ORM 的确定行为，不是偶发。

**根因**。旧代码按 SQLAlchemy 1.x 之前的习惯写"先查再显式开事务写"；2.0 把"执行 SQL 即自动开事务"变成了确定语义，两种开事务方式撞车。**为什么三年没被发现**：上传主链路（保存文件 → 解析 → 建索引 → 状态置 indexed）每一步都是独立事务、各自提交，崩溃发生在**最后的版本记录步骤**——所以文档永远传成功了，前端刷新列表也看得到文档，没人注意到响应码是 500，`resume_versions` 表从建表以来就是空的。

**修复**。把读和写合并进同一个事务：

```python
with session.begin():
    max_ver = ResumeVersionRepository.get_max_version_number(session, conversation_id)
    ResumeVersionRepository.create(session, ...)
```

这不仅消除了冲突，还顺带获得了正确性收益：版本号的读取和写入现在原子了，并发上传两份简历不会拿到同一个版本号。

**验证**。新应用同场景返回 `code: success`，`resume_versions` 表出现 version=1 的记录；旧应用复跑同请求确认 500（作为对照基线）。

### 高频追问应答

- **"autobegin 是什么？为什么 1.x 没事？"**——2.0 把"Session 上第一次执行 SQL 即隐式 begin"定为确定行为；1.4 的 legacy 模式里 autocommit 语义不同。我的环境一直是 2.0，所以旧代码在旧环境里**同样应该炸**——它没炸是因为没人盯着响应码看。
- **"flush 和 commit 的区别？"**——flush 把 ORM 内存变更写成 SQL 发到数据库（在事务内可见），commit 才持久化；close 会回滚未提交事务。这也是故事二里"只 flush 不 commit 等于没写"的根源。
- **"为什么 scoped_session/线程池在这里不是问题？"**——这个 bug 与线程无关，是**同一个请求内**的顺序问题：先 execute 后 begin 必炸。线程局部 session 只影响跨请求的状态隔离。
- **"怎么避免再犯？"**——事务边界只允许一种开法（要么全显式 begin，要么靠 autobegin + commit）；把"SELECT 后 begin"这类模式写进 code review 检查项；用合同测试盯响应码而不只盯功能表现。

### 复盘

做得好的：不信任"看起来能用"，用双端口对照让旧系统自己暴露问题；用最小实验区分"环境问题"和"确定行为"。可以更好的：旧系统的上传响应码早就可以用一条 `grep 500 access.log` 发现——**可观测性欠债不是没数据，是没人看**。

## 故事二：模拟面试的每一轮回答，其实从来没存进过数据库

**钩子**：移植模拟面试功能时读代码发现，旧应用的面试问答、LLM 评价、轮次、总分——全部写库操作都在一个没有 commit 的事务里，`session.close()` 时被整体回滚。也就是说"面试历史与复盘"这个功能，在旧系统里从来没真正工作过。

### 30 秒版

排查方式是纯代码审读：`answer()` 接口里 `InterviewMessageRepository.create()` 只做了 `session.add + flush`——flush 只是把 SQL 发出去，**不提交**；整个函数没有任何 commit，最后 `finally: session.close()`，未提交事务被回滚。所以旧应用面试回放里只有开场题，每一轮回答和评价都在关闭连接时蒸发了。修复成三段式：事务一读快照（会话状态、历史、JD），LLM 评估放在事务外（不能让一个 30 秒的 LLM 调用占着数据库连接），事务二统一落库。新实现冒烟验证：两轮真实问答后，detail 返回完整的 question→answer→evaluation→question 序列，round_count=2。

### 完整版

**现象**。不是运行时报错，而是移植时的代码审读发现：写库路径"看起来完整"（create 都调了），但找不到任何 commit。

**排查**。逐步确认三个事实：① repository 的 `create` 是 `session.add() + session.flush()`——flush 把 INSERT 发到数据库但事务未提交；② `answer()` 里所有 create/update 都不在中国任何 `with session.begin():` 块内；③ 函数末尾 `session.close()`——SQLAlchemy 语义：close 释放连接并**回滚未提交事务**。三者合起来：每次回答的写入都是"写了又擦"。对照 `start()` 接口——它用了 `with db_session.begin():`，所以开场题目是持久化的。这也解释了一个此前的疑惑：`total_score` 列类型是 Integer（存 float 会截断）这个"已知 bug"为什么从没造成可观察的错——因为 total_score 根本没被写进去过。

**根因**。写代码时把 `flush` 当成了"保存"，没有建立"事务边界必须显式"的意识；而 start 接口恰好用了 `begin()`，对比之下 bug 就藏不住了。

**修复**。三段式结构：

```
事务一（读）：会话状态、历史消息、当前题目、JD 文本 → 快照为普通数据，立即释放连接
LLM 评估（无事务）：30 秒级外部调用，绝不占着数据库连接
事务二（写）：重新取实体（在新事务内），写用户回答、评价、下一题，更新轮次/总分
```

**验证**。真实冒烟：开始面试生成 5 题 → 两轮真实作答 → detail 返回 `question, answer, evaluation, question, answer, evaluation, question` 完整序列、round_count=2。修复前这个序列在旧系统里永远只有第一项。

### 高频追问应答

- **"为什么不把 LLM 调用包在事务里？"**——事务持着连接池连接；LLM 一次 30 秒，几个并发面试就能把默认 5 个连接的池耗光。正确姿势是"短事务读写、外部调用在事务外"，评估失败就整体不落库（当前回答丢失但系统稳定）。
- **"flush 了为什么不算数？"**——flush 的目标是让同事务内的后续语句能看到变更（比如拿到自增 ID）和让约束校验提前；持久化语义只属于 commit。
- **"怎么系统性防止这类问题？"**——写操作统一走 `with session.begin():` 的显式边界；code review 时把"这个函数里 commit 在哪"当必答题；对"写完必须能读回"的链路写持久化断言测试（我们修复后的验证就是 detail 回读）。

### 复盘

这个故事的教训比 bug 本身值钱：**"代码执行了"和"数据持久化了"是两件事**。以及一个诚实的表述技巧——这个故事我在旧系统上没有实测复现（结论来自 SQLAlchemy 语义推演 + 代码证据），面试时主动说明"这是审读结论，我没有在旧应用上跑过复现"，比硬说是实测更显工程判断力。

## 故事三：一个花括号，炸掉了全部对话请求

**钩子**：给 Agent 内置 9 个求职技能后第一次冒烟，所有对话请求直接报错——根因是技能描述里的 `{简称}` 三个字符，被 Prompt 模板当成了变量名。

### 30 秒版

内置 ASu-skills 技能包时，我把技能目录动态生成进 Agent 的系统提示。第一次冒烟所有请求都抛 `KeyError: missing variable {'简称'}`。排查发现 project-guide 技能的描述文本里含 `{简称}` 占位符，而系统提示是 `ChatPromptTemplate` 的**模板文本**——模板引擎把动态拼接进去的 `{简称}` 当成了未提供变量。修复是把动态内容注入模板前转义花括号（`{` → `{{`），并把系统提示构建抽成独立函数、加了"渲染结果必须保留花括号字面量"的回归测试。本质上这是 SQL 注入的 Prompt 版：**动态内容永远不能和模板语法混在一层**。

### 完整版

**现象**。内置技能后的第一次对话冒烟，SSE 直接返回 error 事件，后端日志：`Input to ChatPromptTemplate is missing variables {'简称'}`——注意 `简称` 是个中文词，绝对不是我们代码里定义的变量。

**排查**。三步定位：① 报错来自 `prompt.invoke()`，说明是模板校验阶段就炸了，与 LLM 无关；② 全局搜 `{简称}`，唯一来源是 `resources/skills/project-guide/SKILL.md` 的 frontmatter description——它里面写了教程占位符 `{简称}`；③ 我的 `build_agent_system_prompt()` 用 f-string 把技能目录（含各技能 description）拼进系统提示字符串，这个字符串再被 `ChatPromptTemplate.from_messages()` 当模板解析——**两层模板语义叠加**：f-string 先做一次插值，ChatPromptTemplate 再把结果里的 `{xxx}` 当变量。

**根因**。LangChain 的 ChatPromptTemplate 用 `{var}` 做变量插值；任何进入模板文本的动态内容都必须转义（`{{` / `}}`）。用户消息里的花括号是安全的——它走的是变量**值**通道，不经过模板解析；只有我拼进**模板文本**的动态内容才踩雷。

**修复**。

```python
def build_agent_system_prompt() -> str:
    return (
        "你是一个专业的求职助手机器人。……"
        "内置求职技能（ASu-skills）：……\n"
        + skill_loader.catalog_prompt().replace("{", "{{").replace("}", "}}")
    )
```

同时加了回归测试：用真实技能目录渲染模板，断言 `job-match` 在场且 `{简称}` 作为**字面量**保留。

**验证**。重启后同请求全链路通过；Agent 在"用 job-match 分析 JD 和简历"的真实冒烟中正确调用了 `load_skill`，按技能的证据矩阵方法论（已匹配/表达缺口/待确认）输出了 4327 字分析。

### 高频追问应答

- **"为什么用户输入里的花括号不炸？"**——用户内容通过 `invoke({"query": ...})` 走变量值通道，模板引擎不解析值里的花括号。只有拼进模板**文本**的动态内容需要转义。这也是"内容与模板分层"的价值。
- **"这和 Prompt Injection 什么关系？"**——同族问题：不可信内容进入指令层的结构边界。区别是这里炸的是**可用性**（模板变量校验），注入攻击炸的是**安全性**（指令被覆盖）。缓解思路同源：动态内容永远放数据通道，不放指令通道。
- **"怎么系统性防？"**——把系统提示构建抽成纯函数并加渲染回归测试（我们就是这么做的）；对动态拼接进模板的任何内容做转义审查；升级 LangChain 时跑一遍 prompt 渲染的快照测试。

### 复盘

这个 bug 的教学价值在于它是**两层模板语义的叠加事故**：f-string 和 ChatPromptTemplate 都认为自己该解释花括号。以及一个流程教训：第一次冒烟前我只跑了 pytest——单测覆盖了加载器和工具，但没覆盖"提示词模板能渲染"这个集成点。**提示词也是代码，模板渲染也要有冒烟**。

## 故事四：模型编造"召回率提升 22.6%"，我们的系统却告诉用户"低风险"

**钩子**：全链路验证时发现，让模型用 STAR 法则概括项目，它编造了 5 条量化数据（召回率提升 22.6%、人工一致性 89%、3 位同学获面试邀约……），校验器明明全部抓出来了，风险徽标却显示"低"——因为旧规则只看无支撑占比，5/51≈10% 不到 25% 的 medium 线。

### 30 秒版

我们的对话链路带一层幻觉治理：生成后用另一个低温 LLM 把回答拆成断言，逐条判断"是否有检索上下文支撑"，按无支撑占比给低/中/高风险徽标。验证时发现占比规则有盲区：模型编造的**精确假数字**（22.6%、89%）只占 10%，判了低——但用户恰恰最信任这种具体数字。修复：无支撑断言中含"编造的具体量化数据"（百分比/小数/倍数/两位以上数字）时至少升 medium，两条及以上或占比达 10% 直接 high。分级逻辑抽成纯函数 `_assess_risk` 并配 6 个单测，同请求复跑验证 low → high。

### 完整版

**现象**。验证会话里同一问题的两次运行：修复前 supported 46 / unsupported 5，risk=low；细看 unsupported 全是硬编造——"混合检索平均召回率较单 FAISS 提升 22.6%（内部测试集）"、"评分结果与人工初筛一致性达 89%（抽样 50 份）"、"3 位同学获面试邀约（含 2 家一线大厂）"、"Medium 技术笔记 400+ 收藏"、"核心链路 100% 可运行"。这些数字在简历和知识库里都不存在。

**排查**。两问：① 校验器抓到没有？——抓到了，5 条全在 unsupported 列表里，说明"检测"环节是好的；② 分级为什么低？——占比 5/51≈9.8%，低于 0.25 的 medium 线。根因是**分级指标选错了**：占比衡量的是"无支撑的量"，但危害由"无支撑的质"决定——一句模糊的"深受好评"和一组精确假数字，前者用户一笑而过，后者会被写进求职材料。

**修复**。把分级抽成纯函数并加升级规则：

```python
numeric = [c for c in unsupported if _has_concrete_number(c)]   # 百分比/小数/倍数/两位以上数字
if numeric:
    if risk == "low": risk = "medium"
    if len(numeric) >= 2 or ratio >= 0.10: risk = "high"
```

真实案例复核：5 条无支撑里 4 条含量化数字 → ≥2 条 → **high**。

**验证**。6 个分级单测（占比阈值回归、单条量化升 medium、占比≥10% 升 high、两条量化必 high、非量化不误伤）；同请求复跑，risk low → high（模型那次编得更多，11 条无支撑）。

### 高频追问应答

- **"为什么不干脆把 medium 线降到 5%？"**——占比线只解决"量"，解决不了"质"；一条编造的精确数字占比再低也该亮黄灯。两条规则正交：量管整体，质管性质。
- **"校验器会不会误伤？"**——会，而且我们观测到了：模型说"平台已开源（GitHub 链接）"，链接是真的，但简历正文里没有，被标为无支撑。我们的徽标语义是"无上下文支撑"而非"虚假"，前端把无支撑断言原样列给用户自行判断。改进方向是把 GitHub 等元数据并入证据源。
- **"这在工业界叫什么？"**——生成层的 Faithfulness（忠实度）指标：把答案拆成原子陈述，逐条对照检索证据验证。RAGAS 就是这么做的；我们相当于内置了一个轻量版 Faithfulness + 基于断言性质的风险分级。
- **"为什么检测器能抓到？"**——生成后用另一个低温（temperature=0.1）LLM 做"断言 vs 上下文"的一致性判定；检测和生成分离，且检测失败不阻塞主回答（它是增强项）。

### 复盘

做得好的：验证驱动——是全链路验证（而不是拍脑袋）暴露的规则盲区；修复时把规则抽成纯函数，让"分级逻辑"可以被穷举测试。可以更好的：上线这套分级时就应该用"编造数字"类 badcase 做过回归——规则上线没有对抗样本，等于裸奔。

## 加餐（前端题）：对话长了鼠标滚轮为什么彻底失灵

**钩子**：重构前端后用户反馈"对话一长滚轮就死了"——不是滚动慢，是**完全没反应**。

30 秒版：外层布局用了 CSS Grid 但没定行高，隐式行是 `auto`——内容变长整行被撑高，内层聊天区永远"装得下"就不产生内部滚动；而窗口又被 `overflow: hidden` 锁死（防全局滚动的措施），于是**没有任何可滚动的东西**，滚轮自然没反应。修复一行：`grid-template-rows: minmax(0, 1fr)`，配合整条高度链的 `min-height: 0`。追问点：为什么 flex/grid 子项要 `min-height: 0`（默认 min-height:auto 使内容撑开弹性盒子）；`overscroll-behavior: contain` 防滚动链。

## 讲法总纲（四个故事共用的框架）

1. **钩子先给反差**：'功能看起来是好的，响应码是 500' / '所有写库都执行了，数据是空的' / '一个花括号炸掉全部请求' / '编造的数字被判低风险'。
2. **现象只说可观测事实**，不提前下结论。
3. **排查展示方法**：双端口对照、最小复现实验、代码审读三证据、日志堆栈定位——证明的是排查能力，不是运气。
