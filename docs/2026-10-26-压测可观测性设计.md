# 服务器资源监控与后端分段计时 设计

日期：2026-10-26
状态：设计已确认，待实现

## 背景与目标

2026-10-26 在线上（displaydemo.top）完成 13 轮 AI 压测，配置指纹一致，全部成功，样本为 memory 60、RAG 15、Agent 9。暴露出两个无法回答的问题：

1. memory 阶段 2 的 P95 约 7.5s，且慢请求在三轮里位置完全一致（每个用户第 7～10 次请求）。后端 `_MAX_HISTORY_MESSAGES = 12` 触发的历史压缩会同步多调一次小模型，与现象吻合，但没有证据。
2. RAG（约 8.4s）、Agent（约 22.6s）的耗时无法拆到检索、重排、模型、工具、校验等阶段；同时没有 CPU、内存、MySQL 的采样，只能证明“健康检查正常”，不能证明服务器没有瓶颈。

本设计新增两个相互独立的单元，为后续“优化前后对比”提供数据：

- A：服务器资源监控（`tools/loadtest/`，不需要部署后端）。
- B：后端分段计时（后端 + 压测脚本集成）。

先做 A，再做 B。

## 非目标

不引入新依赖，不修改任何业务逻辑，不改变现有接口的响应结构，不做 Prometheus/Grafana/OpenTelemetry（2GB 服务器负担过重）。

## 部署与约束

- 后端是 systemd 管理的单 worker uvicorn（`deploy/job-copilot.service`），stdout 进入 journal。
- 目前没有请求级日志配置；应用里的 `logger.info` 在 uvicorn 默认配置下不会输出。
- 用户称 Locust 与被测服务在同一台服务器上运行，但配置清单记录的压测机是 Windows 11（主机名 ASUS）。两者矛盾，所以监控不假设压测工具的位置，把 Locust 进程单独归组；并把压测机主机名写入配置清单。

## 单元 A：服务器资源监控

### 文件

- `tools/loadtest/server_monitor.py`：采样器，仅用标准库，读取 `/proc`，不需要 root。
- `tools/loadtest/analyze_server.py`：汇总器。
- `tools/loadtest/test_server_monitor.py`：用固定的 `/proc` 样本文本测试。

### 采样

默认每秒一行写入 `<前缀>_server.csv`。时间戳使用 Unix 秒，便于与压测的 `stats_history` 对齐。

| 类别 | 字段 |
|---|---|
| 系统 | CPU 的 user / sys / iowait / steal / idle 百分比（`/proc/stat` 两次采样的差）、load1/5/15、可用内存 MB、已用 swap MB、`pswpin`/`pswpout` 的每秒差值、网卡收发字节每秒、`TCP established` 数 |
| 进程分组 | 每组的 CPU%（`/proc/<pid>/stat` 的 utime+stime 差，100% 表示满载一个核）、常驻内存 RSS MB、进程数 |
| MySQL（可选） | 每 5 秒读取一次 `Threads_connected`、`Slow_queries`，用 `--mysql-defaults-file` 传入凭证，不接受命令行密码 |

进程分组按命令行匹配：

- `backend`：命令行含 `uvicorn` 且含 `app.main`。
- `locust`：命令行含 `locust`。
- `mysqld`：进程名 `mysqld` 或 `mariadbd`。
- `nginx`：进程名 `nginx`。

同一进程只归入第一个匹配的分组。

### 启动元信息

启动时写 `<前缀>_server_meta.json`：主机名、内核版本、CPU 核数、`MemTotal`、`SwapTotal`、`systemctl show job-copilot` 的 `MainPID` 与 `ActiveState`、`git -C <--app-root> rev-parse --short=12 HEAD`（默认 `/opt/job-copilot`）、采样间隔、监控脚本哈希。拿不到的字段写 `null`，不阻断运行。

### 运行方式

```
python3 tools/loadtest/server_monitor.py --out reports/20261026 --label r1 --duration 150
python3 tools/loadtest/server_monitor.py --out reports/20261026 --label r1 --wrap "<压测命令>"
```

- `--duration`：固定时长后退出；`--wrap`：运行给定命令，命令结束后停止；二者都不给则前台运行到 Ctrl+C。
- 输出前缀 `<out>/server-<label>`；前缀已存在则拒绝覆盖，与启动器行为一致。
- 非 Linux 环境（没有 `/proc`）直接退出并说明原因，不产生空文件。
- 单次采样超过间隔时记录 `lag_ms`，不累积漂移。

### 汇总

`analyze_server.py <server.csv> [--config <ai_config.json>]`

- 给了配置清单就按 `run.started_at` ~ `run.ended_at` 裁剪窗口，否则使用整个文件。
- 输出每个进程组的 CPU 均值/P95/峰值、RSS 峰值，以及系统层面的预警：
  - swap 有换入换出活动；
  - 可用内存低于总量 10%；
  - iowait 的 P95 高于 10%；
  - steal 非零；
  - 系统 CPU 持续高于 80% 且超过 10 秒。
- 预警只给出事实和阈值，不给“已经是瓶颈”的结论。

### 配置清单的补充

`run.tool` 增加 `hostname`；`run` 增加 `trace`（是否发送追踪请求头）。二者只做追溯，不进入 `config_id`。

## 单元 B：后端分段计时

### 模块 `backend/app/core/perf_trace.py`

- `PerfTrace`：保存 `trace_id`、起点、span 列表（带锁，防止工具内的线程池乱序）。
- 一个 `ContextVar` 持有当前 trace，另一个持有当前 span 栈。
- `trace_scope(kind, **attrs)`：在 API 入口开启，退出时输出日志；返回 trace 供取 `Server-Timing`。
- `span(name, **attrs)`：没有当前 trace 时返回空操作，**不影响其他接口**。span 记录 `seq`、`name`、`parent`（栈顶名）、`start_ms`（相对起点）、`dur_ms`、`attrs`。
- `record_llm_call(model, dur_ms, in_tokens, out_tokens, fallback, error)`：写一条 `llm.call` span，`parent` 取当前 span 栈顶，用来区分压缩、重排、回答、工具决策、校验、简历抽取。
- 汇总：按顶层阶段名累加耗时，`llm` 单列次数与总耗时。

约定：非流式 chat 是同步端点，在线程池里执行且 context 被复制，`ContextVar` 可见；流式生成器要像 `request_model_scope` 那样在生成器内部开启 scope。

### 打点位置

| 位置 | span 名 |
|---|---|
| `_prepare_chat`：校验可写、读摘要、读历史 | `db.writable`、`db.history` |
| `compress_history` 是否触发 | `compress`（属性：`triggered`、`messages`） |
| RAG 检索：会话索引、内置知识库、重排 | `retrieve.conversation`、`retrieve.builtin`、`rerank` |
| 模型回答 | `answer` |
| Agent 每轮模型决策 / 每个工具 | `agent.round`、`tool.<工具名>` |
| 上下文校验 | `verify` |
| 保存消息、读取详情 | `db.save`、`db.detail` |
| 所有 LLM 调用 | `llm.call`（由 `QuotaFallbackMixin._generate/_stream` 统一记录；token 取不到则为空） |

流式端点额外记录 `ttft_ms`（首个 delta）、`done_ms`（done 事件）、以及 done 之后的 `verify`。

### 输出

- 日志：专用日志器 `app.perf`，每个 chat 请求一行 `PERF {json}`。字段：`v`、`trace_id`、`endpoint`、`mode`、`model`、`conversation_id`、`total_ms`、`stages`（阶段汇总）、`llm_calls`、`llm_ms`、`spans`。不记录问题和回答文本。
- 启用：在应用启动时给 `app.perf` 加输出到 stdout 的处理器并设 INFO，使 systemd 能收进 journal；不改变根日志器。开关 `PERF_TRACE_LOG`，默认开启。
- 响应头：`Server-Timing`，格式 `total;dur=…, prepare;dur=…, retrieve;dur=…, llm;dur=…;desc="n=3", tool;dur=…, verify;dur=…, db;dur=…`。仅当环境变量 `PERF_TRACE_HEADER=1` 且请求带 `X-Perf-Trace: 1` 时返回，其他情况不暴露内部耗时。只做在非流式 `/conversation/chat`。

### 压测脚本集成

- 启动器增加 `-Trace`：设置 `LT_TRACE=1`，每个 chat 请求发送 `X-Perf-Trace: 1`。
- `ai_common.py` 解析 `Server-Timing`，每个 chat 请求写一行到 `<前缀>_ai_requests.csv`：`seq`、`user`、`started_at`、`client_ms`、`ok`、`reason`、`server_total_ms`、各阶段毫秒、`llm_calls`、`llm_ms`。没有响应头时服务端列留空，客户端列仍然写，因此该文件同时提供原始耗时用于合并分位数。
- `analyze_trace.py`：读取一轮或多轮的 `_ai_requests.csv`，输出
  - 各阶段 P50/P95/占总耗时比例；
  - 按“每个用户的第几次请求”分组的客户端耗时与各阶段耗时（用于验证压缩）；
  - `client_ms - server_total_ms` 的差值（网络与排队）。
- 只有 `config_id` 相同的轮次才允许一起汇总，否则拒绝并列出差异。

## 数据流

```
Locust 请求 ──X-Perf-Trace: 1──▶ chat 端点 ── trace_scope
                                   ├─ span: prepare / retrieve / llm.call / tool / verify / db
                                   ├─ 日志: PERF {json} ─▶ journal
                                   └─ 响应头: Server-Timing（受控）
Locust ◀──响应───────────────────────────┘
   └─▶ <前缀>_ai_requests.csv ─▶ analyze_trace.py

服务器 ── server_monitor.py ─▶ <前缀>_server.csv ─▶ analyze_server.py
```

## 错误处理

- 计时代码任何异常都不得影响业务请求：`span` 与日志输出捕获并吞掉自身异常，只记一条 warning。
- 监控读不到某个 `/proc` 文件或进程退出，该字段留空并继续采样。
- `Server-Timing` 缺失或格式异常时压测脚本只留空服务端列，不判失败。

## 测试策略

- 后端：用例覆盖嵌套 span 与父子关系、没有 trace 时的空操作、线程池内的传递、LLM 调用记录的 `parent`、日志 JSON 字段、响应头格式与开关控制。
- 监控：用固定文本验证 `/proc/stat` 差分、进程分组、内存/swap 字段解析、CSV 列、非 Linux 的拒绝。
- 压测：用本地模拟后端验证 `Server-Timing` 解析、`_ai_requests.csv` 列、`analyze_trace.py` 的指纹校验。
- 无法在本机验证的部分：监控在真实 Linux 上的采样，需要用户在服务器上跑一次后核对。

## 验收

- 在服务器上跑一轮阶段 2：`server-<label>_server.csv` 有连续采样，汇总能给出各进程组的 CPU 与内存。
- 部署后端后跑一轮带 `-Trace` 的阶段 2：`_ai_requests.csv` 的服务端列非空，`analyze_trace.py` 能回答“第 7～10 次请求变慢时，额外时间落在哪个阶段”。
- 不带 `-Trace` 时，请求和响应与改动前完全相同。
