## 问题一：project-guide 从发请求到出字要 81 秒

### 实测数据

`conv_20261027150303_cb126c`，2026-10-30 08:39:36，模型 qwen3.8-flash。

| 阶段 | 耗时 | 输入 / 输出 token |
|---|---|---|
| 检索 + DB | 439ms | — |
| 首轮（流式） | 117.4s | 7,579 / 7,716 |
| 工具轮 1（非流式） | 81.1s | 10,295 / 5,369 |
| 工具轮 2（非流式） | 35.0s | 15,693 / 2,704 |
| 工具轮 3（非流式） | 44.0s | 18,371 / 3,477 |
| **合计** | **278s**（首字 81.3s） | 输出 19,266 |

`tool.html_document_tool` 自身执行只要 0.7ms 和 2.3ms，时间全在模型生成。

### 三个原因

**1.1 思考模式是开的，思考期间不产出任何字**

`_get_qa_llm()` 构造客户端时没传 `enable_thinking`，qwen3 系在兼容端点默认开思考。实测对比（同一份 SKILL.md，同样 prompt）：

| 设置 | 首字 | 总耗时 | 输出 token | 其中思考 |
|---|---|---|---|---|
| 默认 | 10.04s | 13.51s | 721 | 517（72%） |
| 默认（第二次） | 11.54s | 13.42s | 678 | 553（82%） |
| `enable_thinking=False` | 0.75s | 5.04s | 197 | 0 |

按这个比例，那次请求约 1.3 万输出 token 是思考内容，用户看不见，但照常计费。

**1.2 内容生成了两遍**

首轮流式先吐 7,716 token 正文（前端已经在显示），然后才决定调 `html_document_tool` 落盘，又生成 5,369 + 2,704 token 的文件内容。同样的东西写了两遍。

原因：`_apply_skill` 只注入了 SKILL.md 全文，没约束"先落盘、别在回答里复述"。对比 `make-resume` 是做了特判的（`conversation_chat_service.py:253-259`）。

**1.3 工具轮是 `invoke`，全程无输出**

`_run_tool_rounds` 里 `self._get_agent_llm().invoke(messages)`，每轮 35~81 秒只有一条 `thinking` 事件，前端只能显示"第 N 轮，已等 Xs"。

### 修改意见（已定：A + B + E2）

**A. 禁止复述正文**

现在首轮先吐 7,716 token 正文，再调 `html_document_tool` 把同一份内容写进工具参数。约束方式照 `make-resume` 的特判（`conversation_chat_service.py:253-259`），但 `project-guide` 要同时接收 E2 的产出范围参数，两处改的是同一段注入文本，合并实现。

预期：首轮输出从 7,716 降到 ~300 token，工具参数不变，总耗时 278s → 约 190s。
风险：低。要验收模型是否真的先调工具——生成型任务的指令服从度通常好，但要实测一次。

**B. 思考过程逐字透传给前端**

不改 `llm_factory`：`ChatGenerationChunk.additional_kwargs` 里已经带了 `reasoning_content`，`QuotaFallbackMixin._stream` 原样透传。在 `chat_stream` 的首轮流式循环里读出来，推一个新事件：

```python
for chunk in self._get_agent_llm().stream(prompt_messages):
    reasoning = (chunk.additional_kwargs or {}).get("reasoning_content")
    if reasoning:
        yield {"event": "thinking_delta", "data": {"text": reasoning}}
    if chunk.content:
        streamed_text += chunk.content
        yield {"event": "delta", "data": {"text": chunk.content}}
```

前端两处改动：

- `stores/chat.js` 的 SSE 解析加 `thinking_delta` 分支，累加到 `assistantMsg.reasoning`（`reactive` 对象上的新字段，不进 `messages`）
- `MessageItem.vue` 在气泡顶部加一个折叠区：标题「思考过程 · 已 Ns」，内容等宽小字、纯文本不渲染 Markdown。**默认展开**（等待时用户需要看到东西），收到 `done` 后自动收起

三条边界必须守住：

1. **不落库**。reasoning 只存在前端内存，`done` 之后刷新页面就没了。不写 `conversation_messages`、不进 detail 回放——一次 1.3 万 token 的思考塞进历史，下一轮输入会直接翻倍。
2. **只有首轮有逐字思考**。工具轮走 `invoke`（非流式），`reasoning_content` 要等整段返回才拿得到，那时答案也出来了，没有展示价值。所以那 81s + 35s + 44s 期间仍然只有 `thinking` 事件（"第 N 轮，已等 Xs"）。E2 + A 生效后工具轮变少，这个问题会自然减轻。
3. **思考可能是长文本**。前端要用固定高度 + 滚动，不能无限撑高气泡；长到几千字时截断显示（保留末尾，因为结论通常在最后）。

风险：低。唯一要盯的是 `done` 事件里不要被 `assistantMsg.content = event.data.answer` 覆盖掉折叠区的显示状态。

**C. 生成型任务关闭思考 —— 已做 A/B，结论是「不关」**

见下一节实测。速度收益确实大，但成稿里开始编造项目路径，而 SKILL.md 的第一条硬性要求就是"文件、函数必须能在源码中定位"。否决。

### 1.4 A/B 实测（2026-10-30 09:05）

同一份 prompt（`build_agent_system_prompt()` + SKILL.md 全文 + 同一句 query），模型 qwen3.8-flash，各跑一次完整导学。原始产物在 `F:\dshcache\ab\`（`thinking_on.md` / `thinking_off.md` / `metrics.json`）。

|---|---|---|---|

| 输出 token | 5,538（其中思考 2,129，38%） | 2,219 | 少 60% |
| 正文字数 | 5,795 | 4,732 | 少 18% |

**结论**：思考开时，模型面对"不知道具体路径"的选择是标注待补；关掉思考后，它选择编一个看起来合理的。对一个"必须可核实"的交付物，这个代价大于 60 秒。

所以时间从另外两处拿：禁掉重复生成（A）+ 让用户先选产出范围（E2），体感由思考透传（B）兜住。预计两份的请求 278s → 190s，单份 90~120s，首字仍然慢，但页面不再像卡死。

> 补充：这次 A/B 的输入只有 4,365 token（没有历史消息）。线上那次 7,579 起、累计到 18,371，所以线上绝对耗时比这里的 100s 更长。比例关系仍适用。

**E2. 前端选择产出范围（本次采用）**

一份导学约 5~8k 输出 token，加面经就是 1.9 万。让用户在发请求前就选清楚要哪一份，单次请求的生成量直接减半。

*前端*（`Composer.vue`）：选中 `project-guide` 技能后，在技能 chip 右侧出现三选一（分段控件，默认「两份」）：

| 选项 | 传给后端的值 | 产出 |
|---|---|---|
| 导学 | `guide` | `导学-{简称}.md` |
| 面经 | `interview` | `面经-{简称}.md` |
| 两份 | `both` | 两份都出（现有行为） |

其他技能不显示这个控件，`skill_option` 一律为空。

*接口*：`ChatRequest` 新增 `skill_option: str = ""`，随 `chat` / `chat/stream` 两个端点透传。只对 `project-guide` 生效，其他技能忽略（不报错，避免前端状态残留导致 400）。

*后端*（`conversation_chat_service._apply_skill` 增加 `option` 参数）：注入文本要同时承担 A 和 E2 两个约束，合并成一段：

```python
_SKILL_OPTION_TEXT = {
    "guide": "本次只生成「导学」这一份（导学-{简称}.md），不要生成面经。",
    "interview": "本次只生成「面经」这一份（面经-{简称}.md），不要生成导学。",
    "both": "本次生成导学和面经两份。",
}

body = (
    f"【本次任务技能】用户显式选择了技能 `project-guide`（{meta['title']}）。\n"
    f"{_SKILL_OPTION_TEXT.get(option, _SKILL_OPTION_TEXT['both'])}\n"
    "直接调用 html_document_tool 把内容写入文件，不要调用 load_skill。\n"
    "回答里只写两三句说明、文件用途和必要缺口，**不要在回答里复述文件正文**。\n\n"
    + document
)
```

*为什么不在 HTTP 层拆两次请求*：两次 SSE 会被塞进同一个助手气泡，前端要额外维护归属；第二份失败时第一份已经落盘，重试语义混乱。而 agent 链路本身支持一次请求内多次 `html_document_tool`，"两份"用一次请求就能完成，没必要在传输层拆。真正要拆的是**生成量**，不是**请求数**——E2 让用户自己决定生成多少。

预期：选单份约 6~8k 输出 token，配合 A 之后单次请求约 90~120 秒；选两份仍是 190 秒左右。
风险：中低。模型可能不服从"只出一份"的约束（SKILL.md 里"硬性交付"一节默认要求两份），注入文本要压过它——把范围写在技能文本**之前**，并在验收时确认只落一个文件。若仍不听话，再考虑在 `html_document_tool` 层按 `skill_option` 拦文件名。

**D. 压缩 skill 注入（可选，排在 A/E2 之后）**

`SKILL.md` 13,427 字符全量注入，输入 token 从 7,579 起。可以拆成"模式选择 + 目标文件结构"注入，`references/*.md` 改为按需加载。收益是每轮 prefill 少 2~3k token，但和 278 秒比是小数。

### 1.5 补测结果（2026-10-30 11:20）

**B 方案实测时发现一个会让它整体失效的坑，已修。**

`CompatibleFallbackChatModel` 直接读 `chunk.additional_kwargs["reasoning_content"]` 读不到东西——`langchain-openai 0.3.35` 的 `_convert_delta_to_message_chunk` 只认 content / tool_calls / audio，`delta.reasoning_content` 在转换阶段就被丢掉了。也就是说，只改 `chat_stream` 那一处，前端折叠区永远是空的。

修法：在 `CompatibleFallbackChatModel` 里覆盖 `_convert_chunk_to_generation_chunk`，把 `delta.reasoning_content` 补回 `additional_kwargs`。原始 OpenAI SDK 的响应里确实有这个字段（实测 42 个 chunk 全部带 `reasoning_content`），丢的是 langchain 的转换层。

修复后的实测（qwen3.8-flash，project-guide + `skill_option=guide`，只 bind 工具不执行）：

| 指标 | 数值 |
|---|---|
| 思考字符 / 帧数 | 7,683 字符 / 836 帧（平均 9 字一帧） |
| 正文首字 | 41.7s |
| 总耗时 | 42.7s |
| 首轮正文 | 101 字（两句话说明缺口，无正文复述） |

**SSE 帧压力（`F:\dshcache\sse_bench.mjs`，复刻 `chat.js` 的读取循环 + `parseSse`）**：

| 场景 | 帧数 | 总字节 | 解析耗时 | 每帧 |
|---|---|---|---|---|
| 每帧 4 字 | 8,000 | 424 KB | **8.5ms** | 1.07µs |
| 每帧 80 字（聚合对照） | 400 | 21 KB | 0.4ms | 0.94µs |

结论：解析可以忽略（一次长任务多花不到 10ms）。真正的开销在 Vue 那次 reactive 更新，已被 150ms 节流压到"每 150ms 一次、每次 4000 字"。**不需要在后端做帧聚合。**

**E2 服从度**：两次样本都没有产出两份——一次直接调 `html_document_tool` 出单个文件（`file_name=guide-job-copilot`、`title=导学 · Job Copilot`、回答正文 0 字），另一次判断"没有仓库信息"先追问缺口、没落盘。没有出现"仍然生成导学 + 面经两份"的违约情况，但**样本只有 2 次，且第二次没走到落盘**，不能算充分验证。上线后第一次真实使用要确认只出一个文件。

> 附带发现：同一段 prompt 在 temperature=0.8 下行为不一致（一次直接落盘、一次先追问）。这是模型的正常判断（SKILL.md 要求信息不足时最多追问 3 个问题），不是缺陷；但说明"能不能一次落盘"不能只看单次结果。

## 问题二：流式进行中切会话后，发送功能永久失效

### 现象

一条消息正在生成时，点「新对话」、点侧栏其它会话、或点「停止生成」，之后在**任何**会话里点发送都没反应，只能刷新页面。

### 根因

`frontend/src/stores/chat.js:28-32`：

```js
stopStreaming() {
  this.streamController?.abort()
  this.streamController = null      // ← 身份凭证被清掉
},
```

收尾逻辑靠这个凭证判断（`chat.js:285-292`）：

```js
finally {
  if (this.streamController === controller) {   // 永远是 false
    this.streamController = null
    this.sending = false                        // ← 永远不执行
  }
}
```

`sending` 只有三个地方会置回 false：`send()` 的 finally、`sendStream()` 收到 `done` 事件、`sendStream()` 的 finally。第一条不适用；`done` 已经被 abort 掉不会来；第三条判断必然失败。

而入口是（`Composer.vue:83`）：

```js
if (chat.sending) return    // 静默返回，没有任何提示
```

触发点在 `Workspace.vue:73-77`：`currentId` 一变就调 `stopStreaming()`。

### 修改意见

**两行改动：**

```js
// chat.js:28
stopStreaming() {
  this.streamController?.abort()
  this.streamController = null
  this.sending = false      // 主动中断时由发起方负责收尾
},
```

```js
// chat.js:273 附近，catch 里
if (err.name !== 'AbortError' && !this.messages.includes(assistantMsg)) throw err
```

第二处的作用：abort 之后气泡可能已经被新会话的 detail 替换掉，原来的判断会把 AbortError 当异常抛给 Composer，多弹一个"操作失败"。

**顺带修一个潜在竞态（可选）**：`done` 事件里 `this.sending = false`（`chat.js:252`）是无条件的。如果旧流的 done 在新流开始后才到达，会把新流的发送锁解开。加一句 `if (this.streamController === controller)` 更稳。

**验收方式**：发一条长消息 → 中途点新对话 → 在新会话里发一条短消息，应能正常发出；再测「停止生成」后的发送。

## 问题三：「参考来源」显示的是刚上传的简历

### 结论：不是跨会话串数据

查证过程：

| 证据 | 结果 |
|---|---|
| 索引目录 | `faiss_index_uploads/<conversation_id>/` 按会话隔离，两个会话各有一份 |
| 复现检索 | 8:43 会话的检索结果 4 条，全部来自 `彭禹弘｜Ai全栈.pdf` |
| 文件字节 | 8:40 那份 420,827B，8:43 那份 422,624B，是两个不同文件 |
| nginx 日志 | 08:34:05 / 08:40:35 / 08:43:20 三次上传，均来自同一个浏览器 UA 与 IP |

08:43:12 建会话 + 08:43:20 上传，是「空态选文件自动建会话」这条路径（`Composer.vue` 的 `onFilesChange` 里 `if (!conv.currentId) await conv.create()`）。用户看到的动作只是选文件，实际发生了"建会话 + 上传"两件事，所以容易误判成"这是以前传的"。

### 真正需要改的两点

**3.1 有文件产物时不要发 `sources`**

`conversation_chat_service.py:435` 无条件 yield sources。而"生成简历"这类任务，检索结果和回答没有因果关系——模型用的是 `resume_generate_tool` 拿到的会话素材，sources 只是顺手跑的一次检索。和上下文校验的处理保持一致（`chat_stream` 里 `not files` 才做 verify，第 454 行）：

```python
if source_docs and not files:
    yield {"event": "sources", "data": {"sources": source_docs}}
```

风险：低。代价是非生成类任务不受影响，生成类任务不再显示来源面板。

**3.2 空态上传后，会话标题改成这个会话的概要**

现状：现有自动标题只管"有消息之后"（`conversation_store_service.py:329-332`）：

```python
if conversation.message_count == 0 and title == "新对话":
    text_for_title = self._strip_image_markdown(user_content).replace("\n", " ").strip()
    title = text_for_title[:20] or "图片消息"
```

纯上传、没发消息的会话永远停在「新对话」——这就是 8:39 那个会话现在的样子，隔一会儿再看根本认不出是哪个。

改法：上传成功后补一次标题，仍然只在「没有消息 + 标题仍是默认」时生效，不覆盖自动标题：

- 在 `app/api/documents.py` 上传成功（`bind_document` 之后）调 `store_service.set_default_title(conversation_id, f"简历：{文件名主干}")`
- `conversation_store_service` 新增 `set_default_title`，内部沿用同一条件（`message_count == 0` 且标题为「新对话」），截 20 字
- `conversation_repository` 需要一个 `update_title`（目前没有更新标题的方法）
