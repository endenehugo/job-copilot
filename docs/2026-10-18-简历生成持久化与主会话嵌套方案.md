# 自动简历生成 P2：主会话嵌套 + 持久化

> 前置：P1 已跑通「规范切片 → 抽取 → Jinja2 渲染 → 预览」，见
> `docs/2026-10-18-自动简历生成模块方案.md`。本文只解决 P1 遗留的三个缺口。
>
> 结论先行：**新增一张表 + 给消息表补一列 + 一个文件自愈策略**，不改渲染链路。

---

## 1. P1 的三个缺口（实测确认，非推测）

| 缺口 | 现状 | 后果 |
|---|---|---|
| 不落库 | `resumeGen` store 只在内存持有 `result` | 刷新即丢；切会话被 `reset()` 清空（`Workspace.vue:78`）；同一会话无法回看历史版本 |
| 主会话无痕 | 生成后直接 `selectNode('resume', cid, '')` 跳预览 | 对话流里没有任何记录，用户回不到「我什么时候生成过、基于哪份材料」 |
| 子节点缺失 | 侧栏树 `/GROUPS` 只有面试/JD 分析/项目优化三组 | 简历是这个工作台里唯一「生成了但树上看不见」的产物 |

一个容易误判的点：**面试 / JD 分析 / 项目优化都不在主对话流里**。它们各自是一张业务表
（`interview_sessions` / `job_analyses` / `project_rewrites`），侧栏树用 GROUP BY 统计出
子节点（`conversation_store_service.py:64 _attach_tree_badges`），主区按 `activeType` 切视图。
消息表 `conversation_messages` 只有 `id/message_id/conversation_id/role/content/created_at`，
**没有任何结构化载荷列**，`MessageItem.vue` 只能渲染 markdown + `files`（多来自 agent 工具的
`html_document` 回传）+ `sources`。

所以「嵌套进主会话」不是加个组件，是要给消息开一条**结构化载荷通道**。

## 2. 数据模型

### 2.1 新表 `resume_generations`

不复用 `resume_versions`（那是「上传简历 → 打分」的版本线，语义不同，混用会污染评分链路）。

```
id               BIGINT PK AUTO_INCREMENT
generation_id    VARCHAR(64)  UNIQUE NOT NULL      -- rg_<16hex>
conversation_id  VARCHAR(64)  NOT NULL
status           VARCHAR(16)  NOT NULL DEFAULT 'ready'   -- ready / failed
target_role      VARCHAR(128) NULL                 -- 冗余，列表展示用
data_json        LONGTEXT     NOT NULL             -- ResumeData 全量 JSON（唯一真相）
source_json      TEXT         NULL                 -- 素材指纹：文档 id / 字符数 / JD 分析 id
warnings_json    TEXT         NULL
missing_json     TEXT         NULL
stages_json      VARCHAR(255) NULL
model            VARCHAR(64)  NULL
html_filename    VARCHAR(128) NULL                 -- generated_docs/ 下的文件名，不含路径
html_chars       INT          NULL
version          INT          NOT NULL DEFAULT 1   -- 同会话内第几版
created_at       DATETIME     NOT NULL
updated_at       DATETIME     NOT NULL
INDEX ix_resume_generations_conv (conversation_id, id)
```

**为什么 `data_json` 是唯一真相、HTML 只是派生物**：P1 的渲染是纯函数（`render_html(data)`），
同一份 JSON 重渲染 0 次 LLM、约 20ms。HTML 存文件（7–15KB）便于下载与 `/conversation/file`
下发，但不入库存双份真相。**文件丢了能从 `data_json` 原地重建**（见 §5）。

**为什么保留 `version`**：同一会话反复「重新生成」应该是新增一版而不是覆盖。用户会想看
「上一版把团队规模标成待补，这一版补上了」。

### 2.2 消息载荷：独立表 `conversation_message_meta`（原方案为加列，实施时改掉）

> **实施变更**：原方案是 `ALTER TABLE conversation_messages ADD COLUMN meta TEXT NULL`，
> 落地时放弃了这个做法。原因是致命的：一旦把 `meta` 列写进 ORM 模型，
> **消息列表的 SELECT 就会带上这一列**——补列失败（缺 DDL 权限）时整个会话的历史消息
> 都查询失败，一个"锦上添花"的卡片功能会把核心链路带崩，且没有降级余地。
> 独立新表由 `create_all` 自动创建，零 DDL 风险，列不存在时最多是卡片不显示。

```sql
CREATE TABLE conversation_message_meta (
  id              BIGINT PK AUTO_INCREMENT,
  message_id      VARCHAR(64) UNIQUE NOT NULL,
  conversation_id VARCHAR(64) NOT NULL,
  kind            VARCHAR(32) NOT NULL DEFAULT '',
  payload_json    TEXT        NOT NULL DEFAULT '{}',
  created_at      DATETIME    NOT NULL,
  INDEX ix_conversation_message_meta_conversation_id (conversation_id)
);
```

按 `conversation_id` **一次查出整段会话的载荷**再合并进消息列表（`map_payloads_by_conversation_id`），
消息列表不会因此变成 N+1。`kind` 让未来的「JD 分析卡片」「面试卡片」直接复用，不用再改表。

`payload_json` 内容：

```json
{
  "kind": "resume",
  "generation_id": "rg_3f9a2c81b0d4e7aa",
  "title": "AI 应用开发工程师 · 第 2 版",
  "meta_line": "A4 单栏 · 1,033 字 · 4 处待核对",
  "warnings_count": 0,
  "missing_count": 4,
  "version": 2,
  "created_at": "2026-10-18T16:34:54.023113"
}
```

设计约束：
- **只存 `generation_id`，不存 `html_url`**。URL 由详情接口按当前文件名生成，避免消息里躺着
  一个文件换了就 404 的死链接。
- 其余字段是**写入时快照**，供消息流直接渲染，不必为每条消息多发一次请求
  （消息列表是高频接口，N+1 不可接受）。重新生成产生新消息，不存在过期问题。
- `meta_line` 用「A4 单栏 · N 字」而不是「一页 A4」：页数没实测就不能写死。

### 2.3 不做在线 schema 变更

项目没有 Alembic（`mysql_base.py:81` 只有 `Base.metadata.create_all`），原计划补一个
`ensure_columns` 幂等补列工具。改用独立表后**这次不需要任何 DDL**，该工具也没实现——
不留下没有调用方的迁移代码。将来真要给存量表加列时再补，届时同样要注意
「ORML 模型一旦声明该列，所有 SELECT 都会带上它」这个约束。

## 3. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/resume/generate` | **改造**：生成 → 落库 → 写 2 条消息 → 返回 `generation_id` / `html_url` / `version` |
| GET | `/api/v1/resume/generations?conversation_id=` | 列表（不含 `data_json`/`html`），侧栏树与历史切换用 |
| GET | `/api/v1/resume/generations/{generation_id}` | 详情（含 `data` 与 `html`；HTML 缺失时自愈重渲染） |
| POST | `/api/v1/resume/generations/{generation_id}/regenerate` | 改 `extra_fields` → 重渲染，**0 次 LLM**，用于「补上学长名再出一版」 |
| DELETE | `/api/v1/resume/generations/{generation_id}` | 删除单版（消息同步删，避免死链卡片） |

`generate` 响应在原 P1 字段上追加：`generation_id`、`version`、`html_url`、`created_at`。
前端 P1 已依赖 `data` / `warnings` / `missing` / `html` / `stages`，**全部保留**，向后兼容。

### 消息写入

在 `ConversationStoreService` 新增 `append_resume_pair(conversation_id, generation)`，
复用现有 `append_message_pair` 里「message_count + 2 / last_message_preview / 首次自动改名」
那段逻辑（抽成私有 `_append_pair` 供两者调用，不复制）：

- user 消息：`生成简历（目标岗位：AI 应用开发工程师）`
- assistant 消息：一句人话 + meta 卡片载荷
  > 已按「AI 应用开发工程师」重排完成，一页 A4。有 2 处数字在原文里找不到出处、
  > 1 个字段缺值，已在下方卡片标出，核对后可重新生成一版。

失败不写消息（避免会话里留一条「正在生成」的僵尸记录）。

## 4. 嵌套与视图链路

```
点「生成简历」
  → POST /resume/generate（落库 + 写消息）
  → 前端 resumeGen.generate() 拿到 generation_id
  → conv.refreshDetail()          # 让新消息出现在对话流
  → conv.selectNode('resume', cid, generation_id)
```

**主区**：`Workspace.vue:147` 已有 `activeType === 'resume'` 分支，只需把 `activeNodeId`
从空串改为 `generation_id`，`ResumeGenerateView` 挂载时若 `activeNodeId` 有值则
`resumeGen.open(id)` 拉详情，否则显示空态。

**对话流内卡片**：新增 `components/chat/ResumeCard.vue`，在 `MessageItem.vue` 里以
`v-if="message.meta?.kind === 'resume'"` 渲染在 `FileCards` 上方。卡片内容：

```
┌──────────────────────────────────────────┐
│ [简历]  AI 应用开发工程师 · 第 2 版        │
│ 一页 A4 · 1,043 字 · 2 处待核对            │
│                      [打开预览]  [下载]    │
└──────────────────────────────────────────┘
```

- 「打开预览」→ `conv.selectNode('resume', cid, generation_id)`，卡片内直接用 store
  （`StartGenerateForm.vue` 已有组件内直接用 store 的先例，不必为一次点击改 4 层 emit 链）。
- 「下载」→ 先取详情拿 `html_url`，再走 `<a download>`。不在 `meta` 里存死链。

**侧栏树第四组**：`ConversationList.vue` 的 `GROUPS` 加 `{ key: 'rg', icon: 'file', label: '简历' }`，
计数来自 `_attach_tree_badges` 再加一条 GROUP BY（与现有三类同构，仍是 4 条聚合查询，无 N+1）。

**降级**：老消息 `meta` 为 NULL，`MessageItem` 走原渲染路径，零影响。

## 5. HTML 自愈

`html_filename` 指向 `generated_docs/resume_<时间戳>_<hex>.html`。该目录在 `.gitignore` 里、
部署时是可写运行时目录，**存在被清理的可能**（换机器、清缓存、容器重建）。

详情接口逻辑：
1. `generated_docs/<html_filename>` 存在 → 直接读；
2. 不存在 → 用 `data_json` 重渲染 → **回写文件 + 更新 `html_filename`/`html_chars`** → 返回。

于是「消息卡片点了 404」这类问题在服务端就地消化，前端无感。这也是当初选「JSON 为真相、
HTML 为派生物」的主要理由。

## 6. 级联删除

`delete_conversation`（`conversation_store_service.py:325`）里补一行
`sql_delete(ResumeGeneration).where(conversation_id == ...)`，与现有 4 张表同事务。

**注意**：`persist_html` 现在的文件名是 `resume_<时间戳>_<hex6>`（`resume_generation_service.py:376`），
**不含 conversation_id**，无法按前缀批量删。所以路由层清理文件时要走
「先查该会话所有 `html_filename`，再逐个删」——这是本次必须一起改的点，否则删会话会留孤儿文件。

## 9. 风险与取舍

| 风险 | 处理 |
|---|---|
| 补列需 DDL 权限，失败会让 meta 写不进去 | 启动只告警不阻断；写入降级为无 meta 消息；`meta` 缺失时卡片退化为 markdown 摘要 |
| `meta` 与 `data_json` 双份摘要字段可能不一致 | meta 只在写入时快照一次；数据变更一律产生新 generation，不存在改旧记录 |
| `data_json` 膨胀 | 单条 6–10KB，LONGTEXT 足够；列表接口不返回该字段 |
| 消息流里出现程序化 user 消息，会进模型上下文 | 文案带明确前缀「生成简历（…）」，语义清晰；若实测发现模型被带偏，可给 messages 加 `visible_only` 标记（本次不做） |
| 文件孤儿 | 删除会话按 `html_filename` 精确删；不做目录扫描（会误删其它会话产物） |

**不做的事**（避免范围膨胀）：
- 不做简历在线编辑（改字段重渲染已能覆盖 80% 场景，真编辑属 P3）
- 不做 PDF 后端生成（P1 已定浏览器打印）
- 不做多模板（P1 已定只做 ASu 单栏）
- 不动对话链路的 `load_skill` 路径

### 实测（真实 3 年 AI 应用简历 + 腾讯企业微信 JD）

| 指标 | 结果 |
|---|---|
| 首次生成 | 18.44s（抽取 17.23s），落库 1 条，会话新增 2 条消息 |
| 补字段重渲染 | **0.63s**（HTTP 1.37s），0 次 LLM，产出版本 2 |
| `missing` 收敛 | 4 项 → 补「学校名称/专业名称」后剩 2 项（自动摘除已补齐项） |
| HTML 自愈 | 删文件后详情接口重建出 **7196 字符（与原文完全一致）**，回写新文件名，二次读取不再重建 |
| 前端冒烟 | 侧栏四组「面试4 / JD 分析1 / 项目优化1 / 简历2」→ 卡片（第 2 版）→ 预览 → **刷新后卡片仍在** |
| 单测 | **272 passed**（P1 的 256 + 本次 16） |

### 实施中踩到并修掉的两个静默错误

1. **`stores/chat.js` 把消息压成 `{role, content}`**，`meta` 在进入视图前就被丢掉 →
   卡片永远不渲染，但接口和 DOM 都"看起来正常"（消息文字是对的）。
   修法：映射时保留 `meta`。
2. **`refreshDetail()` 会把 `activeType` 切回 `conversation`**。生成后用它刷新消息，
   会把刚跳过去的简历预览弹回聊天视图。新增 `refreshMessages()`：只重拉 `detail`，
   不动视图状态。

### 与方案的两处偏差（已在上文修正）

- 消息载荷从「加列」改为「独立表」，理由见 §2.2 的实施变更说明。
- 卡片 `meta_line` 不写「一页 A4」而写「A4 单栏」：页数没在生成时实测过，不能写死。

### 遗留（P3 候选）

- 没有「删除单版」接口（用户没提，且要同步删消息对，收益低）。
  会话整体删除时的级联已覆盖。
- 补字段只支持姓名/学校/专业/学历/毕业时间/手机/邮箱/城市/目标岗位；
  其余 `missing` 项会在生成后提示「需手动编辑」。
- 版本之间没有 diff 对比（两版并列可看，但看不出"这版改了什么"）。
