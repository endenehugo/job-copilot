## 三、项目亮点（可直接替换简历）

**项目：AI 求职助手平台（个人项目）** — FastAPI · SQLAlchemy 2.0 · MySQL · SSE · Pytest · Vue3

- **分层架构与 API 工程化：** Flask 原型在功能扩张后路由与业务耦合、错误格式不一；主导迁移为 FastAPI 四层架构（路由 / Pydantic Schema / Service / Repository），统一响应信封与全局异常处理器，安全校验（路径穿越防护、上传白名单、20MB 限制）收敛在路由层；结果：8 组路由全链路接入统一契约，新增模块零胶水代码，37 项端到端 API 测试守护迁移不回归。

- **数据库事务与一致性治理：** 迁移中通过双端口对照冒烟与代码审读发现两个潜伏缺陷——SQLAlchemy 2.0 autobegin 语义使旧上传接口持续 500 而功能表面正常（SQLite 内存库最小实验确认为确定行为）、面试问答只 flush 不 commit 导致数据从未持久化；据此建立显式事务边界规范：读写合并单事务、外部调用移出事务防连接池耗尽、消息成对原子写入、摘要水位线带乐观锁（仅前进才更新），删除走"先 DB 后文件"的最终一致顺序；结果：接口响应码正确、写后可回读验证，并发版本号分配获得原子性。

- **流式接口与延迟优化：** 单请求内十余次串行外部调用导致首字节 15~30s；通过耗时结构分析定位首因，实施三项动作（重排由 N 次串行调用改单次、校验移出关键路径异步补发、历史摘要改增量持久化），首字节降至 **3.7s**；自研 SSE 事件协议（meta→delta→tool_status→sources→done→verification），处理"SSE 已开始无法改状态码（错误走自定义事件）"与 Nginx 缓冲（X-Accel-Buffering）两个工程边界，事件顺序写入专项单测。

- **外部依赖可靠性治理：** 外部 SDK 超时配置深藏、默认重试 10 次 × 300s 导致最坏 50 分钟等待；将 13 处散装构造收口为统一工厂单例（lru_cache），超时分层（流式 180s / 普通 60s）、重试压至 2 次，并实现故障码驱动的自动降级链（粘性切换、限流不降级、流式仅首分片前可安全切换）；设计 degraded/warnings 降级信封贯穿 Service、API、SSE 三层——降级但可用，且让用户知道打了折。

- **测试体系与可维护性：** 155 项 pytest 全部离线零网络：mock 底层 SDK 精确驱动故障路径（降级链调用序列、粘性保持、流式中途异常）、确定性假向量让检索层可离线断言、把"SSE 事件顺序""未验证不报低风险""缺评分不伪造 0 分"等行为契约做成专项回归——测试的不是"功能能否运行"，而是"故障时行为是否正确"。

## 六、后端面试官可能追问（预埋应答方向）

- **"为什么用 FastAPI 不继续用 Flask？"** → 校验（Pydantic 原生）、自动文档、依赖注入、async 生态；迁移收益是契约统一而非框架本身。
- **"sync 路由在 FastAPI 里怎么跑的？"** → 线程池执行；数据库/外部调用是同步库，刻意保持 sync 避免全链路 async 改造，代价与演进方向能说清。
- **"乐观锁为什么不用 SELECT FOR UPDATE？"** → 冲突率极低（水位线回退只在并发窗口出现），版本比较写回足够且不持锁；悲观锁的收益配不上复杂度。
- **"SSE 断线怎么办？"** → EventSource 自动重连 + meta 事件带会话状态，前端按 id 对齐；当前为单机内存态，分布式需引入消息回放。
- **"水平扩展怎么做？"** → 主动交代 workers=1 的原因（BM25/FAISS 进程内缓存），三层演进：检索独立服务 / Redis 版本号失效 / 索引落盘。
- **"为什么不用 Celery？"** → 当前任务同步链路 + 单机部署，无跨进程任务分发需求；引入队列是过度设计，真需要时会先拆检索服务。
