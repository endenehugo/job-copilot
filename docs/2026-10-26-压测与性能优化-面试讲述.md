# 压测与性能优化 · 面试讲述

> 一句话开场：**我给这个项目做了一套请求级分段计时，然后用它把三个"说不清慢在哪"的场景全部拆开，
> 各降了 26%~75%。** 中途有两次我凭直觉给出的判断被自己的数据否掉——这可能是更值得讲的部分。

## 一、问题：能测到慢，但不知道慢在哪

线上演示站，用户反馈"有时候要等十几秒"。已有的压测只能给出端到端数字：

> memory 模式 P50 2.6s、P95 7.7s；RAG 8.4s；Agent 22.6s

分位数能看，**但拆不开**。RAG 的 8.4 秒里，检索多久、模型多久、校验多久？不知道。
不知道就没法优化——只能改一处、压一轮、看总数字动没动，一次迭代半小时。

## 二、观测：先建分段计时，再谈优化

**请求级 trace，ContextVar 驱动**：没有 trace 时所有 span 是空操作，正常请求零开销。

阶段粒度按代码真实分层：`db` / `init` / `compress` / `retrieve` / `answer` / `agent` / `tool` / `verify`，
`llm` 单独汇总所有模型调用。

两个出口，用途不同：

- **每请求一行 PERF JSON 进 journal**（默认开，无额外请求开销）——查线上个案
- **`Server-Timing` 响应头**（默认关，压测时开）——批量采集，逐请求落 CSV

**一个设计上花了心思的地方**：`rerank` 是 `retrieve` 的子阶段，如果都算进顶层，两者相加会重复计算。
所以顶层阶段保证**互不重叠**（相加 ≤ total），被包住的单独进 `substages` 并标 `desc="of:sub"`。
第一版上线时还踩了一个坑：`retrieve.conversation` 和 `retrieve` 同名，响应头里出现两次，
解析时后者把前者覆盖了——`retrieve` 的真实值 30.7ms 被写成 10.2ms。
这种错如果只看总耗时，永远发现不了。

## 三、定位：一次意外，两次假设被否

这一段是核心。前两条是"建好观测后，它直接告诉了我没想到的地方"；
第三条是**我先下了判断、准备动手，查完数据发现判断是错的**。

| 场景 | 预期 / 我的假设 | 实测结果 | 真正的瓶颈 |
|---|---|---|---|
| memory | 预期是"模型慢"或"检索慢" | `answer` 三轮稳定，`compress` 从第 8 次起每轮触发 | **历史压缩**，占 37% |
| RAG | 假设：检索或重排慢 | `retrieve` 只占 3%（403ms） | **校验占 79%**，且那次 LLM 开着思考 |
| Agent | 假设：工具返回的 HTML 塞爆上下文 | 第 2 轮输入只比第 1 轮多 226 token | **输出 1600 token 的吐字时间** |

表里是三次定位，但性质不同：memory 那次是观测直接给出了答案（我原本以为会是模型本身）；
RAG 和 Agent 两次是我先给了假设、甚至想好了改法，被数据否掉。

第三个假设错得最有意思：我本来准备去截断工具返回的 HTML。查了才发现，`bind_tools` 的
schema 就有 4271 字符、第 1 轮输入 2875 token 全是 system prompt + 工具定义的固定开销，
工具结果只贡献 226 token。**照假设动手，改完什么都不会发生。**

### 校验那 11 秒是什么

PERF 日志里那条调用的 attrs：

```
verify 10912ms   in_tokens=226   out_tokens=1111
```

**输入 226 token，输出 1111。** 校验结果只是一段短 JSON，输出不该是输入的 5 倍——多出来的是思考过程。
本地对照 3 轮：开思考 11985ms / 1300 token，关思考 1562ms / 113 token，
`supported_claims` 判定结果完全一致。**7.7 倍，判定质量没变。**

顺着这条线扫了所有 `build_chat_llm` 调用点，发现 `enable_thinking=False` 只在 3 处传了，
校验和两处重排都漏了。这是**分段计时带来的第二个收益**：它不只告诉你哪里慢，还告诉你去哪找问题。

## 四、修复：四处，按投入产出比排

| 改动 | 内容 | 效果 |
|---|---|---|
| 校验/重排关思考 | 加 `enable_thinking=False` + `max_tokens` 兜底 | verify 11s → 1.2s |
| 压缩双水位 + 转后台 | 阈值 12 触发、压到 8；任务进单线程队列，本轮不等待 | 压缩触发 6 次 → 2 次，第 8 次请求 4.5s → 1.8s |
| 交付回答限长 | prompt 从"简短的交付说明"改成"一到两句、不超过 80 字" + 禁止项 | Agent P50 −26% |
| 小模型换档 | qwen3.8-flash → qwen3.7-flash（快 1.48x，官方价便宜 3~4 倍） | 后台压缩降到 835~927ms/次 |

第三条只有 5 行文案，换来 26%——**给模型的约束必须可执行**。「简短」「适当」这种词模型当不存在，
写「不超过 80 字、不要列清单、不要加粗小标题」它才照做。

## 五、复测：四个场景的最终水位

同参数、同配置，只带 `-Trace` 重跑：

| 场景 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| memory P50 / P95 | 2655 / 7656 ms | **2193 / 4328 ms** | −17% / −43% |
| memory 第 8 次请求 | 4887 / 4523 ms | **1783 / 1792 ms** | **−60%** |
| RAG | 13232 ms | **3329 ms** | **−75%** |
| Agent | 23692 ms | **17563 ms** | −26% |
| 轻接口吞吐 | 未测 | **70 RPS（P95 52ms）** | 新增结论 |

## 六、归因：哪些数字可信，哪些不能算我的

这一段是我觉得最该主动说的：

**P95 从 7656 降到 4328，不能全算优化的功劳。** `answer` 的 P95 在三轮里是
2929 → 3550 → **4217ms** 一路走高，`max` 从 3717 涨到 5200——主模型三轮都是同一个、配置没动，
**是上游在漂**。第三轮的 4328 里 `answer` 就贡献了 4217。

所以真正可信的证据是两个：

1. **同一位置的对比**：第 8 次请求（触发压缩那轮）4887 → 1783，三轮都复现
2. **结构性变化**：`compress` 占比 37% → 8% → 0%，`answer` 62% → 99%

**容量那部分的偏差也要主动声明**：压测脚本跑在服务器本机（直连 127.0.0.1，排除公网 RTT），
locust 自己吃 16~22% CPU，和被测服务抢同一颗 CPU。69-70 RPS 这个数字是**偏保守**的。

## 七、现在的瓶颈在哪（一句话回答）

**四个场景的瓶颈全部在上游模型，不在服务器。** 压测期间系统 CPU 均值 3~4%、swap 全程 0、
backend RSS 稳定 179MB。轻接口 100 RPS 时 backend 单核跑到 101%，而系统总 CPU 只有 67%——
说明瓶颈是**单 worker + GIL**，不是机器不够。

这条结论直接决定了下一步：加 worker 理论上能翻倍（另半颗核闲着），但 `bank_lock` 是进程内锁，
多 worker 会失去互斥、丢题回滚，得先改成 DB 行锁。**这个决定不是压测数字能给出的，得看数据一致性。**

## 附：可能的追问与回答

**Q：那 7 处漏配是你代码的问题吗？**
A：是。但值得说的是发现方式——分段计时上线后第一个请求就暴露了异常（`llm` 合计 6726ms > `total` 4338ms），
顺着查出一次调用被记了两次（`streaming=True` 的客户端在 `invoke()` 时内层走 `_stream`，两层都记），
修完再扫全部调用点，才发现思考开关只传了一部分。**没有这套观测，这几处会一直隐身。**

**Q：样本只有 3 次，分位数有意义吗？**
A：没有。3 次只能支撑"结构比例"，不能支撑分位数。我在报告里写明了这一点，
结论主要建立在"同位置对比"和"占比变化"上，这两个不受样本量影响。

**Q：换小模型为什么敢换？质量怎么保证的？**
A：只换**结构化任务**用的那一档（压缩/校验/重排），主模型没动。换之前跑了基准（5 个候选 × 3 轮）
和结构化冒烟（重排 JSON、校验判定各 5 轮，5/5 可解析）。另外淘汰了一个：`deepseek-v4.1-flash`
在关思考时正文恒为空——不测就上，会让所有小任务静默失效。

**Q：为什么不直接加 worker 提容量？**
A：能加，但代价不在性能上。`question_bank` 用进程内锁做读改写，多 worker 会失去互斥，
表现为丢题和游标回退。这是数据一致性问题，用性能收益换不划算，正确顺序是先改 DB 行锁。

**Q：压测报告里写的"两条路径被自己数据排除"，具体是什么？**
A：工具返回 HTML 塞爆上下文、工具内抽取输出过长。都是我先给的判断，查完数据都不成立
（前者只多 226 token，后者实测 820 token 而注释写 2500-3500、`max_tokens` 从来没跑满）。
价值在于**我没有在错误假设上改代码**——两条都先做了十分钟的诊断再决定不动。

**Q：这套观测本身有开销吗？**
A：有过一轮对比可以直接回答。分段计时上线前后，memory 模式的端到端数字在同一个区间
（P50 2.4~2.8s、P95 7.0~8.0s vs P50 2.66s、P95 7.66s），每请求多一行 JSON 日志、多记十来个 span，
影响在噪声内。另外 `Server-Timing` 默认关闭，不压测时连响应头都不发。
