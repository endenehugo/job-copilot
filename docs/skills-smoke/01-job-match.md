## 1. 岗位结论

**补充材料后投递**。RAG 全流程与大模型应用落地的证据链完整，是这份简历最强的一段；但 JD 把「精通 C++ + 3 年 Linux/Unix 后台」写成硬性条件，而简历是 Python/Go 栈，这是**真实缺口而非表达问题**，不能靠改简历解决。若团队实际接受 Python 栈（同 BG 的其他 AI 后台岗确实有 Python 版本），值得投；否则优先找 Python 后端的同方向岗位。

## 3. 硬性门槛

- **已满足**：1 年以上 AI 应用开发经验（3 年）；大模型应用落地（三个项目连续）。
- **未满足**：精通 C++（简历零证据）；3 年以上 Linux/Unix 后台开发（年限与 OS 均未写，按 2022.7 起算最多 3.3 年，勉强够但无证据）。
- **待确认**：学历专业；是否接受 Python/Go 栈替代 C++（该岗职责里 RAG 与模型调度是主体，C++ 更像团队既有栈要求）。

## 4. 优先补强（最多 5 项）

| 类型 | 动作 | 说明 |
|---|---|---|
| 补能力 | C++ 短期无法补 | 若真要投，只能靠「可迁移的后端能力 + 愿意转栈」在开场白里主动说明，不要虚构 |
| 调整表达 | 把项目二重写成「模型调用框架」 | 现有「限流降级 + 队列 + 缓存」本质就是调度框架，换成 JD 的语言 |
| 补证据 | 补 Linux 部署与排障事实 | 容器、日志、连接池、超时治理，任一条真实的都算 |
| 调整表达 | 简历顶部摘要对齐「AI 应用后台」 | 现在写的是「AI 应用开发」，未体现「后台/服务」 |
| 补证据 | 补一次可量化的调优对比 | 如切片策略调整前后 recall/准确率变化，避免只有终值 |

## 5. 投递策略

- **是否投**：补充材料后投递。前置动作是把第 4 节前四项做完，尤其第 2 项。
- **用哪版简历**：以本简历为底，摘要与项目二按「模型调用与调度」重写；不建议为这个岗单独编 C++ 经历。
- **需要确认**：① 是否强制 C++；② 团队是否已有 Python 侧 AI 后台；③ 岗位实际工作地（标题写成都/北京，页面 Location 写广州）。
- **优先级判断**：若同一 BG 有 Python 版 AI 后台岗，投那个的期望收益更高。
