## 二、任务清单

### T12 · Agent 工具阶段的过程可见性（A5 / B11 / B12）★ P0

**现状（已核实）**：
- 工具轮**无任何进度事件**（grep `tool_status` 0 匹配）。agent 模式 6 轮工具串行执行，每个工具本身是一次完整 LLM（JD 解析/评分/改写/面试），用户对着空气泡干等可达 1~2 分钟——这是现状下**最长的无反馈段**
- 工具轮耗尽 → `chain_output=""` → 兜底道歉字符串（`conversation_chat_service.py:149`、`:245` 两处）→ HTTP 200 + `success`。工具已落盘的文件在 `files` 里，但回答里没有链接，前端把它当正常回答渲染

**改法**：
1. 后端流式工具循环每次执行工具前 `yield {"event": "tool_status", "data": {"name": ..., "index": i, "total": n}}`
2. 轮次耗尽兜底道歉时，`done` 事件 data 附 `degraded: true, warnings: ["工具调用已达上限..."]`；非流式路径走第二批的信封 `degraded`
3. 前端 `chat.js` 处理 `tool_status` 事件 → `assistantMsg.toolStatus`；`MessageItem.vue` 渲染工具状态条（「正在调用 联网搜索 · 第 2/6 步」，流式结束后折叠为一行摘要）
4. 前端对 `done.degraded` 显示醒目提示（复用降级 toast 样式，但在气泡内）

**改动量**：后端 ~40 行 + 前端 ~60 行。**收益**：agent 模式从"黑盒干等"变"可见进度"，失败不再伪装成功。

### T13 · 前端并发与竞态（A28 / A27 / B30 竞态 / B27）P1

**现状（已核实）**：
- 全项目 `Promise.all` 仍为 0 匹配，7 处串行 await 瀑布流（如 `refreshDetail + resume.load` 互不依赖却串行）
- `Composer.vue` 多图 `for...of await` 串行上传，5 张图 5 次串行往返，且上传阶段无整体 loading
- `select()` 快速点 A→B 仍可能乱序渲染（T10 只做了流的中断，响应竞态未做序号保护）
- `sending` 置位仍在 `await conv.create()` 之后（`chat.js:91`），create 可达数秒，窗口内连点会重复发送

**改法**：
1. `select()` 加请求序号（`this._selectSeq`），过期响应丢弃
2. 7 处互不依赖的串行 await 改 `Promise.all`（逐处确认无隐式依赖）
3. 多图上传 `Promise.all` + 上传中禁用发送/显示 loading
4. `sending = true` 提前到函数第一行

**改动量**：~60 行，纯前端。**收益**：页面切换/上传/发送的即时反馈，消除竞态显示错乱。

### T14 · 面试健壮性（B17 / B18）P1

**现状（已核实）**：
- `api/interviews.py:266-276`：`next_question` 为空串仍返回 `action="continue"`、`question_index+1` → 前端渲染空白题目卡，面试**卡死**且状态仍"进行中"
- `:184-188`：`eval_result.get("score", 0)`、`.get("evaluation", "")` 裸兜底——LLM 返回缺字段时 0 分落库、评价空白，提示"回答已记录"

**改法**：
1. 空题分支：`next_question` 为空且 `next_action != "summary"` → 视为异常终止，返回 `action="summary"` + warnings（或明确 fail），保证面试总能落到总结态
2. 评价解析失败/缺字段：score 置 None + warnings（接入 degraded），不再伪造 0 分落库；前端「未评分」处理复用 T6d 的 JdPanel 模式
3. `_parse_response` 增加 normalize（对齐评分服务的校验风格）

**改动量**：后端 ~50 行 + 前端 ~15 行。**收益**：消除面试卡死与 0 分假数据。

### T15 · 导出功能接 UI（B10 / B41）P1

**现状（已核实）**：后端 3 个导出接口完整可用（`/export/analysis`、`/export/interview`、`/export/project-rewrite`），前端 `downloadMarkdown` 工具也已存在——但**三者的调用点全部为零**，用户找不到任何导出按钮。

**改法**：
1. `JdPanel`（分析结果区）、`InterviewSidebar`（总结区/历史项）、`RewritePanel`（优化结果区）各加一个「导出 Markdown」按钮
2. 调对应接口拿 markdown → `downloadMarkdown` 落盘
3. 顺带 B41：`export_service._safe_json_load` 失败时不再静默 `return []`，记 warning 并在导出内容里标注「（该项解析失败）」，与"真的没有"区分

**改动量**：~80 行。**收益**：补全最后一个"功能存在但不可达"的缺口。

### T16 · 索引增量更新（A12）P2

**现状（已核实）**：`rebuild_conversation_index` 每次上传对**全部文档**重新切分 + 重新 embedding（`FAISS.from_texts`），已付费的 embedding 重算一遍；好的一面是临时目录 + 原子替换已存在。

**改法**：
1. 新上传：加载现有索引（存在则 `FAISS.load_local`）→ 仅对新文档 chunk `add_texts` → 存临时目录原子替换；按 `document_id` 去重防止重复入库
2. 删除文档时才走全量重建（删除语义下增量成本更高）
3. BM25 缓存失效逻辑保留

**改动量**：~60 行 + 单测。**收益**：随文档数线性增长的上传耗时变为常数；当前会话规模（4~14 chunk）收益有限，故排 P2、放最后。

### T17 · 启动可见性与杂项加固（B16 / A22 / B23 / B46 / B29 / B31）P2

逐项小改，合一个 commit：

1. **B16/A22 启动可见性**：`/system/health` 响应附 `keys_ok`（复用已有 `check_all()`）；lifespan 启动时跑一次 `check_all()`，失败打 warning 日志。服务"健康但 Key 无效"不再无感

3. **B46 文档状态轮询**：`DocumentPanel` 上传后 pending 状态每 3s 轮询 `refreshDetail`，indexed/failed 即停，上限 10 次
4. **B29 长操作骨架**：JdPanel / RewritePanel / InterviewSidebar 的分析区加 `v-loading`（按钮转圈在折叠面板里看不见，主区必须有意図性反馈）
5. **B31 上传校验**：图片 10MB / 文档 20MB 上限 + 空文件检查，超限前端直接提示不走网络

**改动量**：~100 行散点。
