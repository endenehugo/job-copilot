# 模拟面试提速方案

> 结论先行：**能再快一个数量级，且不需要改架构**。当前慢的主因不是模型能力不够，而是三个可控开关：
> ①思考模式没关（评价类调用白跑 400–1300 token 的推理）；②出题在生成一份从没被用过的 `expected_points`（占出题输出的 70% 以上）；
> ③全程非流式，用户唯一能感知的是"转圈 18 秒"。
>
> 三项都处理掉：**单轮从 15.8–19.7s 降到首字 0.4s / 全文 1.8s；开始面试从 28.5s 降到首字 2.6s**。

## 1. 先看慢在哪（2026-10-18 实测）

测量方式：绕过 HTTP，直接用同一个 JD/简历（简历 2234 字）打 `build_chat_llm` 与百炼兼容端点，
每项一次调用，`temperature` 沿用服务里的 0.4/0.5。**单次实测，存在波动**，看量级别看小数。

### 1.1 单轮作答（评价 + 下一题，一次调用）

| 方案 | 耗时 | 完成 tokens | 备注 |
| --- | --- | --- | --- |
| 现状 · 默认思考 · qwen3.8-max | 16.8–19.7s | 701 | 其中推理约 985 字，用户看不到 |
| 现状 · 默认思考 · qwen3.8-flash | 15.8–17.3s | 888 | 推理 1324 字 |
| **关思考 · flash** | **3.67s** | **159** | 输出 314 字，内容质量与上面相当 |
| 关思考 · max | 4.46s | 147 | 输出 305 字 |
| 关思考 + 流式 · flash | 首字 **1.38s** / 全文 4.64s | — | 用户 1.4s 就开始读评价 |

### 1.2 只评价、不出下一题（配合"题库出题"，见 P2）

| 方案 | 耗时 | tokens |
| --- | --- | --- |
| 关思考 · 非流式 | 3.27s | 111（输出 219 字） |
| **关思考 + 流式** | 首字 **0.40s** / 全文 **1.81s** | — |

### 1.3 开始面试（出题）

| 方案 | 耗时 | tokens | 说明 |
| --- | --- | --- | --- |
| 现状（3–6 题 + `expected_points`）· 默认思考 | >180s（超时） | — | 偶发打满 60s 超时并触发重试 |

### 1.4 与上一轮基准的差异说明

`docs/2026-10-18-模块耗时实测.md` 里记录的是「开始 8.5s / 单轮 3.0–3.6s」，
这次同一接口测到 15.8–19.7s。差异不在代码，在**思考 token 的随机长度**：
同一段 prompt 的推理长度从几百到上千字浮动，耗时随之 3s↔17s 摆动，极端情况会撞超时（实测一次 182s）。
换句话说：**现在的慢是"随机慢"，不是"稳定慢"**，这比平均慢更难忍，也让复现和归因变难。

## 2. 根因三条

1. **思考模式没关**。`llm_factory` 里只有 model/temperature/top_p/timeout/retries，没有 `enable_thinking`。
   qwen3.8 这代在兼容模式端点默认开思考。评价、评分、出题都是"给定材料做结构化判断"，
   推理链对最终 200 字评价的边际贡献很低——实测关掉后输出长度 278→305 字，评分 86，判断不变。
2. **出题在造一份没人用的数据**。`INTERVIEW_START_SYSTEM_PROMPT` 要求每题带 `expected_points`（3–5 条），
   而 `_invoke_answer_llm` 从来没把 `expected_points` 传进评价 prompt；
   `questions[1:]` 也基本不会被使用（每轮的下一题由模型现生成 `follow_up`）。
   即：**每场面试开头花 20 秒生成 5 道题 + 25 条要点，实际只用了第 1 题**。
3. **全程非流式**。`/interview/answer` 返回完整 JSON 才算完成，前端只有一个 loading 态。
   用户的体感时长 = 模型全部输出时间，而不是首字时间。

## 3. 方案（按性价比排序，可分三次交付）

### P0 · 关思考 + 封顶输出（半天，风险最低）

改动：
- `app/core/llm_factory.py`：`build_chat_llm(..., enable_thinking: bool | None = None)`。
  兼容模式客户端走 `extra_body={"enable_thinking": False}`（`ChatOpenAI` 构造参数即可）；
  原生 `ChatTongyi` 链路不支持该参数，传了就忽略并记一次 info。**注意 `lru_cache` 的 key 必须带上新参数**，
  否则开关会串。
- `app/services/interview_simulation_service.py`：`_ensure_answer_llm` / `_ensure_start_llm` 传 `enable_thinking=False`，
  并加 `max_tokens`（评价 400、出题 800）——防止模型偶发自言自语把时长拖长。

收益：单轮 15.8–19.7s → **3.7–4.5s**；方差从 3–20s 收到 3–5s；token 从 888 降到 159（成本同时降 80%）。
风险：面试"总结"那一步建议**保留思考**（要综合全场表现），只对评价/评分/出题关。

### P1 · 砍无用输出 + 评价流式（1 天）

改动：
- 出题 prompt 去掉 `expected_points`，题数固定 3（或保留 5 但改为"先出第 1 题，其余后台补"）；
  若后续要恢复要点，改为**答完再用**时才生成，而不是开场一次性生成。
  → 开始面试 28.5s → **2.6s（先出第 1 题）** 或 **5.8s（3 题一次出）**。
- 新增 `POST /api/v1/interview/answer/stream`，事件序列：`evaluation`（流式文本）→ `score` → `question` → `done`。
  实现直接复用 `conversations.py` 里已验证的写法：`contextvars.copy_context()` + `run_in_threadpool` 驱动生成器，
  不要用 `iterate_in_threadpool`（`__next__` 每次新 context，ContextVar 的 token 无法复位）。
- 前端 `stores/interview.js` 加 `submitAnswerStream()`（复用 `utils/sse.js` 的 `postSse`），
  `InterviewView` 把评价按增量追加，评价完再显示"下一题生成中"。

收益：单轮用户可感知等待 **3.7s → 1.4s 首字**（只评价 + 流式时是 0.4s / 1.8s 全文）。
风险：本来是"一次调用出评价+下一题"的原子返回，拆流后落库时机要重新安排
（建议：评价流完先落评价，题目生成后再落题目并更新 `round_count`；中途断流时面试仍可继续）。

### P2 · 把"题库"真正用起来（需产品决策，1–2 天）

现状是"生成了题库却不用"。改成：
- 开始面试生成 3–5 题的题库（无要点），每轮的下一题**按顺序从题库取**；
- 只有评分低于阈值（比如 < 60）或回答明显偏题时，才让模型现生成一个追问；
- 面试结束时一次性生成总结（保留思考）。

收益：单轮从"评价+出题"变成"只评价"，**首字 0.40s / 全文 1.81s**；题目难度可预期，用户还能在开始前预览题库。
代价：从"完全自适应追问"变成"题库为主 + 低分追问"。**这一档要不要做，需要你拍板**——
如果面试的产品定位是"练真实追问"，那 P1 就到顶；如果是"高效刷题 + 稳定评分"，P2 更值。

## 4. 预期总账

| 环节 | 现在 | P0 | P0+P1 | P0+P1+P2 |
| --- | --- | --- | --- | --- |
| 开始面试（首屏有题） | 8.5–28.5s | 8.5–28.5s | **2.6s** | 2.6s |
| 单轮：提交 → 看到评价首字 | 3.2–19.7s | 3.7s | **1.4s** | **0.4s** |
| 单轮：提交 → 拿到下一题 | 3.2–19.7s | 3.7s | 4.6s | 1.8s |
| 一场 5 轮的总感知等待 | ~100s+ | ~20s | ~8s | ~5s |

## 5. 不做的事（已排除）

- **换更小的模型**：flash 与 max 在关思考后差距只有 0.8s（3.67 vs 4.46），换模型不是杠杆，参数才是。
- **压缩输入**（比如只传简历摘要）：输入 2.2–3.6k 字，对耗时影响在百毫秒级；瓶颈在输出与思考。
- **加缓存**：每轮输入都不同（历史在增长），命中率低，收益远小于上面三项。

## 6. 怎么验证

1. `tools/bench_modules.mjs` 增加 `--interview-rounds=N`，记录每轮首字/全文/总耗时；
2. 对照表：同一 JD/简历/回答固定成 fixture，跑 P0 前后各 5 次，看 P50 与 P90（方差才是重点）；
3. 质量回归：同一组 5 条回答，比较关思考前后 `score` 与 `evaluation` 的人工盲评——目前一次抽样是 86 分、
   评价命中"事务/连接池/P95"三个要点，但样本太小，改之前应有 20 条以上的对照。
