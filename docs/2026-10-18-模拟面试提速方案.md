# 模拟面试提速方案

> 结论先行：**能再快一个数量级，且不需要改架构**。当前慢的主因不是模型能力不够，而是三个可控开关：
> ①思考模式没关（评价类调用白跑 400–1300 token 的推理）；②出题在生成一份从没被用过的 `expected_points`（占出题输出的 70% 以上）；
> ③全程非流式，用户唯一能感知的是"转圈 18 秒"。
>
> 三项都处理掉：**单轮从 15.8–19.7s 降到首字 0.4s / 全文 1.8s；开始面试从 28.5s 降到首字 2.6s**。

## 1. 先看慢在哪（2026-10-18 实测）

测量方式：绕过 HTTP，直接用同一个 JD/简历（简历 2234 字）打 `build_chat_llm` 与百炼兼容端点，
每项一次调用，`temperature` 沿用服务里的 0.4/0.5。**单次实测，存在波动**，看量级别看小数。

### 1.4 与上一轮基准的差异说明

`docs/2026-10-18-模块耗时实测.md` 里记录的是「开始 8.5s / 单轮 3.0–3.6s」，
这次同一接口测到 15.8–19.7s。差异不在代码，在**思考 token 的随机长度**：
同一段 prompt 的推理长度从几百到上千字浮动，耗时随之 3s↔17s 摆动，极端情况会撞超时（实测一次 182s）。
换句话说：**现在的慢是"随机慢"，不是"稳定慢"**，这比平均慢更难忍，也让复现和归因变难。

## 2. 根因三条

1. **思考模式没关**。`llm_factory` 里只有 model/temperature/top_p/timeout/retries，没有 `enable_thinking`。
   qwen3.8 这代在兼容模式端点默认开思考。评价、评分、出题都是"给定材料做结构化判断"，
   推理链对最终 200 字评价的边际贡献很低——实测关掉后输出长度 278→305 字，评分 86，判断不变。
2. **出题在造一份没人用的数据**。`INTERVIEW_START_SYSTEM_PROMPT` 要求每题带 `expected_points`（3–5 条），
   而 `_invoke_answer_llm` 从来没把 `expected_points` 传进评价 prompt；
   `questions[1:]` 也基本不会被使用（每轮的下一题由模型现生成 `follow_up`）。
   即：**每场面试开头花 20 秒生成 5 道题 + 25 条要点，实际只用了第 1 题**。
3. **全程非流式**。`/interview/answer` 返回完整 JSON 才算完成，前端只有一个 loading 态。
   用户的体感时长 = 模型全部输出时间，而不是首字时间。

## 3. 方案（按性价比排序，可分三次交付）

### P0 · 关思考 + 封顶输出（半天，风险最低）

改动：
- `app/core/llm_factory.py`：`build_chat_llm(..., enable_thinking: bool | None = None)`。
  兼容模式客户端走 `extra_body={"enable_thinking": False}`（`ChatOpenAI` 构造参数即可）；
  原生 `ChatTongyi` 链路不支持该参数，传了就忽略并记一次 info。**注意 `lru_cache` 的 key 必须带上新参数**，
  否则开关会串。
- `app/services/interview_simulation_service.py`：`_ensure_answer_llm` / `_ensure_start_llm` 传 `enable_thinking=False`，
  并加 `max_tokens`（评价 400、出题 800）——防止模型偶发自言自语把时长拖长。

收益：单轮 15.8–19.7s → **3.7–4.5s**；方差从 3–20s 收到 3–5s；token 从 888 降到 159（成本同时降 80%）。
风险：面试"总结"那一步建议**保留思考**（要综合全场表现），只对评价/评分/出题关。

### P1 · 砍无用输出 + 评价流式（1 天）

改动：
- 出题 prompt 去掉 `expected_points`，题数固定 3（或保留 5 但改为"先出第 1 题，其余后台补"）；
  若后续要恢复要点，改为**答完再用**时才生成，而不是开场一次性生成。
  → 开始面试 28.5s → **2.6s（先出第 1 题）** 或 **5.8s（3 题一次出）**。
- 新增 `POST /api/v1/interview/answer/stream`，事件序列：`evaluation`（流式文本）→ `score` → `question` → `done`。
  实现直接复用 `conversations.py` 里已验证的写法：`contextvars.copy_context()` + `run_in_threadpool` 驱动生成器，
  不要用 `iterate_in_threadpool`（`__next__` 每次新 context，ContextVar 的 token 无法复位）。
- 前端 `stores/interview.js` 加 `submitAnswerStream()`（复用 `utils/sse.js` 的 `postSse`），
  `InterviewView` 把评价按增量追加，评价完再显示"下一题生成中"。

收益：单轮用户可感知等待 **3.7s → 1.4s 首字**（只评价 + 流式时是 0.4s / 1.8s 全文）。
风险：本来是"一次调用出评价+下一题"的原子返回，拆流后落库时机要重新安排
（建议：评价流完先落评价，题目生成后再落题目并更新 `round_count`；中途断流时面试仍可继续）。

### P2 · 把"题库"真正用起来（需产品决策，1–2 天）

现状是"生成了题库却不用"。改成：
- 开始面试生成 3–5 题的题库（无要点），每轮的下一题**按顺序从题库取**；
- 只有评分低于阈值（比如 < 60）或回答明显偏题时，才让模型现生成一个追问；
- 面试结束时一次性生成总结（保留思考）。

收益：单轮从"评价+出题"变成"只评价"，**首字 0.40s / 全文 1.81s**；题目难度可预期，用户还能在开始前预览题库。
代价：从"完全自适应追问"变成"题库为主 + 低分追问"。**这一档要不要做，需要你拍板**——
如果面试的产品定位是"练真实追问"，那 P1 就到顶；如果是"高效刷题 + 稳定评分"，P2 更值。

## 5. 不做的事（已排除）

- **换更小的模型**：flash 与 max 在关思考后差距只有 0.8s（3.67 vs 4.46），换模型不是杠杆，参数才是。
- **压缩输入**（比如只传简历摘要）：输入 2.2–3.6k 字，对耗时影响在百毫秒级；瓶颈在输出与思考。
- **加缓存**：每轮输入都不同（历史在增长），命中率低，收益远小于上面三项。

## 6. 怎么验证

1. `tools/bench_modules.mjs` 增加 `--interview-rounds=N`，记录每轮首字/全文/总耗时；
2. 对照表：同一 JD/简历/回答固定成 fixture，跑 P0 前后各 5 次，看 P50 与 P90（方差才是重点）；
3. 质量回归：同一组 5 条回答，比较关思考前后 `score` 与 `evaluation` 的人工盲评——目前一次抽样是 86 分、
   评价命中"事务/连接池/P95"三个要点，但样本太小，改之前应有 20 条以上的对照。

## 7. P1 落地记录（2026-10-18）

P0 落地后（见 `0ecbd85`）单轮 1.99/2.29/2.80s，出题仍有 7.13s。P1 把这两处都收掉。

### 7.1 改了什么

**出题：只出第 1 题，去掉 `expected_points`**（`interview_simulation_service.py`）

原 prompt 要 3–6 题、每题 3–5 条参考要点，实测输出 1256 tokens；
而 `_invoke_answer_llm` 从来没把 `expected_points` 传进评价 prompt，
`questions[1:]` 也没人用（每轮的下一题是模型现生成的 `follow_up`）。
等于每场面试开头花 20 秒造一份只用第 1 行的题单。现在只出 1 题、不要要点，`max_tokens` 收到 500。

**评价：一次调用、流式增量解析**（新增 `POST /api/v1/interview/answer/stream`）

事件序列 `evaluation`（覆盖式全文，多次）→ `score` → `question`（summary 轮没有）→ `done`。

- 后端用 `llm.stream()` 累积 JSON 原文，每帧用 `extract_partial_string(raw, "evaluation")`
  从半截 JSON 里取出当前文本推下去，流结束后再整体 `parse_llm_json` 落库。
- 前端 `utils/sse.js` 的 `postSse` 复用，`stores/interview.js` 的 `submitAnswer` 改流式。

**为什么不是"评价与下一题分两次调用"**：那会把单轮变成两次串行 LLM 往返，
首字再快一点但拿到下一题更慢。一次调用的 JSON 本来就能边出边解析，
两次调用的拆分留给 P2（题库化之后下一题不需要模型生成）。

### 7.2 实测（`tools/bench_interview.mjs`，同一 JD/简历/固定回答）

| 环节 | 原始 | P0 后 | P1 后 |
| --- | --- | --- | --- |
| 开始面试（首屏有题） | 28.5s | 7.13s | **1.4–2.2s** |
| 单轮：提交 → 看到评价首字 | 3.2–19.7s | 1.99–2.80s（全文） | **0.5–1.2s** |
| 单轮：提交 → 拿到下一题 | 同上 | 同上 | **1.7–3.5s** |
| 一场 5 轮的感知等待 | ~100s+ | ~13s | **~5s**（首字口径） |

两轮各 3 次的原始记录：`开始 1.39/2.20/2.13s`，`首字 0.64/0.56/0.47s` 与 `0.89/0.98/1.16s`。
方差仍在（LLM 固有时延），但量级已经从"十几秒"压到"一秒级"。

UI 连拍（CDP，1440×900，每 600ms 一帧）：t=500ms 已出现"生成中"占位与自己的回答气泡，
t=1100ms 评价正文 98–149 字在滚，t=2600ms 变成实线气泡 + 65/68 分，题目换成第 2 轮。

### 7.3 三个实现要点

1. **delta 发覆盖式全文，不发增量片段**。丢帧不会缺字，前端直接赋值即可；
   增量拼接需要处理"乱序/重复帧"，收益只是每帧少几十字节，不值得。
2. **解析失败不落库**。`max_tokens` 截断时 `parse_llm_json` 抛错 → 后端发 `error` 事件，
   前端回滚占位条、把回答还给输入框并提示重试。把半截 JSON 猜成评价写进面试记录，
   比让用户重试一次严重得多。`extract_partial_string` 里还专门处理了跨 chunk 的
   `\uXXXX`（`"尾巴\u4e2` 这一帧先停在"尾巴"）。
3. **提交瞬间先插 pending 占位条**。否则从提交到 `done` 这几秒，用户只能看到输入框里
   一段被禁用的旧文本，分不清是提交成功还是在排队。占位条同时解决了"进行中看不到
   自己写了什么"——配合 `resumeSession` 从 `interview_messages` 重建 `answer` 字段，
   刷新后也能看到历史回答。

### 7.4 顺带修的两个既有问题

- **刷新后会话树里"暂无记录"**：分组展开状态存在 localStorage，数据不在，
  `onToggleAll` 又要先收起再展开才会 `loadSessions`。现在列表一到就为已展开的分组补一次懒加载。
- **进行中视图看不到自己的回答**：`rounds` 原先只存 evaluation/follow_up。

### 7.5 单元测试

`backend/tests/test_interview_stream.py` 13 项：半截 JSON 取字段（未闭合、转义、半截 `\u`、
`null`、相似 key）、delta 单调不回撤、list content 拼接、截断必须抛错、
落库时 `question_index` 推进、第 8 轮强制 summary。全量 **218 passed**。

## 8. P2 落地记录（2026-10-18）

P1 之后单轮首字已到 0.5–1.2s，但"拿到下一题"还要等模型把 `follow_up` 写完
（全文 1.7–3.5s），而且题目完全由模型即兴生成，难度和覆盖面都不可预期。
P2 把"出题"从每轮评价里拆出去，改成**题库为主 + 低分追问**。

### 8.1 关键取舍：题库不在开场生成

方案文档最初写的是"开始面试生成 3–5 题的题库"，但 P1 刚把开场从 28.5s 压到 1.4–2.2s，
再在开场同步生成 3 题会退回 5.8s 量级——等于把 P1 的收益还回去。

所以改成两段：
1. 开场只出 **1 题**（约 2s，用户马上看到题）；
2. 紧接着用 FastAPI `BackgroundTasks` **在后台补 3 题**（约 4.4–5.8s）。

后台补题的耗时用户感知不到，因为它正好落在"读题 + 打字"的窗口里。
实测后台补齐 4.36s，而用户提交第一轮普遍在 20s 之后——但即使手快也没问题，见 8.5 的降级。

### 8.2 数据结构

仍存在 `interview_sessions.initial_questions`（这一列本来就是"本场题单"），
P2 起换成带版本的对象，**同时兼容 P1 及更早的纯 list**：

```json
{"v": 2, "state": "pending|ready|failed", "cursor": 1, "questions": [{...}]}
```

- `cursor` = 已出题数，`questions[cursor]` 是下一题；
- 老场次（纯 list）解析成 `cursor = len`，即"已全部出过"，继续走追问兜底，
  升级后不会突然重问一遍老题；
- **游标坏了比丢题更危险**（越界会让同一道题被反复问），所以 `cursor` 非法时
  一律退化成 `len`；
- `interview/detail` 仍返回 `initial_questions` 列表（前端在用），另加
  `question_bank: {size, cursor, state}` 供调试与基准脚本轮询。

### 8.3 下一题的决策阶梯

`question_bank.plan_next_question`（纯函数，不碰数据库）：

1. 评分 < 60，或本轮未评分，或回答 < 20 字 → **现场追问**（不让题库吃掉这题）；
2. 否则按游标取题库下一题；
3. 题库用尽 / 还没补出来 → 现场追问；
4. 追问也失败 → 模型在评价里顺带给的 `follow_up`（P1 及更早的行为）；
5. 全都没有 → `_persist_answer` 把 continue 转成 summary 并告警（B18 的兜底搬到了这里）。

**追问不推进游标**：追问是"绕道"，问完仍回到题库的正常顺序。这也让
"答崩了会被追根问底、答得好就往前走"这两种体验可以共存。

### 8.4 并发：题库只由后台追加，游标只由作答推进

两个线程都会重写 `initial_questions` 整列（一个是追加题目，一个是推进游标），
用请求早先读到的快照写回去会互相覆盖——丢题、或者游标回退导致重复出题，
两种都不报错。

处理方式：
- 所有读改写都过 `question_bank.bank_lock`，且**读发生在写事务内部**
  （`_update_bank` / `_persist_answer`），拿到的永远是最新值；
- 后台补题只追加、不动 cursor；作答只改 cursor、不动题目列表；
- 锁在单进程内有效，**多 worker 部署会静默失效**（写入到注释里）。

### 8.5 降级路径（都实测过）

| 情况 | 行为 | 实测 |
| --- | --- | --- |
| 后台补题成功 | 后续轮次按题库顺序出题 | `source=bank`，下一题在评分后 0.4–0.5s 到达 |
| 用户手快，题库还是 pending | 本轮退回现场追问 | `--wait-bank=0`：`source=follow_up`，总耗时 3.55s（多 1.4s） |
| 补题失败（JSON 坏/额度） | 状态标 `failed`，之后每轮现场追问 | 单测覆盖 |
| 题库用尽 + 追问失败 | 模型自带的 `follow_up`，再没有就正常收尾 | 单测覆盖 |
| 老场次（纯 list） | 视为已出完，行为与 P1 完全一致 | 库里两个老场次实测解析为 `cursor == size` |

### 8.6 实测（`tools/bench_interview.mjs`，同一 JD/简历/固定回答）

| 环节 | P1 | P2 |
| --- | --- | --- |
| 开始面试（首屏有题） | 1.39–2.20s | **2.01–2.24s** |
| 后台补题库 | — | **4.36s（用户不可见）**，4 题 ready |
| 单轮：首字 | 0.47–1.16s | 0.88–1.02s |
| 单轮：评分出来 | 1.7–3.5s（全文） | 1.81–2.32s |
| 单轮：拿到下一题（题库轮） | 1.7–3.5s | **2.25 / 2.33s**（评分后 +0.4s） |
| 单轮：拿到下一题（追问轮） | — | 3.38s（多一次追问调用） |

单轮总量看起来只降了一点（2.3s vs 2.5s 量级），但结构变了：

- 评价不再生成题目，完成 token 从 ~160 降到 ~110；
- 题目来自预生成题库，**不再随模型即兴发挥**，难度与覆盖面可预期；
- 追问只发生在真正答崩的轮次，而且是"追着这次回答挖"，不是换一道新题。
