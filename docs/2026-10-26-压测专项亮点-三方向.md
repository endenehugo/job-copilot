# 压测专项亮点（三方向）

> 素材：2026-10-26 一天内完成的观测建设 + 三轮优化 + 容量测试。
> 三个方向的**事实相同、能力轴不同**：Agent 方向讲成本结构，后端方向讲可观测性与并发，全栈方向讲跨层决策。
> 所有数字出处见文末账本；测试数口径更新为 **399 项**（原 272 / 143 / 155 三处口径已过期）。

---

## 一、Agent 开发方向

**核心主张：Agent 的耗时可以被还原成「调用次数 × 每次输出 token」，不是黑盒。**

- **Agent 成本结构建模：** 为 ReAct 工具循环建立逐次调用核算——同一请求的 3 次模型调用（决策调工具 / 工具内结构化抽取 / 收尾回答）分别记录 in/out token 与实际耗时，得出"耗时 ≈ 输出 token ÷ 吐字速度（约 70 token/s）"的定量关系；据此判定输入侧（工具 schema 4271 字符 + system 提示）是固定成本、输出侧才是可优化项，**推翻了自己"工具返回的长文本塞爆上下文"的假设**（实测第 2 轮输入仅比第 1 轮多 226~465 token）。

- **Prompt 约束的可执行化：** 发现"回答要简短"这类模糊指令对模型无效（收尾轮仍输出 441~551 token 的文件名/格式/段落清单），改写为可执行约束——"一到两句、不超过 80 字"+ 三条禁止项（不列清单、不用加粗小标题、不复述正文）；结果收尾轮输出降至 181~411 token（均值 −41%），**Agent 端到端 P50 23.7s → 17.6s（−26%）**，且回答质量提升（改为主动指出简历缺失字段，比罗列文件属性更有用）。

- **上下文管理双策略：** 历史压缩从"单阈值兼作触发与目标"改为**双水位**（攒到 12 条触发、一次压到 8 条），把压缩频次从每轮一次降到每三~四轮一次；进一步将摘要生成移出问答关键路径——单线程后台队列 + 会话级去重，本轮直接带全量历史回答，摘要供下一轮使用，写库沿用摘要水位线的乐观锁（多进程失效也不会写回退）；压缩触发 6 次 → 2 次，触发那轮请求 4.5s → 1.8s。

- **结构化调用的思考开关：** 校验与检索重排的 LLM 调用未关闭思考模式，校验输入 226 token 却输出 1111 token；关闭后同一判定结果下 12.0s → 1.6s（**7.7×**），输出 token 降 92%。

## 二、Python 后端方向

**核心主张：把"慢"从主观感受变成可测量、可归因的事实，并且在优化时不破坏一致性。**

- **请求级分段计时的工程化：** 自研基于 ContextVar 的请求级 trace，无 trace 时全为空操作（正常请求零开销）；阶段粒度贴合代码真实分层（db / init / compress / retrieve / answer / agent / tool / verify），两个出口分工——每请求一行结构化日志进 journal（查线上个案）、`Server-Timing` 响应头（默认关闭，压测时开启批量采集）。关键设计：**顶层阶段保证互不重叠**（相加 ≤ total），被包住的子阶段单列并标记 `of:sub`，避免 `retrieve` 与其子阶段重复计算；上线即发现两处埋点缺陷（一次调用被记两次、同名子阶段覆盖父阶段真实值）。

- **并发引入而不破坏一致性：** 为把历史摘要移出关键路径，新增后台单线程队列——会话级去重避免重复提交，任务内部重新读取最新摘要与历史（而非沿用入队时的快照），写库复用既有的乐观锁（`until_id` 仅前进才更新）；**明确记录多 worker 部署下内存去重会失效，但乐观锁保证最坏只是重复计算、不会把水位写回退**；同时用硬上限（40 条）兜底用户连发场景，超过则退回同步压缩。

- **容量测试与瓶颈归因：** 将压测执行方从开发机搬到被测服务器本机（直连回环地址，排除公网 RTT），放开限速做四档梯度探测；结论——**吞吐天花板 69~70 RPS，瓶颈是单 worker + GIL 而非机器资源**（backend 单核 101% 时系统总 CPU 仅 67%，MySQL 25%、内存空闲 428MB、swap 0）；用"纯静态接口同时变慢"排除了 SQL 慢查询的可能。主动声明三项偏差：压测工具与被测服务抢同一颗 CPU（16~22%）、压测期间线上真实变慢、轻接口 RPS 不能描述 AI 场景容量。

- **优化决策的风险边界：** 面对"加 worker 可翻倍"的结论，未直接实施——指出面试题单使用进程内锁做读改写，多 worker 会失去互斥（丢题、游标回退），属数据一致性问题；正确顺序是先改数据库行锁再扩容。**用性能收益换一致性不划算**。

## 三、AI 全栈方向

**核心主张：跨「前端体验 / 后端实现 / 模型选型」三层做取舍，每一层都用数据说话。**

- **全链路耗时治理闭环：** 从"用户反馈有时要等十几秒"出发，建观测（请求级 trace + 服务器资源采样）→ 定位（四个场景各拆到阶段级）→ 修复（四处改动）→ 复测（同参数对比）→ 归因，形成完整闭环；结果 **memory P95 −43%、RAG −75%、Agent −26%，轻接口 70 RPS（P95 52ms）**。

- **非流式与流式的体验差异识别：** 发现压测走非流式接口会把"回答耗时"与"事后校验耗时"相加，而真实用户走流式——校验在 `done` 之后异步补发，用户实际感知延迟比压测数字低数倍；压测数据据此标注为"偏保守"，避免用错误的数字做产品决策。

- **模型选型的成本-性能双优化：** 对小模型档位做基准（5 个候选 × 3 轮 + 结构化输出冒烟 5 轮/项），选定比原档位**快 1.48×、官方单价低 3~4 倍**的模型，且重排 JSON 与校验判定的可解析率均为 5/5；同时淘汰一个"关闭思考后正文恒为空"的候选——**不测就上会让所有结构化任务静默失效**。

- **归因诚实度：** 主动区分"优化带来的降幅"与"上游模型漂移"，指出 P95 从 7.7s 降到 4.3s 中 `answer` 阶段自身在漂（三轮 2929 → 3550 → 4217ms），因此只把**同位置对比**（触发压缩那轮 4887 → 1783ms）与**结构性占比变化**（压缩 37% → 0%）作为可信证据，不把总降幅全记为优化收益。

## 五、三个方向的取舍建议

- **投 Agent 岗**：主推第一节的三条（成本结构建模、prompt 可执行化、上下文双策略），把"输出 token 决定耗时"作为核心洞察讲；RAG 与容量那部分略过。
- **投 Python 后端岗**：主推第二节（可观测性工程化、并发一致性、容量归因、风险边界），把 LLM 降级为"外部依赖"，别把主角让给模型调优。
- **投 AI 全栈岗**：主推第三节（闭环、非线性体验差异、模型选型、归因），强调"每一层都能自己动手且知道代价"。

**一个通用提醒**：这套材料的杀伤力在「发现手段」而不在「降了多少」——面试时先说怎么发现的（第一个请求就暴露了 `llm` 合计超过 `total`），再说改了什么。反过来讲容易变成"你的代码怎么有这么多问题"。
