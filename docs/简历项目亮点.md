## 一、项目经历（可直接替换简历）

### 求职助手 Agent 平台（Job Copilot）｜个人项目

**技术栈**：FastAPI · LangChain · Vue3 · FAISS/BM25 · SSE · MySQL · Pydantic

- **Agent 编排与工具容错**：自研 ReAct 工具编排循环（不依赖 LangGraph/AgentExecutor），编排 JD 解析、简历评分、项目改写、模拟面试等 **9 个可插拔工具**；System 提示只注入技能清单、模型按需加载完整 SOP（渐进式技能加载），避免 9 份长指南常驻上下文；工具错误以字符串回灌保证 tool_call/ToolMessage 一一对应，配合白名单查找与轮次耗尽优雅降级，工具异常不中断主链路。

- **会话级 RAG 检索与重排优化**：构建 FAISS 向量 + BM25 关键词混合检索与三级降级链路（会话私有索引 → 公共索引 → 内置知识库）；将重排由「逐篇串行 LLM 打分」重构为 **listwise 单次调用**，重排耗时 21.4s → 3.7s（**提速 5.8×**）。

- **SSE 流式与延迟治理**：实现流式问答事件序列（meta→delta→tool_status→sources→done→verification）；通过耗时结构分析定位「单条消息内串行 LLM 调用次数」为延迟首因，将幻觉验证移出关键路径异步补发、历史摘要改增量持久化 + 水位线，**首字节（TTFF）15~30s → 3.7s**。

- **LLM 输出治理与工程化**：后置归因幻觉验证（含量化数据的无支撑断言自动升级风险等级）、结构化输出逐字段 normalize（缺字段置「未评分」、不伪造 0 分）、degraded/warnings 降级可见化信封；将散落 **13 处**的 LLM 客户端收口为统一工厂单例，修复「默认重试 10 次 × 超时 300s」导致的**最坏 50 分钟等待（压至 2 分钟）**；建立 **pytest 143 项**用例，完成 Flask 单体 → FastAPI 分层（API/Schema/Service/Repository）架构迁移。

## 四、可能追问与应答要点

- **「你说是手写 ReAct，为什么不用 LangGraph？」** → 垂直场景工具数量可控、循环逻辑简单，手写能完全掌控消息序列与流式行为，也更省依赖；LangGraph 的收益在复杂分支与持久化状态机，本项目用不上。
- **「5.8× 怎么测的？」** → 在同一真实索引上跑三种策略（逐篇 / 批量打分 / listwise）对比，listwise 3.7s vs 逐篇 21.4s，Top-4 重合 0.71。**主动补一句**：批量打分有分数退化（模型都给相近分），所以最终选了 listwise。
- **「为什么否决 RRF？」** → 这是加分点：RRF 是业界经典零成本方案，但实测与 LLM 排序重合率仅 0.14~0.33，根因是中文按字切分的 BM25 本身召回质量差，融合坏信号得不到好结果。**方案被自己的数据否决**。
- **「TTFF 3.7s 是怎么降下来的？」** → 定位到延迟首因是串行 LLM 次数（检索+Rerank 最多 16 次串行），三项动作：Rerank 改单次调用；幻觉验证从关键路径移到 done 之后异步补发（省 ~15s）；历史摘要移出关键路径。
- **「143 项测试都测什么？」** → 含 SSE 事件顺序契约、降级信封、面试输出 normalize、索引增量、幻觉风险分级等专项回归。
