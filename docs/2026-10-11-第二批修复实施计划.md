## T6 · 降级可见化（本批核心）

### 为什么必须先做这个

`context_verification_service.py:189-195` 的异常分支返回空 claims → `_assess_risk` 里
`total=0` → `ratio=0.0` → `risk="low"`。前端 `SourcePanel.vue:7-8` 的 `RISK_CLASS[risk] || 'risk-low'`
把它渲染成**绿色徽章**。验证根本没跑成功，界面却主动告诉用户"这回答可信"。

逐个补 catch 打不完地鼠：`resume_scoring_service.py:89-105` 字段缺失一律填 0、0 分照样落库；
Rerank 失败降级 RRF 前端也毫不知情。这些的共同点是**协议层没有表达降级的字段**。

### 6a · 响应信封加 `degraded` / `warnings`

`backend/app/core/response.py`（全文 31 行）：

```python
def ok(data: Any = None, message: str = "", *, degraded: bool = False,
       warnings: list[str] | None = None) -> dict:
    body = {"code": "success", "message": message, "data": data if data is not None else {}}
    # 仅在真的降级时附加，保持正常响应干净
    if degraded or warnings:
        body["degraded"] = True
        body["warnings"] = [w for w in (warnings or []) if w]
    return body
```

**兼容性已核实**：前端拦截器（`client.js:31-39`）只判断 `'code' in body` 与 `body.code === 'success'`，
多字段不影响；后端测试只断言 `code` / `message` / `data`。34 处 `ok()` 调用点无需改动即可保持原行为。

### 6b · 前端拦截器统一提示（一次改动覆盖所有接口）

`client.js` 在 `if (body.code === 'success') return body` 之前插入：

```js
if (body.degraded || body.warnings?.length) {
  const text = (body.warnings || []).filter(Boolean).join('；') || '部分功能降级，结果可能不完整'
  ElMessage({ type: 'warning', message: text, duration: 6000 })
}
```

这样任何服务只要带上 `degraded`，前端自动提示，**不需要每个组件各写一遍**。

> 风险：若对高频接口（每次对话）都带 warnings 会变成提示轰炸。
> 约定：**只在真正影响结果可信度时打 degraded**，常规降级（如 Rerank 走 RRF）只记日志、不打标。

### 6c · 验证失败返回 `unknown`，前端不再 fallback 成绿色

**后端** `context_verification_service.py`：

- `:42-49`（无回答或无上下文的早返回）`hallucination_risk` 由 `"low"` 改为 `"unknown"`，
  `verification_detail` 改为"无回答或无上下文，未执行验证"。
- `:189-195`（`_llm_verify` 异常）返回值加 `"hallucination_risk": "unknown"`、
  `"verification_error": str(exc)`；`verify_answer` 需识别该字段，不再走 `_assess_risk`。
  实现建议：`_llm_verify` 返回的 dict 里带 `hallucination_risk` 时，`verify_answer` 直接采用，不覆盖。
- `hallucination_risk` 的合法值文档注释由 `"low" | "medium" | "high"` 补上 `"unknown"`。

**前端** `SourcePanel.vue:7-8, 24-25`：

```js
const RISK_CLASS = { low: 'risk-low', medium: 'risk-medium', high: 'risk-high', unknown: 'risk-unknown' }
const RISK_TEXT  = { low: '幻觉风险：低', medium: '幻觉风险：中', high: '幻觉风险：高', unknown: '未验证' }
```
- 去掉 `|| 'risk-low'` 的兜底（**这是把未知风险显示成绿色的直接原因**），改为 `|| 'risk-unknown'`；
- `RISK_TEXT` 同理兜底为 `'未验证'`，避免出现"绿色空徽章"；

**SSE 路径**：`conversation_chat_service.py` 的 `verification` 事件把后端验证结果原样下发即可，
6a/6b 的 SSE 侧提示由 `streamError` 之外的独立字段承载——建议在该事件里直接带 `degraded`，

## T9 · 流式 Markdown 渲染节流

`MessageItem.vue:8` `const html = computed(() => renderMarkdown(props.message.content))`
——每个 token 触发一次**全量** markdown 解析 + DOMPurify + `v-html` 整块替换。

**实测**（`markdown-it`，不含 DOMPurify 与重排）：

| 单次内容长度 | 单次渲染 |
|---|---|
| 1 440 字符 | 0.87 ms |
| 5 760 字符 | 2.20 ms |

| 流式最终长度 | 重渲染次数 | 累计 |
|---|---|---|
| 600 字符 | 200 次 | 23 ms |
| 3 000 字符 | 1 000 次 | **153 ms** |

**结论**：典型回答（3 千字）累积 153 ms 解析，加上消毒与重排约几百毫秒，摊到 15~20 秒的流式里
**不是主要卡顿源**，所以排 P2。但改法很便宜，顺手做掉：

- streaming 期间按 ~100 ms 节流渲染（或 `requestAnimationFrame`）；
- `streaming` 由 true 变 false 时**立即全量渲染一次**，保证最终内容与服务端一致；
- 长回答（>5 千字符）收益会明显变大。

## T10 · 请求可取消

`chat.js:113` 的 `fetch` **没有传 `signal`**，无 AbortController：

- 用户无法中断生成（长回答只能干等）；
- 切换会话/离开页面后旧流仍在跑（浪费 token 与后端线程）。

改动：

- `sendStream` 建 `AbortController`，`fetch(..., { signal })`，controller 存到 store；
- 切换会话（`conversation.select`）与组件卸载时 `abort()`；
- `Composer` 在 `sending` 时把发送按钮切成「停止生成」。

> 说明：abort 只作用于前端接收，**后端会继续生成并落库**（`append_message_pair` 在 `done` 前执行）。
> 用户之后切回该会话能看到完整回答，这是可接受行为，但要在按钮提示里说清是"停止接收"而非"撤销"。

## 建议不做：A13 与 A14

**A13 · 数据库索引 —— 无收益**

`conversations` 表现只有 **5 行**，`documents` / `interview_sessions` 同量级。
所有查询都按 `conversation_id` 过滤，而该字段是 `unique=True`（MySQL 自动建唯一索引）；
`list_recent` 是 `order by updated_at limit 50`，百行量级全表扫描与走索引无差别。
加索引属于过早优化，且会给未来迁移增加负担。**等会话量到千级再评估。**

**A14 · 路由改 async —— 现状更好，改了会更糟**

已核实：`api/` 下 **45 个 handler 全部是同步 `def`**，而 `services/` 下**没有任何 async 方法**
（`llm.invoke` 等都是同步阻塞调用）。

FastAPI/Starlette 会把同步 handler 放进 anyio 线程池（默认 40 线程）执行，**不阻塞事件循环**。
若把 handler 改成 `async def` 而 service 仍是同步阻塞，阻塞调用就会被搬到事件循环上——
**一个请求卡住所有请求**，比现状更差。正确的做法是 service 一起改成 async，或统一 `asyncio.to_thread`
包裹，成本高、收益在单用户场景为零。

唯一真实的问题是 SSE 生成器（`api/conversations.py:100` 的 `def generate()`）在整个流期间
占住一个线程池线程（20~40 秒）。单用户无影响；并发上来了再考虑用 `to_thread` 包裹或改 async generator。
