## 二、三方向定位（稳妥版 / 进取版）

**Python 后端实习生**

- 稳妥：能独立写完一条链路的后端实习生——FastAPI 四层分层、MySQL 事务边界、SSE 流式接口、外部依赖降级，330 项离线测试 + 3.5 万请求压测零失败兜底。
- 进取：把"慢"和"静默失败"当一等公民治理——用耗时结构分析定位瓶颈再动手（首字节 15~30s → 3.7s），用协议层降级信封代替各处 try/catch，**用远程 + 本机两轮压测把吞吐天花板定在 75 QPS 并把瓶颈实证到 CPU**，还修掉了压测工具自己"把静默失败判成成功"的盲区。

**Agent 应用开发实习生**

- 稳妥：手写过 ReAct 工具循环，做过混合检索 + 重排、技能按需加载、结构化输出治幻觉——不是调 LangChain 的 API 拼装工。
- 进取：知道 Agent 的质量问题大半出在**上下文**而不是提示词——内置方法论与用户真实经历必须分区、重排策略要用基准数据选、模型输出必须当不可信输入做 normalize 和归因校验。

**AI 全栈实习生**

- 稳妥：一个人交付了从 Vue3 界面到 FastAPI、到 MySQL、到域名 HTTPS 上线的完整周期，功能覆盖 RAG / Agent / 流式 / 简历生成，**并附一整套可复现的压测记录**。
- 进取：前后端一起治流式——前端占位气泡 + 场次 ID 比对防串写，后端事件协议 + contextvars 固定上下文；容量问题也不留给面试官猜——原始 CSV 和报告就在仓库里，可以现场打开。

## 三、Python 后端实习生（简历可直接用）

**项目：AI 求职助手平台（个人项目）** — FastAPI · SQLAlchemy 2.0 · MySQL · SSE · Pytest · Vue3

**简历顶部摘要（约 120 字）**

> Python 后端方向，主力栈 FastAPI / SQLAlchemy 2.0 / MySQL / Pytest。独立交付一个 AI 应用后端：53 个接口按四层架构组织，建立显式事务边界并修掉两个继承缺陷；SSE 流式链路首字节 15~30s 压到 3.7s；11 个模块的模型客户端收口为统一工厂，最坏等待 50 分钟 → 2 分钟；三轮压测 3.5 万请求零失败，瓶颈实证到 CPU，330 项离线单测覆盖故障路径。

**项目亮点（6 条，按"做了什么 → 系统能力 → 结果"排）**

- **分层架构与接口契约：** 接手一套 Flask 原型（路由与业务耦合、错误格式各异），重构为 FastAPI 四层——路由 / Pydantic Schema / Service / Repository，现有 12 个路由组、53 个接口、18 个 Service 与 13 个 Repository。统一 `{code, message, data}` 响应信封与全局异常处理，把路径穿越校验、扩展名白名单、20MB 上传上限收敛在路由层；新增模块不再写胶水代码，77 项端到端 API 测试守护契约不回归。
- **事务一致性与两个继承缺陷：** 重构冒烟时发现两处静默故障——SQLAlchemy 2.0 autobegin 语义让旧上传接口稳定 500（表面功能正常）、面试问答只 `flush` 不 `commit` 导致数据从未落盘。用 SQLite 内存库写最小复现实验确认行为后修复，并据此立规范：读写合并单事务、外部 LLM 调用移出事务防连接池耗尽、问答消息成对原子写入、摘要水位线用版本号乐观锁（仅前进才更新）、文件删除走"先 DB 后文件"的最终一致顺序。结果：接口状态码正确、写后可回读验证。
- **SSE 流式接口工程：** 自研六事件协议（meta→delta→thinking→tool_status→sources→done→verification），处理三个真实边界：① 流已开始就无法改 HTTP 状态码，错误改走自定义 `error` 事件；② 关 Nginx 缓存（`X-Accel-Buffering: no`）否则 token 攒到结束才吐；③ 同步生成器不能直接喂 `StreamingResponse`——`iterate_in_threadpool` 每次 `__next__` 新建 context 拷贝，ContextVar 的 set/reset 跨 context 会抛 `Token was created in a different Context`，改成 async 生成器 + `copy_context()` + `run_in_threadpool(ctx.run, ...)` 固定整条流。把"首字节"当指标后定位到真因是单条消息内串行 LLM 次数（检索 + 重排最多 16 次），三项动作把首字节从 15~30s 压到 **3.7s**。
- **外部依赖可靠性：** 原有 11 个模块各自 `new` 模型客户端，无一处设超时，而 SDK 默认重试 10 次 × 300s，单次最坏 50 分钟。收口为 `lru_cache` 单例工厂（裸构造 0 处），超时分层（流式 180s / 普通 60s）、重试压到 2 次，最坏等待降到 2 分钟；实现错误码驱动的粘性降级链——额度/欠费/无权限才降级，限流不降级（避免抖动导致永久降级），流式只在首分片前可安全切换；降级状态用 `degraded / warnings` 信封贯穿 Service、API、SSE 三层，**降级但可见**。
- **容量摸底与瓶颈归因（三轮压测，34,997 + 404 请求零失败）：** 远程与服务器本机各压一轮纯数据接口：服务端单请求 **27ms 中位**（本机回环），吞吐天花板 **~75 QPS**（远程与本机两次独立测量一致），拐点在 20 并发——之后加并发只涨延迟不涨吞吐。压测中抓服务器快照，40 并发时 **CPU 86.4% 占满、load 4.95 压在 2 核上**：瓶颈是 CPU，不是代码里那个 40 线程池（线程根本没排队）。另外发现并修掉压测工具自身的盲区——模型返回空时接口回 `success` + 人话兜底文案，不判失败的话错误率恒为 0 且 P95 反而变好；加了 `E_FALLBACK` / `E_EMPTY` 判定后，404 个 LLM 请求里静默失败为零。逐秒原始 CSV 与 locust 报告归档在仓库，可现场打开。
- **越权与数据隔离：** 用纯 ASGI 中间件签发 HMAC 签名访客令牌（HttpOnly，180 天），配合 `conversations.owner_key` 行级归属做数据隔离，子表靠 `conversation_id` 串联因而无需改表；空串代表历史数据、只对管理员可见，**零迁移脚本**。刻意不用 `BaseHTTPMiddleware`（它会包装 response body，对 SSE 有风险）；越权与"资源不存在"返回同一句文案 + 同一个 code——否则两者差异本身就是存在性探测器。写了 `scripts/check_isolation.py`：两个独立 cookie jar 交叉打 28 个端点，断言全部被拒且错误一致。

**可能追问（预埋）**

- *75 QPS 是不是太低了？* 这个数字要连着三个事实一起说：单机 2 核 1.6G；LLM 链路的瓶颈在模型侧不在服务端；纯数据接口 27ms 单请求。75 是这台机器的物理上限，不是代码问题——而"把天花板测出来并归因到 CPU"才是这轮压测的价值。
- *怎么证明瓶颈是 CPU 而不是线程池？* 40 并发时线程池 40 没满（40 个用户最多占 40 个线程，且都在工作），但 CPU 已 86.4%、load 4.95。如果是线程池排队，特征应该是吞吐被线程数限制而 CPU 空闲——实测相反。
- *同机压测不是会互相污染吗？* 会，服务器本机轮的 locust 自身占 23.6% CPU，高并发档延迟被抬高。所以结论只取两组独立测量一致的项（天花板、瓶颈），本机轮的高并发延迟不单独引用——两组数据各有偏差，交叉验证后剩下的才可信。
- *为什么不用 Celery？* 当前是同步链路 + 单机部署，没有跨进程任务分发需求；真需要时会先拆检索服务，而不是先上队列。
- *为什么乐观锁不用 `SELECT FOR UPDATE`？* 水位线回退只在并发窗口出现、冲突率极低，版本比较写回足够且不持锁。
- *水平扩展怎么做？* 主动交代 `workers=1` 的原因（BM25/FAISS 进程内缓存），结合压测结论给三层演进：检索独立服务 / Redis 版本号失效 / 索引落盘；75 QPS 的天花板在拆出检索服务后会先被 CPU 核数缓解。
- *两个缺陷怎么能发现？* 双端口对照冒烟 + 代码审读 + SQLite 内存库最小实验。重点讲"最小实验"这一步，实习生能讲出这个方法论比修了 bug 更值钱。

## 四、Agent 应用开发实习生

**项目：求职助手 Agent 平台（个人项目）** — FastAPI · LangChain · FAISS/BM25 · SSE · MySQL · Vue3

**简历顶部摘要（约 115 字）**

> Agent 应用方向，手写过 ReAct 工具编排循环（不用 LangGraph/AgentExecutor）。独立完成一个求职助手 Agent：10 个可插拔工具、9 个可渐进加载的技能、FAISS + BM25 混合检索与 listwise 重排、结构化输出治理与幻觉归因校验；用基准数据把重排从 21.4s 降到 3.7s，并用同一套数据否决了 RRF 方案。

**项目亮点（5 条）**

- **手写 ReAct 编排与工具容错：** 自研工具循环而非套 AgentExecutor——最多 6 轮，每轮执行前推 `tool_status` 事件（工具轮是非流式 `invoke`，实测静默 60~100 秒，不推事件前端就是"卡死"）；工具异常转字符串回灌模型，保证 `tool_call` / `ToolMessage` 一一对应不断链；工具名白名单查找，轮次耗尽走优雅降级而非抛错。当前 10 个工具（JD 解析、简历评分、项目改写、模拟面试、简历生成、文档导出、联网搜索、技能加载等）。
- **技能层与现实约束的对齐：** 9 个 SKILL.md 按"系统提示只给目录、模型判断匹配后 `load_skill` 取全文"的渐进式加载做，避免 9 份长指南（2.5k–15.7k 字符）常驻上下文；后加请求级注入——用户在输入框选定技能后，把指南直接插到 system 之后并禁止再调 `load_skill`，省一轮工具调用。踩过的坑：动态内容里的花括号必须转义（否则被当成 `ChatPromptTemplate` 变量，全请求报错）；`make-resume` 不能注入全文——它的流程与内置模板渲染规则冲突，走例外分支只指向生成工具。
- **混合检索与用数据选策略：** FAISS 向量 + BM25 关键词双路召回，三级降级（会话私有索引 → 公共索引 → 内置知识库）。重排从"逐篇串行 LLM 打分"重构为 listwise 单次调用，**21.4s → 3.7s（5.8×）**，Top-4 重合 0.71。同一套基准否决了 RRF 融合：与 LLM 排序重合率仅 0.14–0.33，根因是中文按字切分的 BM25 召回质量差，融合坏信号得不到好结果——**方案被自己的数据否决**，这比"我用了 RRF"更难编。
- **上下文污染治理（最有价值的一条）：** 内置知识库是通用方法论、用户上传的才是真实经历。原先无条件追加 Top-2 检索结果，导致模型把 Flask 文档当用户经历，简历里出现用户从没给过的"企业级 AI 智能问答平台"。改法：相关性阈值 0.55、简历类写作用任务**完全不注入**内置库、`_format_context` 分区标注来源；并且把 `similarity_search_with_relevance_scores` 的分数真读出来（旧代码 `getattr(doc, "score", 0)` 恒为 0，阈值等于没设）。
- **输出治理：不让模型直出成品。** 结构化输出走五级 JSON 解析 + 逐字段 normalize（缺评分置"未评分"，不伪造 0 分）；生成简历不让模型吐 HTML，先抽成约 1.5k token 的结构化 JSON 再走 Jinja2 固定模板渲染——相比直出 15–25k token 的 HTML，截断风险低一个量级，改字段可零 LLM 成本重渲染，链路耗时 220s → 21s；最后用**确定性规则**做审计（逐个数字回查原文，找不到出处就报警），比再调一次模型自查更可靠、零成本、可写单测。

**可能追问**

- *为什么不用 LangGraph？* 工具数量可控、循环逻辑简单，手写能完全掌控消息序列与流式行为；LangGraph 的收益在复杂分支与持久化状态机。
- *5.8× 怎么测的？* 同一真实索引跑三种策略：逐篇 21.4s / 批量打分 9.7s / listwise 3.7s。**批量打分虽然快但分数退化（模型给的分都挨得很近），所以没选它**——这句是加分点。
- *listwise 会不会漏掉排在后面的文档？* 会，Top-4 重合 0.71 意味着有约 3 成排序差异；但下游是生成不是检索评测，最终看的是回答可用性。
- *技能和代码里的业务模块重复吗？* 实测文本重合度 0.7%–1.4%，两套独立。`resume_generation_service` 是唯一"内置得对"的范式：运行时读 SKILL.md，11375 字符里只取 1770 字符的白名单小节。

## 五、AI 全栈实习生

**项目：AI 求职助手平台（个人项目）** — Vue 3 · FastAPI · MySQL · LangChain · SSE · Pytest · Nginx

**简历顶部摘要（约 120 字）**

> AI 全栈方向，主力栈 Vue3 / FastAPI / MySQL / LangChain。独立交付一个 AI 求职助手平台：ChatGPT 风格工作台（SSE 流式渲染、会话树、置顶、竞态治理）× 12,495 行后端 × 330 项离线测试，集成 RAG、Agent 工具编排、模拟面试、自动简历生成；三轮压测 3.5 万请求零失败并归档全部原始数据，Docker Compose + systemd + Nginx 部署到云服务器并配置域名 HTTPS。

**项目亮点（5 条）**

- **端到端独立交付：** 前端 Vue3 + Vite + Pinia（5,815 行、24 个组件、10 个 store，ChatGPT 风格工作台 + 会话父子树 + 主区多视图），后端 FastAPI 四层 53 个接口，MySQL 持久化，Docker Compose / systemd / Nginx 三件套部署，域名 + HTTPS 上线（含 ICP 备案与证书续期脚本）。功能覆盖简历与 JD 上传解析、会话级 RAG 问答、模拟面试、简历评分与改写、文档导出。
- **流式体验的前后端契约：** 后端六事件协议 + 前端按事件分派：提交瞬间出占位气泡、`done` 时按场次 ID 比对待写目标（防切换会话后串写）、失败回滚并把文本还给输入框；`AbortController` 同时承担"停止生成"与会话切换中断。首字节 15~~30s → 3.7s 是前后端一起做的：后端砍串行调用、前端在 `done` 就释放发送态（校验排在 `done` 之后还要再跑 5~~33s，等它等于让用户白等）。
- **越权隔离的全栈落地：** 后端 ASGI 中间件签发访客令牌 + `owner_key` 行级归属，前端配合做只读会话的展示降级（演示样本所有访客可见但不可写）、管理员视角的归属与时间展示；越权与不存在同文案同 code。用脚本而不是人肉点页面验收：两个 cookie jar 交叉打 28 个端点。
- **AI 功能全链路：** 10 个工具的可插拔工具循环、9 个可渐进加载技能、混合检索 + listwise 重排（21.4s → 3.7s）、模拟面试"题库为主 + 低分追问"（后台异步补题，用锁保护题单并发读改写）、自动简历生成（结构化抽取 + 固定模板，220s → 21s）。
- **把压测做成可审计的资产：** 三轮压测（远程两轮 + 服务器本机一轮）共 **34,997 个数据请求 + 404 个 LLM 请求，全部零失败**；逐秒原始采样 CSV、locust HTML 报告、口径说明（含"能证明什么 / 不能证明什么"清单）全部归档在仓库 `tools/loadtest/reports/`。压测脚本本身也是资产：探路、阶梯、按信封 code + 兜底文案判成败、自动清理压测会话，clone 下来十几分钟可复现。面试可以现场打开报告，而不是口头报数字。

**可能追问**

- *实习生做这么多，哪部分最接近生产标准？* 降级信封、事务边界、故障路径测试、越权隔离、压测归档是按生产标准做的；`workers=1` 的进程内缓存和无监控埋点是已知妥协。
- *前端最难的是什么？* 不是界面，是流式下的状态一致性：占位、串流、回滚、中断四件事，任何一件没对齐用户就会看到别人的答案或丢输入。
- *为什么把压测数据放进仓库？* 因为"报数字"和"给证据"是两个等级——数字可以被怀疑是背的，逐秒 CSV 加可复现脚本不能。

## 附：三条最容易被追问、也最能拉开差距的答题骨架

- **"你做过最难的 bug 是什么？"** → 不报"修了 500 错误"，报**观测错了入口**：简历工具一直"不生效"，逐项排除工具绑定、prompt、流式合并、历史干扰后，写下 `diag_stream.py` 直接调 service 逐事件打印，才发现工具 3.63s 就调了、错在工具内部而模型在圆场。教训：先确认你观测的链路和真实链路是同一段代码。
- **"怎么保证模型不说假话？"** → 三层：输入侧不喂污染（内置方法论与用户经历分区 + 简历写作不注入知识库）；输出侧逐字段 normalize（缺字段不伪造 0）；产出侧确定性审计（数字逐个回查原文）。外加一个正则兜底：模型声称生成了文件但 `files` 为空时，补一句真话。
- **"为什么选这个方案？"** → 一律先给数据再给结论，并主动交代被否决的方案（RRF、批量打分、LangGraph、Celery、`SELECT FOR UPDATE`）。五个"我试过但没选"比五个"我用了"更能证明判断力。压测也是同一个逻辑：75 QPS 的天花板、"瓶颈是 CPU"的结论、以及"还不知道 GIL 和 MySQL 各占多少"，三层都如实说。
