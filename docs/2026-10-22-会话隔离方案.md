# 会话隔离方案

- 日期：2026-10-22
- 用途约束：**面试时对外展示**（面试官点开链接就要能用）+ **可能作为毕业设计**（要讲得出设计）
- 状态：方案，未实施

---

## 一、先说结论

采用 **「签名访客令牌 + 行级归属」**，不做注册登录：

| 决策点 | 选择 | 一句话理由 |
| --- | --- | --- |
| 身份 | 后端签发 HMAC 签名的访客令牌，放 HttpOnly Cookie | 面试官零门槛，且不能靠改 localStorage 冒用别人 |
| 数据边界 | `conversations.owner_key` 一列，行级过滤 | 所有子表（消息/文档/分析/面试/简历）都靠 `conversation_id` 串起来，卡住父表就够了 |
| 老数据 | `owner_key` 为空 = legacy，**仅管理员可见** | 不写迁移脚本，语义自带向后兼容 |
| 演示内容 | 一组 `owner_key='demo'` 的只读样本会话，所有访客可见 | 面试官点进来不能是空侧边栏 |
| 管理员 | 现有 JWT，可见全部（含访客会话） | 反过来才对：你看得到访客来试用了，访客看不到你的测试记录 |

预计改动：后端 20 个点位 + 1 个中间件 + 1 张表的列，前端 4 个点位，测试 10 项左右。

## 二、现状（不是猜的，逐条对过代码）

| # | 现状 | 位置 | 后果 |
| --- | --- | --- | --- |
| 1 | `conversations` 表没有归属列 | `repositories/conversation_repository.py:11-26` | 数据层面没有任何隔离依据 |
| 2 | `list_recent` 不设条件，取全表 | `conversation_repository.py:40` | 侧边栏列出所有人（含你的开发会话） |
| 3 | `get_current_role` 无 token 一律返回 `user` | `core/security.py:75` | 访客与访客之间没有区别 |
| 4 | `GET /conversation/file/{filename}` 不校验归属 | `api/conversations.py:243` | 拿到 URL 就能下载他人简历（文件名不可枚举，属"知道才拿得到"的弱保护） |
| 5 | 导出接口按资源 id 直取 | `api/exports.py:14,23,33` | `analysis_id` 是自增整数，可以顺序猜 |
| 6 | `conversation_id` 形如 `conv_20261022145811_371a49` | `conversation_store_service.py:41` | 时间戳+6 位 hex，不可枚举（这点是好的） |

第 6 条值得单独说：**现有 ID 生成方式已经挡住了遍历式攻击**，所以真正的洞不是"猜 ID"，而是"列表全开" + "文件直下"。这也决定了方案不需要把 ID 换成 UUID，省一大块改造。

## 三、三个候选方案

### 方案 A：前端生成 UUID，请求头带 `X-Visitor-Id`

- 改动最小（一个中间件 + 一处过滤）
- **淘汰**：UUID 存在 localStorage，改一行 JS 就能切到别人的身份。答辩时这个问题答不上来——它叫"过滤"，不叫"隔离"。

### 方案 B：完整账号体系（注册 / 登录 / 会话）

- 设计上最"正统"，毕设章节最好写
- **淘汰**：面试展示场景下，让面试官先注册是自毁。而且这套东西与产品定位（一个给个人用的求职助手）不匹配，做出来是给答辩看的装饰。

### 方案 C（推荐）：签名访客令牌 + 行级归属

- 访客不需要做任何操作，打开就有身份
- 令牌由后端签发，篡改即失效
- 管理员用现有 JWT，一套代码两种角色
- 缺点：清 cookie / 换浏览器 = 换身份，旧会话找不到。**对这个产品可接受**（访客本来就是来试用的），而管理员的会话因为"可见全部"而永不失联

## 四、方案 C 详设

### 4.1 身份：签名令牌

```python
# core/security.py 新增，复用 AUTH_SECRET，用 audience 区分用途
def create_visitor_token(visitor_id: str) -> str:      # jwt: {sub: visitor_id, role: "visitor"}
def decode_visitor(token: str) -> str | None:          # 无效返回 None，不抛
```

用 JWT 而不是裸 HMAC：现有 `PyJWT` 已在依赖里，且能和 admin token 共用一套密钥与校验逻辑，不用再写一个签名协议。

**为什么放 HttpOnly Cookie 而不是 localStorage 或请求头**：
- HttpOnly 让前端 JS 读不到（XSS 拿不走）
- 同源请求自动携带，`fetch` 的 SSE 流也带，不用改前端每个请求
- 项目是同源部署（nginx 一个域名反代 `/api` 与静态资源），`SameSite=Lax` 足够，无跨域 cookie 的麻烦

### 4.2 签发时机：中间件懒签发

不在前端加"初始化"请求，避免多一个往返和"没初始化就调接口"的空窗：

```python
class VisitorMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        owner = decode_visitor(request.cookies.get(COOKIE_NAME))
        issued = owner is None
        owner = owner or f"v_{secrets.token_hex(12)}"
        request.state.owner_key = owner          # admin 由依赖层覆盖
        response = await call_next(request)
        if issued:
            response.set_cookie(COOKIE_NAME, create_visitor_token(owner),
                                httponly=True, samesite="lax", max_age=180*24*3600)
        return response
```

注意 `set_cookie` 必须在 `call_next` 之后、响应体开始流出前设置——SSE 的 `StreamingResponse` 在首帧写出时头就定死了，而这个位置正好在两者之间。

> 一处待验证：`BaseHTTPMiddleware` 对 `StreamingResponse` 的响应头追加在多数 Starlette 版本可用，但历史上出过 header 被重建的坑。落地的第一件事就是用 `curl -i` 打一次 `chat/stream`，确认响应头里有 `Set-Cookie`；如果没有，退化成一个显式的 `GET /api/v1/auth/visitor` 引导端点，前端启动时先调一次。两种实现后端逻辑相同，只差签发位置。

### 4.3 权限合并：管理员覆盖访客

```python
def get_owner_key(request: Request, role: str = Depends(get_current_role)) -> str:
    """返回当前请求的归属标识；管理员返回 ADMIN_OWNER（特殊值，查库时不过滤）。"""
    if role == "admin":
        return ADMIN_OWNER
    return getattr(request.state, "owner_key", "") or ""
```

两套身份不冲突：管理员浏览器里也有访客 cookie，但只要有 `X-Admin-Token` 就按管理员算。**写操作（建会话）走管理员身份时归属记 `admin`**，这样你在自己电脑上聊出来的会话不会跟访客混在一起。

### 4.4 数据层

`conversations` 加一列：

```python
owner_key: Mapped[str] = mapped_column(String(64), nullable=False, default="", index=True)
```

加列走已有的 `mysql_base._COLUMN_PATCHES`（启动时 `inspect().get_columns()` 比对后执行 DDL，幂等）。**不要写独立迁移脚本**——项目没有迁移框架，这是既定做法。

但要注意它的边界：`_COLUMN_PATCHES` 只比对**列**，模型上的 `index=True` 对已有表**不会生效**（`create_all` 只建新表）。所以索引必须写进同一条 DDL：

```python
_COLUMN_PATCHES = {
    "conversations": {
        "pinned_at": "ALTER TABLE conversations ADD COLUMN pinned_at DATETIME NULL",
        "owner_key": (
            "ALTER TABLE conversations "
            "ADD COLUMN owner_key VARCHAR(64) NOT NULL DEFAULT '', "
            "ADD INDEX idx_conversations_owner (owner_key)"
        ),
    },
}
```

MySQL 支持一条 `ALTER` 多个子句，这样列与索引一次补齐，仍然幂等（列已存在就整条跳过）。漏了索引不会报错，但列表查询会全表扫——访客多了才感觉得到，属于典型的"不报错但慢"，顺手补上。

`owner_key` 的三类取值：

| 值 | 含义 | 访客可见 | 管理员可见 |
| --- | --- | --- | --- |
| `""`（NULL） | 历史数据（10-22 之前的所有会话） | 否 | 是 |
| `admin` | 管理员自己建的 | 否 | 是 |
| `v_xxxxxxxx` | 某个访客 | 仅自己 | 是 |
| `demo` | 演示样本 | 是，只读 | 是 |

**关键设计：空串 = legacy 而不是写迁移脚本回填。** 查询条件天然是 `owner_key = :owner`，空串永远不匹配任何访客，等于"只对管理员可见"。省掉一次数据迁移，也让方案在任何一份历史备份上都成立。

### 4.5 授权三层，逐层收口

**第一层：列表过滤**

```python
def list_recent(session, owner_key, limit=50):   # owner_key=ADMIN 时不过滤
    stmt = select(Conversation)
    if owner_key != ADMIN_OWNER:
        stmt = stmt.where(Conversation.owner_key.in_([owner_key, DEMO_OWNER]))
```

**第二层：单会话校验**（新增一个函数，所有写路径首行调用）

```python
def assert_conversation_owner(conversation_id: str, owner_key: str) -> None:
    """不存在与无权访问返回同一种错误，避免枚举。"""
    entity = ...get_by_conversation_id(...)
    if entity is None or (owner_key != ADMIN_OWNER and entity.owner_key not in (owner_key, DEMO_OWNER)):
        raise ValueError("会话不存在")
```

调用点（这是主要工作量，约 15 处）：

| 文件 | 端点 | 说明 |
| --- | --- | --- |
| `api/conversations.py` | `create` / `detail` / `chat` / `chat/stream` / `delete` / `pin` | 6 |
| `api/conversations.py` | `image/upload` | 1 |
| `api/documents.py` | `upload` / `delete` | 2 |
| `api/jobs.py` | 分析 / 优化 / 列表 | 3 |
| `api/interviews.py` | 开始 / 作答 / 总结 / 列表 | 4 |
| `api/resumes.py` | 评分 / 版本列表 | 2 |
| `api/resume_generation.py` | generate / list / regenerate | 3 |

**第三层：按资源 id 直取的端点要回查**（容易被忘的一层）

`exports.py` 三个接口收到的是 `analysis_id` / `session_id` / `rewrite_id`，不经过 `conversation_id`。必须先 `SELECT conversation_id FROM ... WHERE id = ?`，再走第二层。同理 `resume_generation.py` 的 `GET /resume/generations/{generation_id}` 和 `regenerate`。

**这一层不做，前两层等于没做**——绕开父表直取子表是最常见的越权路径。

### 4.6 演示样本会话（面试场景的核心）

访客第一次进来侧边栏是空的，产品看不出价值。所以预置一组样本：

- 由你本地跑一遍完整链路（JD 分析 → 简历评分 → 模拟面试 → 生成简历），然后把这几条会话的 `owner_key` 改成 `demo`
- 列表里排在前面，带「演示」角标
- 可看全部内容（消息、文档、简历版本、面试问答）
- **写操作一律拒绝**：发消息、上传文档、删除、置顶、pin 都返回 `403 演示会话只读`
- 前端在只读会话里把输入框换成一句引导 + 「开始我自己的对话」按钮，不是弹错误

为什么不用"每个访客 clone 一份"：每份要复制 FAISS 索引（几百 KB）与索引目录，10 个访客就 10 份，还得做清理任务。只读样本零复制成本，且面试时"点开就能看到完整效果"这个诉求已经满足。

如果后续觉得"想聊但聊不了"体验不好，再上 fork：**在 demo 会话里发消息时，后端把该会话复制成访客自己的会话并重建索引，然后在新会话里继续**。这个模式通用（"体验账号 → 转正"），P2 再做。

### 4.7 文件下载

`GET /conversation/file/{filename}` 是**唯一不经过 conversation 的资源**，文件名不带会话信息。两条路：

- **P0 暂缓，接受现状**：文件名含时间戳 + 6 位随机，不可枚举；URL 只在会话内出现。写进方案文档的风险清单即可。
- **P1 签名 URL**：生成文件时把 URL 改成 `/conversation/file/<name>?t=<hmac(name + exp)>`，下载端点校签。无状态、不改目录结构、不需要知道归属。历史 URL 失效可接受（都是临时产物）。

推荐 P1 一起做——它只有 3 个生成点，成本远低于漏一个洞的代价。

### 4.8 前端改动（4 个点位）

1. `api/client.js`：`baseURL: '/api/v1'` 是相对路径，同源，cookie 自动携带，**不用改**
2. `stores/conversation.js`：列表项透传 `readonly` 标记
3. `components/sidebar/ConversationList.vue`：只读项隐藏「删除 / 重命名 / 置顶」，加「演示」角标
4. `components/chat/Composer.vue`：只读会话禁用发送，替换为引导按钮

`chat_stream` 用原生 `fetch`，同源默认带 cookie，无需额外传头。

## 五、验收：不靠人肉点，靠交叉脚本

漏端点是这类改造最常见的失败方式。写 `scripts/check_isolation.py`：

```
1. 用两个不同的 cookie jar 各建一个会话，各发一条消息
2. 枚举全部 15 个带 conversation_id 的端点 × 4 种攻击面：
   - 访客 A 拿 B 的 conversation_id
   - 访客 A 拿 demo 的 conversation_id 做写操作
   - 访客 A 拿 legacy（空 owner）的 conversation_id
   - 不带 cookie
3. 断言全部返回 4xx，且**错误信息与"不存在"一致**（不泄漏存在性）
4. 断言访客 A 的列表里只有自己的 + demo
```

这个脚本同时是毕设材料——"我如何证明隔离有效"比"我实现了隔离"更有说服力。

另外补 10 项单测：

- 建会话写入 `owner_key`
- 列表只返回自己的 + demo（管理员返回全部）
- 详情越权 → "会话不存在"
- 删除越权 → 同上，且数据未被删
- 发消息越权 → 同上
- 上传文档越权 → 同上
- demo 写操作 → 403
- exports 按 `analysis_id` 越权 → 拒绝
- 篡改 cookie → 视为新访客（不报错，也不给权限）
- legacy 会话访客不可见、管理员可见

## 七、这套设计在答辩里怎么讲

不是"我加了登录"，而是四个可讨论的点：

1. **无状态签名身份 vs 服务端 session 表**：本项目没有多端登录与主动登出的需求，签名令牌省掉了 session 存储与清理，代价是"无法即时吊销"。这个取舍要能讲清。
2. **行级归属 + 三层收口**：列表过滤 / 单资源校验 / 按 id 直取回查。第三层最容易被漏，也最能体现对越权路径的理解。
3. **空值语义承担兼容**：`owner_key = ""` 表示 legacy，靠查询条件天然隔离，避免了一次数据迁移——这是"用 schema 语义替代迁移脚本"的具体例子。
4. **只读样本 + 写入降级**：演示账号的通用模式，从"只读"到"fork 成自己的"是一条清晰的演进路径。

要准备的追问：**"cookie 丢了怎么办"**（答：访客态本来临时；管理员因可见全部而不失联）、**"能防伪造吗"**（答：HMAC 签名，改一个字节即失效）、**"为什么不加密钥"**（答：密钥在 env，且只存随机 ID 不含隐私）。

## 八、明确不做

- 不做注册登录（与产品定位冲突，且挡住面试官）
- 不做多租户组织/团队（无此需求，且会把 `owner_key` 变成一张表）
- 不做审计日志（访客量级不需要；管理员的"看到访客会话"已经满足观察需求）
- 不改 `conversation_id` 生成规则（现有时间戳+6 位 hex 已不可枚举，换 UUID 只增加改动面）

## 九、需要你确认的三件事

1. **老会话（现有 16 条，含 10-11~10-18 的开发验证）**：按本方案会变成 legacy，只有你登录后可见。要不要顺便删掉其中确认是废弃的那些？
2. **演示会话用哪几条链路**：建议「JD 分析 + 项目优化」一条、「模拟面试」一条、「简历生成」一条，覆盖三个最有说服力的模块。
3. **管理员是否要能看到访客会话**：本方案默认能看（便于你发现"有人在用"），如果你不想看到别人试用的记录，改成管理员也只过滤自己即可。
