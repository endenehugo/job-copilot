# 方案评审：JD 分析与项目优化迁移到会话记录（沿用模拟面试模式）

- 日期：2026-10-13
- 状态：已实施（2026-10-13 当天完成，174 项后端测试通过，前端构建通过，真实库冒烟通过）
- 前置：模拟面试已完成迁移（见同日评审文档），本方案复用其全部基础设施——`activeType/activeNodeId` 复合选中模型、树形会话列表、主区多视图、列表徽标聚合。

---

## 一、两个模块的现状与关键差异

| 项 | JD 分析 | 项目优化 |
|---|---|---|
| 侧边栏入口 | `JdPanel.vue`（🎯 JD 分析面板） | `RewritePanel.vue`（✏️ 项目优化面板） |
| 数据落库 | ✅ `job_analysis` 表，按 `conversation_id` 一对多，**每次分析存一条** | ❌ **完全不落库**，结果只存 Pinia 内存，刷新即丢 |
| 历史能力 | 后端 repository 有 `list_by_conversation_id`（limit 20）但**未暴露 API**；前端只显示最新一条 | 无任何历史概念 |
| API | `POST /job/analyze`、`GET /job/analysis/latest`、截图分析 | `POST /resume/project/rewrite`（纯函数式，返回即扔） |
| 删除 | 无 | 无 |
| 导出 | `GET /export/analysis?analysis_id=`（按记录导出，天然支持历史） | `POST /export/project-rewrite`（传结果对象导出） |
| 与面试的耦合 | `interview_sessions.job_analysis_id` 软引用分析记录；面试 start/answer 会取**最新**分析的 jd_text | 无 |

**结论**：
- JD 分析迁移是"顺水推舟"——数据天然一对多，只差暴露列表/详情/删除三个接口。
- **项目优化迁移有一个前置工程：必须先加持久化（新表）**，否则树里没有历史可挂。这是本方案最大的决策点。

---

## 二、统一改造模式（对齐面试模块的做法）

1. **父节点徽标**：`/conversation/list` 的聚合查询扩展，顺带统计 `analysis_count`、`rewrite_count`（同一条 GROUP BY 加两列，无额外请求成本）。
2. **子节点懒加载**：展开父节点时拉取子项摘要列表；子项点击 → 主区对应视图。
3. **主区多视图**：`activeType` 从 `'conversation' | 'interview'` 扩展为 `+ 'analysis' | 'rewrite'`；主区按类型切换 `AnalysisResultView` / `RewriteResultView`。
4. **发起入口**：Composer 工具条对话框 + 空态卡片扩展为三个入口（面试 / JD 分析 / 项目优化），复用现有 store 动作。
5. **侧边栏退役**：`JdPanel`、`RewritePanel` 两个折叠面板取消，结果渲染部分拆成主区视图组件，输入表单拆成发起组件。

## 三、JD 分析部分的改动

**后端（小，≈0.5 天）**
1. `GET /job/analysis/list?conversation_id=` — 摘要列表（id / job_role / total_score / created_at）。repository 方法已存在，只差暴露。
2. `GET /job/analysis/detail?analysis_id=` — 单条全量（复用 `analysis_entity_to_dict`）。
3. `POST /job/analysis/delete` — 删除单条。**注意引用关系**：`interview_sessions.job_analysis_id` 软引用它，且面试作答时实时读"最新分析"的 jd_text → 删除最新分析会让该会话的面试追问拿不到 JD。处理选项见待拍板 #2。
4. `/conversation/list` 徽标扩展（与项目优化一起做）。

**前端（主体 ≈1 天）**
1. `JdPanel` 结果渲染部分 → `AnalysisResultView.vue`（主区版式，内容结构不变：总分/维度条/关键词/折叠明细）。
2. JD 输入 + 截图分析按钮 → `StartAnalysisForm.vue`（发起入口）。
3. 树子节点：`📊 {job_role} · {total_score}分 · {MM-DD HH:mm}`，懒加载 + 删除。
4. 侧边栏面板退役。**注意**：JdPanel 里"分析后结果保存"的体验迁到主区后，`loadLatest`（选中会话自动拉最新分析）的定位要重新想——建议主区不再自动展示分析，分析只在子节点里看（更符合"会话记录"语义）。

**历史价值**：现在前端只能看最新一条分析，迁移后历史每一条都可回看——这是顺带的功能增强。

## 四、项目优化部分的改动

**后端（前置工程 + 接口，≈1 天）**
1. **新表 `project_rewrites`**：`id / conversation_id(index) / original_description / original_issues(JSON) / improved_version / python_backend_version / agent_version / created_at`。启动时 `create_all` 自动建表，无迁移脚本（与面试改造同理）。
2. `POST /resume/project/rewrite` 改造：LLM 结果落库后返回，响应体增加 `rewrite_id`；响应结构其余字段不变（前端与导出接口兼容）。
3. 新增 `GET /resume/project/rewrites?conversation_id=`（摘要列表）、`GET /resume/project/rewrite/detail?id=`（全量）、`POST /resume/project/rewrite/delete`。
4. 导出接口不动（`POST /export/project-rewrite` 传结果对象，detail 页可直接复用）。

**前端（≈1 天）**
1. `RewritePanel` 结果渲染 → `RewriteResultView.vue`（三个版本 + 复制 + 原描述问题）。
2. 输入表单 → `StartRewriteForm.vue`。
3. 树子节点：`✏️ 优化 · {original_description 前 12 字}… · {MM-DD HH:mm}`，懒加载 + 删除。
4. 侧边栏面板退役。

## 五、树的展示结构（三个分组）

一个会话下最多三类子节点，推荐**分组小标题**而非平铺混排：

```
▼ 【演示2】make-resume 生成 HTML 简历      🎯2 📊1 ✏️3
    🎯 面试 (2)
      · 通用方向 · 3轮   10-12 14:30  [85分]
      · Python 后端 · 5轮  10-11 09:00  [进行中]
    📊 JD 分析 (1)
      · 后端开发工程师 · 75分  10-12 12:00
    ✏️ 项目优化 (3)
      · 电商系统后端开发…  10-10 16:00
```

- 父节点右侧显示三个 mini 徽标（数量为 0 不显示）。
- 分组标题点击展开/收起该组，各组独立懒加载。
- 建议默认展开规则沿用现状：面试组有"进行中"场次时自动展开。

**children 拉取方式**：面试已有 `/interview/list`，JD/优化各自加 list 接口，各组独立拉（三个请求）——保持与面试一致、互不阻塞；也可以做聚合接口 `/conversation/children` 一次返回三类（一个请求但响应大）。列为待拍板 #4。

## 六、预计改动清单汇总

| 层 | 内容 | 规模 |
|---|---|---|
| 后端 | 4 个 JD 分析接口 + 4 个项目优化接口（含新表）+ 徽标扩展 | ≈1.5 天 |
| 前端 | 2 个主区视图 + 2 个发起表单 + 树分组化 + store 扩展 | ≈2 天 |
| 测试 | 新接口 e2e 用例（列表/详情/删除/落库）≈ 10 项 | 随开发 |
| 不动 | job_analysis 表结构、resume_versions、导出接口、面试链路 | — |

**风险点**
- 项目优化新表是本次唯一 schema 变更，`ensure_tables` 惰性建表对现有库无感，但**旧数据无法补录**（改造前的优化结果已永久丢失，只能从今天起有历史）。
- 删除"最新一条 JD 分析"会影响面试追问的 JD 来源，需要明确策略（见下）。
- 侧边栏三个面板退役后，侧边栏只剩 会话/文档/知识库，信息密度下降——文档与知识库面板是否也要类似治理，可以后续另议（不在本方案范围）。

## 七、待拍板问题（2026-10-13 已审核确认）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 项目优化持久化 | **建表** `project_rewrites`，create_all 自动建表，旧结果不补录 |
| 2 | JD 分析删除策略 | **允许删 + 提示**——被面试引用/为最新一条时确认弹窗说明影响，用户可继续删 |
| 3 | 树展示 | **分组小标题**——面试/JD 分析/项目优化三组，各组独立懒加载 |
| 4 | children 拉取 | **各组独立接口**——与 /interview/list 模式一致，三请求并行 |
| 5 | 发起入口布局 | **三处都放**——空态卡片与 Composer 对话框均放三个入口 |

方案已定稿，可按「六、预计改动清单」进入实施。建议实施顺序：后端（新表 + JD 分析接口 → 项目优化接口 → 徽标扩展）→ 前端（store/树分组 → 主区视图 → 发起入口 → 面板退役）。
