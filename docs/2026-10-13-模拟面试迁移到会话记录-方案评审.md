# 方案评审：将「模拟面试」从侧边栏迁移到会话记录（父子结构）

- 日期：2026-10-13
- 状态：已实施（2026-10-13 当天完成，167 项后端测试通过，前端构建通过）
- 目标：把侧边栏独立的「🎤 模拟面试」折叠面板取消，将面试场次作为**子节点**挂到会话记录列表中，形成「会话（父）→ 面试场次（子）」的结构。

---

## 一、现状盘点

| 项 | 现状 | 位置 |
|---|---|---|
| 面试入口 | 侧边栏折叠面板内嵌 `InterviewSidebar`，约 300 行单组件承载「未开始 / 进行中 / 历史回放」三种状态 | `frontend/src/components/sidebar/InterviewSidebar.vue`、`views/Workspace.vue:83-85` |
| 面试状态管理 | Pinia `interview.js`，锚定 `conv.currentId`；切换会话即清空内存状态并重载历史 | `frontend/src/stores/interview.js:47,84-90` |
| 数据关联 | `interview_sessions.conversation_id` 软关联会话，**一个会话可有多场面试**；删除会话时已有级联清理 | `repositories/interview_repository.py:16`、`services/conversation_store_service.py:286-298` |
| 消息存储 | 面试消息独立存 `interview_messages`，不与聊天消息混写 | `api/interviews.py:109,206-252` |
| 会话列表 | 扁平列表，返回 `conversation_id/title/message_count/last_message_preview` 等，**不含面试信息** | `services/conversation_store_service.py:233-243` |
| 已有 API | start / answer / list（按会话列场次）/ detail（全量回放） | `api/interviews.py` |

**关键结论**：父子关系在数据层已经成立，本方案**不需要改数据库表结构、不需要写迁移脚本**，历史数据自动以树形呈现。改造成本集中在：前端结构重组、会话列表接口增强、少量新 API。

## 二、想法的可优化点（审核重点）

### P1. 「点击子节点后，主聊天区显示什么」——最核心的决策

点击面试场次子节点时有两个选项：

- **方案 A（推荐）**：子节点点击 → 主聊天区切换为「面试视图」，以聊天气泡形式回放/进行面试问答。面试彻底融入会话流，视觉统一。
- **方案 B**：子节点只是快捷入口，点击后仍打开右侧/侧边的面试面板，主聊天区不变。改动小，但"迁移到会话记录"的意义打折。

方案 A 需要把 `MessageList` 做成可切换的双视图（聊天消息 / 面试 transcript），并复用 `interview/detail` 的全量数据渲染。**此决策影响后面所有条目，请先拍板。**

### P2. 选中状态模型要升级，防竞态机制要覆盖子节点

现在 `conversation.js` 用 `currentId` + `selectSeq` 防止快速切换时"高亮 B、内容 A"。引入子节点后，选中项必须升级为复合模型，例如 `{ type: 'conversation' | 'interview', id }`：

- 所有 watch（chat / analysis / interview / resume 联动）要改为感知 `type`——选中面试子节点时不应再触发 analysis/resume 重载。
- `selectSeq` 需覆盖子节点切换，否则同样会出现过期回放。
- 建议在 store 层新增一个 `activeNode` 概念，`currentId`（父会话）与 `activeNode` 分离，避免大面积改动现有逻辑。

### P3. 会话列表接口：避免 N+1，建议「徽标 + 懒加载」

树形列表需要每个会话下的面试场次。两种取法：

- ❌ 前端选中后再逐会话请求 `/interview/list` → 展开 N 个会话就发 N 个请求。
- ✅ **推荐**：`/conversation/list` 用一条聚合查询附带 `interview_count` 和最新场次摘要（时间/状态），列表只渲染徽标（如「面试 ×2」）；**展开父节点时才懒加载** `/interview/list?conversation_id=xx` 拉子节点明细。

这样首屏压力不变，接口改动可控（一条 GROUP BY，注意用独立查询而非循环）。

### P4. 进行中面试的状态恢复（现有弱点会被放大）

现状：进行中面试的轮次状态只存在 Pinia 内存里，切换会话即丢，刷新页面即丢。现在侧栏里有"进行中"提示兜底，迁移后用户从树里点回子节点，**如果直接渲染成"已结束"或空白，会误以为进度丢失**。

优化建议：以 `interview_messages` 为准恢复状态——`detail` 已返回全量消息，前端打开子节点时按 `msg_type` 重建 rounds，`status=in_progress` 且轮数未达上限（8 轮）的场次显示「继续作答」。这一条是**新增工作量**，但不做会直接产生"丢数据"的观感。

### P5. 「发起面试」入口要重新设计

原来「开始面试」按钮在侧栏，迁移后入口消失。候选：

- 父节点 hover 显示「+」发起面试（快，但列表内嵌表单体验差）；
- **推荐**：选中会话后，主聊天区空态/工具条提供「发起模拟面试」按钮；未上传简历时（后端 `interviews.py:61-69` 会拒绝）前端先校验并引导去上传，而不是让用户点了才报错。

方向选择（direction）表单建议做成主区的临时引导卡片，而非弹窗。

### P6. 缺「删除单场面试」的 API 与入口

树形结构天然诱导用户右键删除子节点，但后端目前**没有删除单个 interview session 的接口**（只有随会话级联删除）。需要新增 `POST /interview/delete`（session 级，双表清理 `interview_messages` + `interview_sessions`），并补单测。若不打算提供此功能，子节点菜单应只保留"查看"。

### P7. 组件拆分：300 行单组件借机拆掉

`InterviewSidebar.vue` 三态合一，迁移时正好拆为：

- `InterviewTranscript.vue`（只读回放，方案 A 下即主区面试视图的消息渲染层）
- `InterviewRunner.vue`（输入、逐轮评价、追问逻辑）

拆分后侧边栏的面试面板整体退役，`Workspace.vue` 的联动 watch 相应简化。

### P8. 小项清单

- 子节点文案建议：`🎯 面试 · {direction} · {rounds}轮` + 状态徽标（进行中/已完成/得分）。
- `interview.js` 的 `loadHistory` 与子节点懒加载合并为一个数据源，避免两处各自拉。
- 树展开状态要持久到 `localStorage`，否则每次切换面板收起都重置。
- 补测试：`conversation/list` 新字段的聚合查询、interview/delete 级联、进行中场次的状态恢复逻辑（前端逻辑为主，后端测试聚焦接口）。

## 三、预计改动清单

**后端（小）**
1. `conversation_store_service.py`：list 接口附带 `interview_count` + 最新场次摘要（聚合查询）。
2. `api/interviews.py` + repository：新增 session 级删除接口（P6，可选）。
3. 无表结构变更、无迁移脚本。

**前端（主体工作量）**
1. `ConversationList.vue` → 树形（el-tree 或自绘两级列表），子节点懒加载。
2. `conversation.js` 新增 `activeNode` 复合选中模型，`selectSeq` 覆盖子节点。
3. 主聊天区支持聊天/面试双视图（方案 A 时），`MessageList` 或其容器改造。
4. `InterviewSidebar.vue` 拆分为 Transcript + Runner，侧栏面板退役。
5. `interview.js`：以 detail 消息恢复进行中状态；发起面试入口迁移。

**不做的事**
- 不动 `interview_sessions/interview_messages` 表结构。
- 不把面试消息写进 `conversation_messages`（保持消息隔离，级联删除逻辑不受影响）。
