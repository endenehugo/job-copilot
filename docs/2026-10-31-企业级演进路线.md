# 企业级演进路线（差距分析 → 触发条件 → 方案）

> 定位：这份文档回答一个面试高频问题——**"这个项目离真正可落地的企业级系统还差多少？为什么那些差距你现在不修？"**
> 它是一次全仓深度审查（后端安全/数据层/前端/工程化四路并行 + 线上站点实测）的结论沉淀，也是后续演进的排期依据。
> 写法约定：每一项都按「差距是什么（带代码证据）→ 为什么现在不做 → 什么信号出现时必须做 → 方案草图与成本」四段展开。
> **"知道差距在哪、算得清什么时候值得修"本身就是工程能力**——比把所有中间件堆上更有说服力。

## 一、评估结论（2026-10-31 全仓审查）

| 维度 | 当时评分(5 分制) | 企业级基线 | 定性 |
|---|---|---|---|
| 代码质量 / 事务纪律 / 降级设计 | 4.5 | 4 | 已达标 |
| 测试（403 用例，现为 425） | 4 | 4 | 已达标 |
| 单机可运维性（systemd / 备份 / 压测体系） | 4 | 4 | 已达标 |
| 身份与多租户 | 1.5 | 4 | 架构缺失（有意为之，见 §四） |

| 可观测性 / 告警 | 2.5 | 4 | 有地基（perf_trace + llm_usage），缺上层 |
| 高可用（多实例 / 自愈） | 2 | 4 | 单点，暂可接受 |

**核心判断**：差距是**架构级**的不是**代码级**的——单看事务处理、归属隔离、降级路径，很多地方好于真实企业代码；缺的是支撑规模四根柱子：真实身份、滥用防护、水平扩展、持续交付。其中两根（滥用防护、持续交付）已在 2026-10-31 补齐，剩下两根在本文档里挂了明确的触发条件。

## 三、演进项（按触发条件排期，不是按"看起来高级"排期）

### 3.1 Alembic 迁移框架

- **差距**：无迁移框架。`create_all` 只建新表；结构演进靠 `mysql_base.py` 的 `_COLUMN_PATCHES` / `_INDEX_PATCHES` 手工登记（现共 2 列 + 2 索引），补丁失败只 error 日志，schema 会静默漂移。`message_meta_repository.py` 甚至因为"没有 Alembic"而特意把卡片载荷拆成独立表来规避 DDL 风险——设计已被这个欠账反向扭曲。
- **为什么现在不做**：当前两轮演进靠补丁表是**够用且诚实**的——每次补丁都带"请手工执行"的日志兜底；引入 Alembic 有一次性成本（基线生成、CI 双跑、部署流程改造），而 schema 变更频率目前是月级。
- **触发条件**（任一满足即做）：① `_COLUMN_PATCHES + _INDEX_PATCHES` 合计条目 ≥ 6；② 出现第一次"需要改列类型/删列"这类补丁表达不了的变更；③ 第二个部署环境（staging）出现，两边 schema 需要同步演进。
- **方案**：`alembic init` → `autogenerate` 生成基线（现网库 `stamp head`）→ CI 里对空库跑 `upgrade head` 验证可重建 → 部署脚本加 `alembic upgrade head` 步骤 → 删两张补丁表。约 1.5 天。

### 3.2 会话消息分页

- **差距**：`list_by_conversation_id`（`message_repository.py`）一次拉整会话全部消息（含 Text 大字段），会话详情接口全量下发。压缩水位只约束模型输入，不约束 DB 读取——聊几百轮的会话每次打开都全量传输。
- **为什么现在不做**：展示站的会话长度天然有限（访客日均几轮），且全量回放对"刷新后消息不丢"的体验是兜底的；分页会引入"加载更多"的前端状态机。
- **触发条件**：单会话消息数 P95 > 200 条，或会话详情接口 P95 > 800ms（监控页可观测）。
- **方案**：游标分页（按 `id` 倒序，首屏 50 条，`before_id` 翻页）——比 offset 分页稳定（消息插入不改变游标语义）。后端 1 天 + 前端加载更多 1 天。

### 3.3 错误码结构化 + 信封契约收敛

- **差距**：信封 `code` 混用字符串 `'success'` 与整数 400/404/429；无业务错误码体系，前端排障只能靠 message 文本；REST 风格混用（`DELETE /knowledge/entries/{id}` 与 `POST /document/delete` 并存）。"HTTP 永远 200"让网关监控、重试策略、缓存语义全部失效。
- **为什么现在不做**：信封是旧版迁移过来的**自觉契约**，前后端两端的解析都依赖它；全量切换是一次前后端联动的破坏性变更，演示期收益为负。
- **触发条件**：① 出现第二个消费方（小程序 / 开放 API）；② 需要接入网关级监控告警（HTTP 状态码是它的语言）。
- **方案**：新接口直接用新契约（真实 HTTP 状态码 + `{code: "BUSINESS_CODE", message, data}`）；旧接口在信封里**加** `biz_code` 字段（向后兼容），过渡期双轨；REST 化只做"新端点用资源式命名"。约 2~3 天 + 前端联调。

### 3.4 SSE 断连落库兜底

- **差距**：`chat_stream` 的 `append_message_pair` 在流末尾；客户端中途断开触发生成器取消，**已下发的半截回答不落库**——用户刷新后看到的内容与刚才屏幕上的不一致。
- **为什么现在不做**：展示场景下断连概率低，用户重发即可；修它要把持久化挪进 `finally` 并处理 `GeneratorExit` 的语义边界（半截回答该不该存、存了标记什么状态），不是三行改动。
- **触发条件**：监控出现"chat 流式请求无 done 事件"占比 > 2%（需要在 done 事件上补计数），或移动端弱网场景成为主路径。
- **方案**：生成器 `try/finally` + `GeneratorExit` 分支：已有非空 `streamed_text` 时照常落库，消息标记 `aborted`，详情接口回放时补一个"（生成中断）"角标。约半天 + 2 个单测。

### 3.5 水平扩展（最大的一项，分四步走）

**差距全景**：`workers=1` 是硬约束，卡点不在 MySQL（本就可共享）而在三处——

1. **文件系统是唯一事实源**：上传文件/解析文本/FAISS 索引全在本地 `backend/resources`（`document_index_service.py` 直接 `open(parsed_text_path)`），机器 B 上文件全 404；
2. **索引写路径竞态**：重建序列 `rmtree→rename` 非原子；BM25 缓存只在本进程失效——双 worker 时混合检索两路召回互相矛盾且**无任何报错**（最危险的一类 bug）；
3. **进程内队列与锁**：压缩队列是线程池 + 内存 set（重启丢任务，幂等可接受）；题库锁是进程内 RLock（多进程会静默失效丢题）。

**为什么现在不做**：单核服务器实测容量天花板 69-70 RPS，瓶颈是 CPU 而非架构；演示站的真实负载离天花板有两个数量级。为 10 倍流量预付架构成本，是企业级**过度设计**和工程成熟之间的经典误判。

**触发条件**（按顺序出现，按顺序做）：

| 步骤 | 触发条件 | 内容 | 成本 |
|---|---|---|---|
| ① 文件外置 OSS | 出现第二台机器的需求，或磁盘水位 > 70% | 上传/生成产物迁 OSS（`backup_push.sh` 已具备 rclone 通路），`resources` 只留可重建索引；读写包一层 Storage 抽象 | 2~3 天 |
| ② 引入 Redis | 需要多进程/多实例，或需要跨请求共享计数 | 三件事：题库锁换分布式锁、压缩队列换 arq/RQ（保持轻量，不上 Celery）、限流与配额计数器外置 | 2 天 |
| ③ 多 worker | Redis 就位后 | uvicorn `--workers 2`；索引目录加 version 文件做 BM25 缓存失效（读到旧版本号即重载）；FAISS 会话级索引天然按会话分片，每实例一份即可 | 2 天 |
| ④ Nginx 多 upstream | 出现第二台机器 | upstream 加实例 + 健康探测 | 半天 |

**明确不换向量库**：会话级索引按 conversation_id 分片、无跨实例写冲突；等单表千万级或需要多模态检索再评估 Milvus / pgvector。RRF 重合率 0.14~0.33 的教训是"检索组件的替换要用重合率基准说话"（`scripts/bench_rerank_v3.py` 的方法论直接复用）。

### 3.6 可观测性上层（指标 → 告警）

- **差距**：有 perf_trace（请求级分段计时）+ llm_usage（计量）+ 监控页，但无 Prometheus 指标、无告警、trace_id 不回传客户端（用户报障无法关联日志）。
- **为什么现在不做**：单机演示站，"人肉看监控页 + UptimeRobot 拨测"的覆盖已经够；Prometheus 全家桶在这台单核服务器上是要认真权衡的内存开销。
- **触发条件**：① 出现过一次"故障发生但没人发现"；② 引入第二个实例后日志分散。
- **方案**：先做零成本的——trace_id 写进响应头 `X-Trace-Id` + 监控页顶部加"最近 10 分钟错误率"；再决定是否上 `prometheus-fastapi-instrumentator`（一个 /metrics 端点 + 免费托管抓取，不一定要自建 Grafana）。1 天。

## 四、明确不做的决定（与理由一起存档）

| 决定 | 理由 |
|---|---|
| **不做完整注册/登录体系** | 游客即用是演示产品的正确产品决策——注册墙会杀掉"面试官点开就玩"的转化。auth 知识点已由 visitor 签名 Cookie（HS256 + aud 隔离 + 形态校验）与 admin JWT（bcrypt + PyJWT）覆盖。若未来转真实产品，第一步是"可选邮箱绑定"（游客数据无感升级），而不是推翻 visitor 机制 |
| **不做 REST 全量化改造** | 同 §3.3：契约是自觉的、双端已闭合，破坏性迁移的收益为负 |
| **不上 K8s / 微服务** | 单机 compose + systemd 对当前与可预见规模是正确选择；服务拆分只会把已经清晰的模块边界搅碎。什么时候需要？——出现独立伸缩需求（如批处理压满 CPU 但不影响在线流量）时，先拆那个批处理为独立 service，而不是先上 K8s |
| **不上 Celery/Kafka** | 压缩任务每会话几秒一次、补题每天几十次，Redis 队列绰绰有余；中间件选型的原则是"为当前负载的 10 倍设计，不为 1000 倍付费" |

## 五、面试讲述建议

被问"这个项目生产化还差什么"时，三层答法：

1. **先讲已经闭环的**（带数字）：配额熔断怎么设计的（两级：按访客按天 + 全站 token 预算，为什么访客限额挡不住脚本——身份只是个 cookie）、限流三桶怎么选的路由、`llm_usage` 一张表怎么同时驱动熔断和监控页；
2. **再讲差距的定位**（带证据）：水平扩展的三个真卡点是文件系统、索引写竞态、进程内锁——不是"加个负载均衡"一句话的事；每个都有代码位置；
3. **最后讲排期逻辑**（这条最加分）：每一项都有触发条件（`_COLUMN_PATCHES` ≥ 6 条才上 Alembic、单会话 P95 > 200 条才做分页）——**架构演进由信号驱动，不由简历驱动**。这句话说完，"为什么不做"就从短板变成了判断力。
