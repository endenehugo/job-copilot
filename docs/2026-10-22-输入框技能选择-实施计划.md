# 输入框技能选择：实施计划

> 2026-10-22。目标：把"模型自己判断该用哪个技能"改成"用户点选技能"，并让 7 个内置技能从隐性变显性。
> 本文只写方案，不动代码。

## 1. 范围

**做**

- 输入框为空且获得焦点时，自动弹出技能面板一次（已选过或打过字就不再自动弹）
- 输入 `/` 随时唤起面板
- 「+」菜单里加常驻入口「选择技能」
- 选中后在输入框上方显示 chip，发送时随请求带上技能名
- 后端按技能注入指南，并覆盖"不注入"的例外（make-resume）

**不做**

- 会话级技能持久化（不加 `conversations.skill` 列）
- 技能搜索框（7 项，列表足够）
- 用户自定义技能上传
- `job-apply`、`contributor` 从此不在任何界面出现

## 2. 技能清单收敛

去掉 `job-apply`、`contributor` 后剩 7 项。这两个在后端没有可执行工具（一个要浏览器自动化、一个要 GitHub 操作），留着只会让模型输出"请你手动去填/去提 PR"的流程说明。

| name | title | group |
| --- | --- | --- |
| job-match | 岗位匹配分析 | 求职判断 |
| great-resume | 简历经历提升 | 求职判断 |
| make-resume | 制作简历文件 | 交付文件 |
| interview | 模拟面试 | 面试 |
| project-guide | 项目导学与面经 | 面试 |
| evidence-recap | 交付证据复盘 | 面试 |
| offer | 秋招进度管理 | 过程管理 |

`title` / `group` 由后端给，前端不硬编码（改技能不用改两处）。

**关键点：不能只在前端过滤。** `build_agent_system_prompt()` 里的技能目录、`SkillTool.description` 里手写的 9 个技能名，都要同步。否则用户看不到 `job-apply`，模型仍然会去调。

## 3. 后端改动

### 3.1 `app/utils/skill_loader.py`

```python
# 展示元信息：标题、分组、是否对外。exposed=False 的既不进接口也不进系统提示。
SKILL_META = {
    "job-match":      {"title": "岗位匹配分析", "group": "求职判断"},
    "great-resume":   {"title": "简历经历提升", "group": "求职判断"},
    "make-resume":    {"title": "制作简历文件", "group": "交付文件"},
    "interview":      {"title": "模拟面试",       "group": "面试"},
    "project-guide":  {"title": "项目导学与面经", "group": "面试"},
    "evidence-recap": {"title": "交付证据复盘",   "group": "面试"},
    "offer":          {"title": "秋招进度管理",   "group": "过程管理"},
    "job-apply":      {"title": "求职申请填写",   "group": "过程管理", "exposed": False},
    "contributor":    {"title": "开源贡献",       "group": "过程管理", "exposed": False},
}
```

- `list_skills(visible_only: bool = True)`：默认过滤 `exposed=False`。默认值取 True，这样 `catalog_prompt()` 和 `SkillTool` 的 `list` 分支自动跟着收敛，不需要改调用方。
- 每项补 `title`、`group`，`summary` 取 description 首句（复用 `catalog_prompt()` 现有切分逻辑，抽成 `_first_sentence()` 共用）。
- 新增 `skill_meta(name) -> dict`：取 `SKILL_META` 并兜底（未知技能返回 `{title: name, group: ""}`），`_apply_skill` 用。
- `load_skill()` 不做白名单收窄：纯静态文本，没有执行风险；收窄反而会让"模型自己决定加载 job-apply"直接报错。

### 3.4 `app/api/conversations.py`

两个端点（`/conversation/chat`、`/conversation/chat/stream`）各加一段校验，非空时必须在可见清单里，否则 400：

```python
skill = (payload.skill or "").strip()
if skill and skill not in {item["name"] for item in skill_loader.list_skills()}:
    return fail(f"未知技能：{skill}", code=400)
```

不透传的话就是任意字符串进系统提示，等于送了个提示注入口子。校验放在端点内、`fail(...)` 走现有信封，和别的参数错误一致。

### 3.5 `app/services/conversation_chat_service.py`

三个改动点：

1. `_prepare_chat(..., skill: str = "")` 多收一个参数、多返回一个（元组从 7 项变 8 项，`chat()` 与 `chat_stream()` 两处解包同步）。
2. 新增 `_apply_skill(messages, skill)`：把注入内容插到 system 消息之后（`messages[1:1]`），返回新列表，不改原对象。
3. `chat()` / `chat_stream()` 在 `prompt.invoke(...).to_messages()` 之后、`_invoke_agent()` 之前调用。

```python
_MAX_SKILL_CHARS = 14000

def _apply_skill(self, messages: list, skill: str) -> list:
    """把用户显式选择的技能指南插到系统提示之后。

    这里是消息内容，不是 ChatPromptTemplate 模板，花括号**不需要**转义。
    """
    document = skill_loader.load_skill(skill)          # 已校验过白名单
    meta = skill_loader.skill_meta(skill)
    if skill == "make-resume":
        # 系统提示已明确"不要 load_skill make-resume，规范内置于工具"，
        # 这里注入全文只会和 resume_generate_tool 的模板规则打架
        body = (
            "【本次任务技能】用户选择了「制作简历文件」。"
            "直接调用 resume_generate_tool 生成并落盘，不要调用 load_skill，"
            "也不要把 HTML 源码贴进回答。"
        )
    else:
        if len(document) > _MAX_SKILL_CHARS:
            document = document[:_MAX_SKILL_CHARS] + "\n\n（指南过长，已截断）"
        body = (
            f"【本次任务技能】用户显式选择了技能 `{skill}`（{meta['title']}）。\n"
            "完整操作指南已附在下方，请严格按它组织回答，不要再调用 load_skill。\n"
            "如果用户这个问题与该技能明显无关，先用一句话确认是否仍按该技能处理，不要硬套。\n\n"
            + document
        )
    return [messages[0], SystemMessage(content=body), *messages[1:]]
```

**多模态路径不注入**：`chat()` / `chat_stream()` 里 `_invoke_multimodal()` 走的是另一套消息组装（`_invoke_multimodal(history, context, query, urls)`），本次不动。有图片时技能不生效，前端 chip 照常显示但不影响结果——这一点写进文档，不做额外提示。

### 3.6 `app/tools/skill.py`

`description` 里手写的九个技能名单删掉 `contributor`、`job-apply` 两项，并把"不确定有哪些技能时传 `list`"保留（现在 list 只会给出 7 个）。

### 4.2 `components/chat/SkillMenu.vue`（新）

### 4.3 `Composer.vue`

状态：

```js
const skills = ref([])
const skillOpen = ref(false)
const skillIndex = ref(0)
const selectedSkill = ref(null)     // { name, title, ... }
const skillsLoaded = ref(false)
const hintSeen = ref(sessionStorage.getItem('jc_skill_hint_seen') === '1')
```

三个触发：

1. **聚焦自动弹一次**：`@focus="onFocus"`，条件 `!hintSeen && !text.trim() && !selectedSkill`。弹出后立即写 `sessionStorage.jc_skill_hint_seen = '1'`。用 sessionStorage 而不是 localStorage——永久记住等于让功能消失；每次都弹又太吵。
2. **`/` 唤起**：`@input` 里判断 `text.value === '/'`（必须"恰好是 `/`"，这样 `and/or` 不会误触发），然后 `text.value = ''`、打开面板、`autosize()`。
3. **「+」菜单**：`PlusMenu` 加一组 `{ icon: 'sparkle', title: '选择技能', desc: '按固定流程处理求职任务' }`，`emit('open-skills')`；`Composer` 接住后 `plusOpen = false; openSkillMenu()`。

键盘：面板打开时焦点仍在 textarea，所以拦截写在现有 `onKeydown` 最前面（`isComposing` 判断之后）：

```js
if (skillOpen.value) {
  if (e.key === 'ArrowDown') { e.preventDefault(); skillIndex.value = ...; return }
  if (e.key === 'ArrowUp')   { e.preventDefault(); ...; return }
  if (e.key === 'Enter')     { e.preventDefault(); pickSkill(filtered[skillIndex.value]); return }
  if (e.key === 'Escape')    { skillOpen.value = false; return }
}
```

chip：放在 `.composer-shell` 里、`.composer-row` 之前（与 `composer-attach` 同级），样式沿用 attach 的圆角小标签：

```
[ sparkle 模拟面试 × ]
```

`×` 清空 `selectedSkill`，chip 消失。发送后不清空——用户连着聊同一个技能是常态。

payload：`sendStream` 与 `send` 带上 `skill: selectedSkill?.name || ''`。`chat.sendStream(query)` 改成 `chat.sendStream(query, { skill })`，`chat.js` 里拼进 body。

面板数据：首次打开时 `skillsApi.list()`，失败只 `notifyError` 并关面板，不阻塞输入。

## 6. 验收

**pytest**（新增 `tests/test_skills_api.py`）

- 清单返回 7 项，且不含 `job-apply` / `contributor`
- 每项都有 `name/title/group/summary`，`summary` 不含换行、长度 < 60
- 传入不存在的 skill → `code=400`，文案含技能名
- `_apply_skill`：注入内容含 SKILL.md 正文首行；`make-resume` 走例外分支（不含 `# /make-resume` 标题、含 `resume_generate_tool`）；`messages[0]` 原样保留
- `catalog_prompt()` 不含 `job-apply`

**前端手测**

1. 新开会话 → 点输入框 → 面板自动弹，`sessionStorage` 有标记；再点不弹
2. 输入 `and/or` → 不弹；清空后输入 `/` → 弹，且 `/` 被吃掉
3. 「+」→ 选择技能 → 弹；Esc 关；点面板外关
4. 选「模拟面试」→ chip 出现 → 发"帮我模拟面试" → 后端日志里能看到注入段落，回答走面试流程
5. 点 × → chip 消失 → 再发一句 → 后端无注入（回归）
6. 只读演示会话 → 不弹、无 chip
7. 发一条带图片的消息 → 不报错（技能不生效属预期）

**回归**：`cd backend && D:/conda/python.exe -m pytest tests/ -q`（现有 314 项应全绿）。

## 7. 风险与注意

- **`_prepare_chat` 返回值从 7 元组变 8 元组**：两处解包必须同步，漏一处就是 `ValueError: too many values to unpack`，而且是在请求路径上炸，测试覆盖要包含一次真实 chat 调用。
- **花括号**：注入的是消息内容，不是 `ChatPromptTemplate` 模板，不要照抄 `catalog_prompt()` 的 `.replace("{", "{{")`，那是 system 模板专用的。反过来忘了这点会得到 `{{` 字面量。
- **token 成本**：`project-guide` 13.4k 字符 ≈ 7k token，只注入选中那一条消息，不做会话级累积；若以后要改成会话级，必须先想清楚每轮都付这笔钱的代价。
- **改 `stores/*.js` 要整页刷新**：本次 `chat.js` 的 `sendStream` 签名会变，改完让用户 Ctrl+Shift+R，否则会看到"chip 有、注入没有"的假象。
- **只读会话**：`Composer` 的 readonly 分支不渲染 shell，天然不弹。别为了统一把面板挂到外层。
- **技能与意图冲突**：注入文案里保留"明显无关先确认"，否则用户选了 interview 再问"改简历"会被硬套流程，体感是被劫持。

## 9. 实施记录（2026-10-22 17:30，已落地）

实施比计划又收了一步：**interview 和 make-resume 也不进面板**，可选清单从 7 项缩到 5 项
（job-match、great-resume、project-guide、evidence-recap、offer）。理由是同一天实测：
这两个技能背后各有专用模块（状态机 / 模板渲染），让用户在面板里再选一遍等于绕开模块。

随后按用户要求再去掉 `offer`（秋招进度管理），**最终对外 4 项**：
job-match、great-resume、project-guide、evidence-recap。offer 的产出是一份本地进度表，
本产品没有对应存储与视图，留着只能输出一段没有落点的格式。

与计划原文的差异：

| 计划 | 实际 |
| --- | --- |
| 7 项面板 | 5 项；interview / make-resume 也 `exposed: False` |
| `summary` 取 description 首句 | description 首句最长的 78 字，面板放不下 → `SKILL_META` 手写一句话（`_auto_summary` 只做未登记技能的兜底） |
| `_prepare_chat` 返回值 7 元组改 8 | **没改**：skill 不参与上下文准备，直接作为 `chat()` / `chat_stream()` 的末位参数，解包零改动 |
| job-match 只做说明 | 真正串联：`AnalysisResultView` 加「用 job-match 深入判断」，经 `chat.composerPreset` 把技能 chip + JD 原文预填进输入框，用户可改再发 |

  「岗位结论 + 要求—证据矩阵 + 五态匹配」（真实缺口 / 证据不足），**没有额外走 load_skill 那一轮**
