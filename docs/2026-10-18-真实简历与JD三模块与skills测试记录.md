## 2. 模块一：JD 分析（`/job/analyze/stream`）

| 指标             | 结果                                                               |
| -------------- | ---------------------------------------------------------------- |
| 简历上传 + 解析 + 索引 | 1.73s                                                            |
| 端到端耗时          | **8.44s**（解析 JD 3.63s → 匹配评分 4.47s → 落库）                         |
| 阶段事件           | `jd_parse@0.36s` → `scoring@3.63s` → `save@8.09s` → `done@8.44s` |
| 总分             | **87**（技能 90 / 项目相关 85 / 表达 88 / 岗位契合 86）                        |
| JD 结构化         | 21 个关键词、10 条硬性要求、5 条加分项、5 条建议突出角度                                |
| 落库校验           | `analysis_id=27`，`/job/analysis/latest` 回读分数与四维一致                |
| warnings       | 空（无降级）                                                           |

产出的 `gaps` 质量不错，三条都指向真问题：

1. 「简历未提及 C++，而 JD 明确要求精通 C++，属于硬性门槛缺失」
2. 「技术栈以 Go/Python 为主，缺乏 Linux/Unix 系统底层描述」
3. 「未突出与产品、算法团队联动的具体案例」

**发现两个产品级问题：**

- **总分未对硬门槛打折**：`gaps` 已认定 C++ 是硬性门槛缺失，但总分仍是 87（四个维度没有"门槛"项），用户容易读成"85 分以上可投"。
- **改进建议会诱导编造**：建议第 1 条原文是「在简历中补充使用 C++ 进行系统开发或性能优化的经历，哪怕只是参与或调优部分模块」——这与"不虚构经历"的产品底线冲突，应改为"若真实接触过则补证据，否则换 Python 栈岗位"。

## 3. 模块二：模拟面试（两场）

### A 场：等题库补齐后作答（模拟真人节奏）

| 阶段                      | 耗时                                                              |
| ----------------------- | --------------------------------------------------------------- |
| 开场（只出第 1 题）             | **2.28s**                                                       |
| 后台补题（4 题，`state=ready`） | 4.27s（不阻塞）                                                      |
| 第 1 轮                   | 2.56s（首字 1.03s），78→**68 分**，`source=bank`                       |
| 第 2 轮                   | 2.54s（首字 1.17s），**65 分**，`source=bank`                          |
| 第 3 轮                   | 2.47s（首字 0.97s），**68 分**，`source=bank`                          |
| 落库                      | `round_count=3`，题库 `cursor=4/4`，消息成对（problem/answer/evaluation） |

题目与简历强相关，且逐轮推进（不是重复问同一段）：

1. 切片策略 → 「500 字、重叠多少、标题层级怎么保留」
2. 提示词工程 → 「模板怎么迭代、有没有 A/B 或用户反馈量化」
3. 并发稳定性 → 「Redis 缓存策略、RabbitMQ 异步、限流阈值」

评价文本有具体批评（"切片策略描述较简略，未说明 500 字块的合理性""只提 2 秒内，缺少缓存/异步/分层架构的具体手段"），不是套话。

### B 场：立刻作答 + 答得很糊（验证降级与追问）

| 指标   | 结果                                                         |
| ---- | ---------------------------------------------------------- |
| 开场   | 2.71s                                                      |
| 回答   | 「就是把文档切一切塞给模型，没怎么调优。」                                      |
| 本轮耗时 | 4.39s（首字 1.06s），**45 分**，`source=follow_up`                |
| 追问质量 | 直接拿简历反打：「你提到'就是切一切'，但项目里写了'准确率 90%+ 和百万级文档秒级检索'，请说明切分边界……」 |

补充观察（调试批次）：若首轮作答早于题库补齐（开场后 2–3 秒内就答完），即使回答质量不错（78 分）也会退回 `source=follow_up`，该轮多花约 1.3s。这是 P2 设计内的降级路径，不是缺陷，但意味着**开场即刻作答的用户会付出一次现场出题的延迟**。

## 4. 模块三：项目改写（`/resume/project/rewrite`）

| 指标 | 结果                                                   |
| -- | ---------------------------------------------------- |
| 耗时 | **7.42s**                                            |
| 产出 | 5 条 `original_issues` + 三个版本（通用 / Python 后端 / Agent） |
| 落库 | `rewrite_id=6`，`/resume/project/rewrites` 历史 1 条     |

`original_issues` 是有价值的（"未突出 RAG 各环节技术选型""成果表述模糊""未区分个人与团队"），三版风格也确实分化（通用版偏业务价值，Python 版补 FastAPI/Milvus 集群，Agent 版补 ReAct/状态机/记忆）。

**但存在编造风险（本次最重要的发现）：**

| 原文事实                    | 改写产出                        | 问题              |
| ----------------------- | --------------------------- | --------------- |
| 准确率 90%+                | 「从 78% 提升至 92%」             | 78% 与 92% 原文都没有 |
| 响应 ≤2s                  | 「检索延迟稳定在 1.2s 内」「QPS 达 120」 | 均无出处            |
| 文心一言 Embedding + Milvus | 「集成 Docling 实现多格式解析」        | 技术栈凭空新增         |

根因在提示词：`project_rewrite_service.py` 的「优化原则 2」写的&#x662F;**"尽可能加入量化指标（QPS、响应时间、准确率、覆盖量等）"**，没有约束指标只能来自原文。建议加一句：「不得新增原文未出现的数字、技术栈或职责；确需量化时用原文已有数据，或改为可核验的定性表述」。这条与 JD 分析里那条"补充 C++ 经历"是同一类风险，建议一起治。

## 7. 结论

1. **三个模块在真实素材上都能跑通并落库**，端到端约 37 秒（JD 8.4s + 面试两场 ~12s + 改写 7.4s + 上传 1.7s + 启动开销），与之前 P0/P1/P2 的实测口径一致。
2. **面试与 JD 分析的"说人话"程度够用**：追问会拿简历原话反问，评价有具体批评；JD 分析的 gaps 抓到了 C++ 这个真门槛。
3. **真正的质量风险不在速度，而在"生成内容的真实性"**：项目改写会补数字、JD 分析建议会建议补经历。两者都建议在本轮修复，属于 P0。
4. **skills 侧只有一个硬故障**：make-resume 装不全；其余 10 个静态全绿，3 个求职核心 skill 在真实素材上产出可用。
