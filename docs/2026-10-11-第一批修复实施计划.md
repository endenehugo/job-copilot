## §0 前置验证结论（已实测，不是推测）

这几条决定了方案能不能落地，先固化下来：

| 结论 | 验证方式 | 结果 |
|---|---|---|
| `ChatTongyi` **没有** `timeout` 字段 | `inspect.getsource` + `model_fields` | 只有 `max_retries`，无 timeout |
| 超时可通过 `model_kwargs` 透传 | 构造实例后打印 `_default_params` | `model_kwargs={"request_timeout": 45}` → 进入 `_default_params` → 透传给 `dashscope.Generation.call(**kwargs)` → `api_request_factory.py:33` `kwargs.pop("request_timeout")` 用作 HTTP 超时 ✅ |
| **`max_retries` 默认 10** | `ChatTongyi.model_fields['max_retries'].default` | **10**，tenacity 指数退避 1~4s，仅对 `HTTPError` 重试 |
| dashscope 默认超时 300 秒 | `dashscope/common/constants.py:20` | `DEFAULT_REQUEST_TIMEOUT_SECONDS = 300` |

### 由此新增一个审计时未发现的关键事实

**单次 LLM 调用的最坏耗时 = 10 次重试 × 300 秒 = 50 分钟。**

这不是理论值：Rerank 是 16 次串行调用，每次都可能触发重试。DashScope 限流或抖动时，用户面对的不是"慢"，是**近乎无上限的等待**。这也解释了为什么前端 5 分钟超时仍可能不够。

所以 T3 里 **`max_retries` 从 10 降到 2，比加 timeout 更重要**。

## T1 · Rerank 去串行（收益最大的一项）

**问题**：`document_index_service.py:389-407` 对每篇文档串行发一次 LLM，最多 16 次。且 BGE Reranker 因缺 FlagEmbedding 依赖必然降级，所以 LLM Rerank 是**常态路径**。

### ⚠ 方案已修正：原计划默认 RRF 是错的，实测推翻

原计划打算默认走 RRF 融合（零 LLM）。在真实索引上实测后**否决**，改为 **listwise 批量排序**。

实测数据（会话 `conv_20260712072752_db28e8`，简历 + 电商商品混合文档，5 个 query，脚本见 §6）：

| 策略 | 总耗时 | 相对逐篇提速 | 与逐篇 Top-4 重合 |
|---|---|---|---|
| 逐篇 LLM（现状） | 21.4 s | 1x | 1.00（基准） |
| 批量打分（一次调用给所有文档打 0-10 分） | 9.7 s | 2.2x | 0.73 |
| **listwise（一次调用直接输出排序）** | **3.7 s** | **5.8x** | **0.71** |
| RRF 融合 | 0 s | — | **0.14 ~ 0.33** |

**为什么 RRF 不行**：它不是"略差"，是在语义明确的查询上把完全不相关的文档排到第一——
- 「有哪些电商产品在售」→ RRF 第一名是简历里的 "LiteLLM 统一调用层" chunk
- 「联系方式是什么」→ RRF 第一名同样是那个简历 chunk，而正确答案（个人信息/电话）被排到第二

根因：`_tokenize` 用 `re.findall(r"[一-鿿]|[a-zA-Z0-9]+")` **按字切分**中文，BM25 召回质量很差；RRF 又完全不看 query-doc 语义，只信任两路召回的排名，于是被污染。叠加 `_search_conversation_docs` 的兜底 `similarity` 检索**无论如何都返回 k 篇**（含不相关的），污染进一步放大。

**为什么 listwise 比批量打分更好**：批量打分出现**分数退化**——「有哪些电商产品在售」时模型给了 8/8/8/8，排序退化成近似随机，把"甜汤"排到了"牛肉丸"前面。listwise 直接要求输出编号顺序，强制产生严格序，同一个 query 下第一名恢复为正确答案。而且输出只有几个数字，比输出 N 个 JSON 对象**更快**（3.7s vs 9.7s）。

### 改动清单

**1. `backend/app/core/config.py`** — 新增配置
```python
rerank_strategy: str = "listwise"   # listwise | per_doc | rrf | off
llm_rerank_max_docs: int = 10       # 超过则先按召回分截断，控制 prompt 长度
llm_rerank_char_limit: int = 300    # 每篇截断字数
rerank_rrf_k: int = 60              # 仅 rrf 策略使用
```

**2. `backend/app/services/document_index_service.py`**

- **新增 `_rerank_with_listwise()`**（新默认）：单次调用，prompt 列出最多 10 篇（每篇 300 字），要求只输出 JSON 编号数组 `[3,1,7,2]`；解析失败或编号越界 → 记 warning，降级到 RRF
- **新增 `_rrf_fuse()`**：仅在 LLM 不可用/失败时兜底，`score(d) = Σ 1/(k + rank)`
- **保留 `_rerank_with_llm()`**（逐篇）供 `per_doc` 策略对比用，**不再作为默认**
- **改 `_rerank_docs()` 为分派**：按 `settings.rerank_strategy` 走 `listwise` / `per_doc` / `rrf` / `off`
- **修复 A2**：`_rerank_with_llm` 里的 `ChatTongyi(...)` 改为走 T3 的 LLM 工厂单例
- **修复 B15**：打分失败置 `score = None`（不是伪造 5.0），并记 warning；前端显示"—"
- **修复 B38**：`:335-336` 的 `logger.debug` 改 `logger.warning`

**3. 保留 `_rerank_with_bge`** 不动，将来装了 FlagEmbedding 自然生效。

**4. 不在本批**：BM25 换 jieba 分词（能治 RRF 的根因，但要加依赖）。已记录到第二批候选。

### 风险与对策

| 风险 | 对策 |
|---|---|
| listwise 输出编号越界/重复/不足 | 解析时过滤非法编号，不足时用未出现的编号按召回顺序补齐（脚本里已实现并验证） |
| prompt 超长（10 篇 × 300 字 = 3000 字） | `llm_rerank_max_docs` 可下调；qwen-plus 上下文充足 |
| `score` 字段语义变化 | 现在混装了 BM25 分、LLM 分、向量分。统一为：`score` 只存**相对序位**，来源放 `metadata["score_source"]`；失败置 `None` |
| 实测样本只有 1 个会话 5 个 query | 上线后保留开关，`per_doc` 可一键回退；建议在真实使用中对召回质量做一轮人工抽查 |

### 验证
```bash

```
预期：listwise 提速 ≥ 4x，与逐篇 Top-4 重合 ≥ 0.7。

## T2 · 上下文验证改异步补发

**问题**：`conversation_chat_service.py:243-251` 在流式结束后再跑一次验证 LLM，`verification`/`sources`/`done` 全排在它之后，用户静默等 3~8 秒。

**方案**：`done` 提前到验证之前；验证结果用独立事件补发。

### 改动清单

**1. `backend/app/services/conversation_chat_service.py:241-269`**

现在的顺序：
```
answer → 验证(3~8s) → append_message_pair → sources → verification → files → done
```
改成：
```
answer → append_message_pair → sources → files → done(answer)   ← 立即结束，用户看到完整回答
       → 验证 → verification(cited_answer + verification)       ← 补发
```

**2. 关键设计点：`cited_answer` 怎么办**

现在 `done` 里带的是**带引用标注**的 `cited_answer`（`chat.js:150` 会用它整体覆盖 `assistantMsg.content`）。改成异步后，`done` 只能发原始 `answer`，引用标注必须随 `verification` 事件一起补发。

做法：`verification` 事件的 data 增加 `cited_answer` 字段：
```python
yield {"event": "verification", "data": {
    "verification": verification_result,
    "cited_answer": cited_answer,      # 新增
}}
```

**3. `frontend/src/stores/chat.js:145-146`** — verification 分支补一行
```js
} else if (event.event === 'verification') {
  assistantMsg.verification = event.data.verification
  if (event.data.cited_answer) assistantMsg.content = event.data.cited_answer
}
```
前端**不需要**处理乱序：`assistantMsg` 是 `reactive`，`done` 后置 `streaming=false` 不影响后续字段更新渲染。

**4. 顺带修 B13**：`:216-223` 流式生成异常只 `logger.warning`，改为同时 yield 一个 `error` 事件，让前端能提示。

### 风险与对策

| 风险 | 对策 |
|---|---|
| 验证在 `done` 之后跑，若此时生成器抛异常会中断连接 | 验证段整体 `try/except`，最坏情况是少发一个 verification 事件，不影响已完成的回答 |
| 用户看到 `done` 后关闭页面，验证白跑 | 可接受；后续可加"验证仅在页面存活时执行"的心跳判断，本批不做 |
| 引用标注延迟出现导致内容"变一下" | 这是取舍：原来用户要**等 3~8 秒才看到任何内容**，现在立即看到、之后补标注。可接受 |

### 验证
浏览器发一条带文档的提问，观察：打字机结束 → 内容**立刻**出现（`done`）→ 1~5 秒后来源面板和风险徽章出现。对比改前的"打完字又卡住"。

## T3 · 统一 LLM 工厂：超时 + 降低重试

**问题**：13 处 `ChatTongyi(` 无一处设超时；`max_retries` 默认 10。

**方案**：新建工厂，所有构造点统一走它。

### 改动清单

**1. 新建 `backend/app/core/llm_factory.py`**
```python
@lru_cache
def build_chat_llm(
    model: str, temperature: float, top_p: float,
    streaming: bool = False, timeout: int | None = None,
    max_retries: int | None = None,
) -> ChatTongyi:
    return ChatTongyi(
        model=model,
        temperature=temperature,
        top_p=top_p,
        streaming=streaming,
        max_retries=max_retries if max_retries is not None else settings.llm_max_retries,
        model_kwargs={"request_timeout": timeout or settings.llm_request_timeout},
    )
```
`@lru_cache` 保证同参数复用同一个客户端实例（顺带修复 A2/A25 的"每次 new 不复用连接"）。参数都是标量，可哈希。

**2. `backend/app/core/config.py`** — 新增
```python
llm_request_timeout: int = 60      # 单次请求超时
llm_max_retries: int = 2           # 从默认 10 降下来，这是关键
llm_stream_timeout: int = 180      # 流式单独放宽，因为长回答本身就要时间
```

**3. 替换 13 处构造点**（保持各自 temperature/top_p 不变）

| 文件 | 行号 |
|---|---|
| `services/context_compression_service.py` | 214 |
| `services/context_verification_service.py` | 286 |
| `services/conversation_chat_service.py` | 306, 312 |
| `services/document_index_service.py` | 369 |
| `services/image_analysis_service.py` | 59 |
| `services/interview_simulation_service.py` | 96, 105 |
| `services/job_description_service.py` | 47 |
| `services/knowledge_review_service.py` | 112 |
| `services/project_rewrite_service.py` | 49 |
| `services/resume_scoring_service.py` | 56 |

**注意**：`conversation_chat_service.py:306` 的 `qa_llm` 若用于流式，走 `llm_stream_timeout`。

### 风险与对策

| 风险 | 对策 |
|---|---|
| `model_kwargs` 里的 `request_timeout` 被 dashscope 忽略 | 已在 §0 实测确认会透传到 `api_request_factory`；仍建议起服务后用一个必然慢的请求实测一次 |
| 超时 60s 对长回答不够 | 流式走 180s；非流式生成长报告的场景（项目改写）若超时，可单独调高 |
| `max_retries=2` 降低成功率 | 只对 `HTTPError` 重试，2 次足以覆盖偶发抖动；真限流时快速失败 + 明确报错，远优于静默等 50 分钟 |

### 验证
```bash

print('单例复用:', build_chat_llm('qwen-plus', 0.7, 0.9) is llm)
"
```
