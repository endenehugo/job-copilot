# Agent 延迟优化方案（2026-10-26）

## 0. 先纠正上一版判断

上一轮我说「Agent 慢是因为工具返回的整页 HTML 塞回了上下文，下一步把它截断」。**这个判断没有数据支撑，查下来是错的：**

| 检查项 | 实测 | 结论 |
|---|---|---|
| 第 2 轮输入 vs 第 1 轮输入 | 3101~4188 vs 2875~3723，**只多 226~465 token** | 工具返回（含 HTML）贡献很小 |
| `bind_tools` 的 schema 体量 | 4271 字符（11 个工具） | 固定开销，不是可截断的"工具结果" |
| 工具结果截断 | `_TOOL_RESULT_PREVIEW_CHARS=1200` 只用在"轮次用尽"的兜底路径 | 正常路径确实没截断，但**那里本来就没多少内容** |

第 1 轮就有 2875~3723 token 的输入，几乎全部是 **system prompt + 工具 schema 的固定开销**，不是历史、不是工具结果。所以「截断工具返回」这个改动即使做了，也只能省几百 token。

## 1. 真正的杠杆：输出 token

Agent 23.4s 拆开是三次 LLM 调用，输出 token 与耗时几乎线性对应：

| 调用 | in_tokens | **out_tokens** | 耗时 | 换算 |
|---|---|---|---|---|
| 第 1 轮（决定调工具） | 2875~3723 | 63~365 | 1.7~6.7s | — |
| 工具内（简历结构化抽取） | 2563~2806 | **820~845** | 9.2~11.7s | ~11.5s/800token |
| 第 2 轮（收尾回答） | 3101~4188 | **441~551** | 7.5~9.2s | ~16s/1000token |

合计输出约 1300~1700 token / 23.1s ≈ **70 token/s**（6 个样本估算，不是精确基准）。
**输入 token 的增减对总时长影响很小，输出长度才是分母。**

## 2. 三个候选改动

### A. 收尾轮回答瘦身（推荐先做）

**改什么**：`build_agent_system_prompt()` 里加一条约束——工具已经产出文件时，回答限一两句，
不复述内容、不列条目。

**预期**：线上第 2 轮输出 441~551 → 目标 150~200 token，省 4~6s（**需实测，见下**）。

**风险**：回答信息量下降。用户可能想知道"改了什么"——现在模型会列文件名、格式、包含段落。
压成一句话后这些信息只能从文件里看。

**为什么不承诺具体数字**：我做了离线对照（同一段工具结果 + 两种 prompt，各 2 轮）：

```
现状 prompt   3348ms  out_tokens=176
一句话确认    2743ms  out_tokens=136
```

只差 600ms，因为离线环境复现不出线上的 500 token 输出（线上 system prompt 里有技能目录、
工具规范、历史）。**所以这个改动必须先改、再测、看 out_tokens 真降了才留下**，
不能按"省 5 秒"去立项。

**验证方式**：改完跑 `-Stage 3 -Mode agent -Trace -RequestsPerUser 3`，
对比 `_ai_requests.csv` 的 `st_agent` 与 PERF 日志里第 2 轮的 `out_tokens`；
同时人工看 3 个生成的 HTML 是否完整。

### B. 工具内抽取瘦身 —— **已诊断，无收益，不做**

原以为这里能省 4s（`max_tokens=6000` 太宽松）。查完源码，结论相反：

- `resume_generation_service.py:437` 的注释写「一份双页简历 JSON 约 2500–3500 token」，
  **但线上实测输出只有 820~845 token**，`max_tokens=6000` 从来没被用满。
- 输出已经是一份精简的结构化简历 JSON（约 600~800 汉字），再裁字段就是真的少内容了。

所以这里没有"浪费"可省：把 `max_tokens` 降到 2000 只减少失控风险，不影响耗时。
（顺带一个遗留问题：那条注释的数字是错的，会误导后来的人，应该改掉。）

### C. RAG 的 verify 异步化（不建议做）

RAG 现在 3.3s，verify 占 1.2s。要省这 1.2s 得改非流式响应契约（`verification` 字段变延迟/为空），
收益 36%、成本是接口语义变更。**性价比不如 A。**

## 2.5 诊断结论：Agent 没有浪费，只有输出速度

三条路径逐一排除后，Agent 的 23.4s 可以完整解释为：

```
总输出 token ≈ 63~365 + 820~845 + 441~551 ≈ 1300~1700
耗时 23.1s ÷ 1600 token ≈ 70 token/s
```

**这是 qwen3.8-flash 吐字的速度，不是哪里有 bug。** 没有可截断的冗余输入，
没有可压缩的无效输出（除了 A 里讨论的"收尾回答是否要那么长"）。
除 A 之外，唯一能降 Agent 时间的手段就是换更快的模型（见第 3 节）。

## 3. 一个更大的变量：主模型

Agent 的三次调用全部走 `qwen3.8-flash`。上一轮实测 `qwen3.7-flash` 比它快 1.48x
（压缩场景，1028 vs 2248ms）。如果主模型换档：

- Agent 23.4s → 约 16s
- memory 2.2s → 约 1.5s
- RAG 3.3s → 约 2.4s

**收益比 A+B 加起来还大，但这是产品决策**：主模型降档会改变回答质量，而这个项目的卖点之一是
"能生成可用的简历"。我不建议由压测数据单方面推动，应该用 5~10 个真实 JD 做质量对比。

## 4. 推荐顺序

1. **A（改 prompt）** — 只改一处文案，可回滚，先改再测，不达标就撤回。这是**唯一**还能动的代码。
2. **B 不做**（已诊断无收益），只顺手把那条错误注释改掉。
3. **C 不做。**
4. **换主模型**是唯一能动 Agent 大头的手段，但要单独做质量评估，不算在压测优化里。

## 5. 两个提醒

**第一，Agent 是「生成文件」场景，用户心理预期本来就是慢**（十几秒生成一份简历是合理的）。
把 23s 压到 18s，用户体验的边际改善远小于「生成失败/生成不完整」的风险。
如果只能投入一件事，我建议先确保简历生成的正确性，而不是它的速度。

**第二，我这一轮的两个判断都被自己的数据推翻了**（"截断工具返回"、"抽取输出过长"）。
这说明看整体数字猜瓶颈很容易猜错，值得先花十分钟做分解再动手。这条比方案本身更有用。
